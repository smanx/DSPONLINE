# 自动工厂封存影子实验报告（2026-07-31）

## 结论先说

“稳定 60 秒后自动封存，外部条件变化时自动解封”在机制上可行，但不能简单地停止计算后继续凭空增加产物。正确做法是把一组稳定产线转换成带输入、输出、电力、燃料和容量边界的“结算合同”，只在边界事件发生时推进；守卫条件不成立时，必须先结算到事件时刻，再恢复精确模拟。

对本次用户终局存档进行只读影子实验后，逐建筑第一版方案的收益明显低于最初设想：

- 保守估计：单步模拟耗时下降 **7.6%**，等价处理速度提高约 **8.2%**。
- 理想估计：单步模拟耗时下降 **11.2%**，等价处理速度提高约 **12.6%**。
- 这不足以单独解决 7 天、30 天离线结算问题，也不适合直接作为默认功能上线。
- 真正值得继续做的是“整条产线/整颗行星合同化”，并与关键事件离线快进结合；逐建筑封存可作为其识别和安全守卫基础。

## 样本和隐私

实验使用用户提供的终局存档，只在内存中克隆后运行：

- 存档大小：4,917,957 字节，约 4.92 MB。
- GameState 版本：42。
- 实体：2,648 个。
- 传送带线路：5,746 条。
- 物流站：416 座。
- 原始文件没有写入、修复、覆盖或重新保存。
- 实验结束后原始内存状态哈希保持不变。
- 报告和 JSON 结果不包含存档路径、实体 ID、物品明细、玩家身份或存档哈希。

## 实验方法

本次没有让近似算法接管正式状态，而是使用“影子封存”：

1. 克隆存档，并用当前正式模拟器精确运行 60 个模拟秒。
2. 记录每个实体和线路的状态变化，识别最长 20 秒的重复周期。
3. 把满足条件的对象标记为“如果正式实现，此刻可以封存”。
4. 继续用精确模拟器运行 5 分钟，同时在旁路重放预测变化。
5. 真实变化与预测合同不一致时，记录为自动唤醒；影子预测绝不覆盖真实状态。
6. 按当前 profiler 实测的生产、线路、物流和电力耗时，以及验证后的可封存覆盖率，估算正式专用实现能节省的时间。

短期复核还执行了“60 秒学习 + 60 秒验证”；延长到 5 分钟后结论只小幅变化，因此下面以更严格的 5 分钟结果为准。

## 当前精确模拟基线

360 个精确模拟秒的结果：

| 指标 | 实测结果 |
| --- | ---: |
| 平均单步耗时 | 110.402 ms |
| 中位单步耗时 | 107.443 ms |
| P95 单步耗时 | 123.408 ms |
| 最慢单步 | 221.375 ms |
| 总引擎耗时 | 39,744.785 ms |

主要耗时分布：

| 子系统 | 实测耗时 | 占引擎总耗时 |
| --- | ---: | ---: |
| 物流 | 25,748.844 ms | 64.8% |
| 传送带 | 9,052.111 ms | 22.8% |
| 电力 | 1,852.582 ms | 4.7% |
| 生产 | 1,397.930 ms | 3.5% |

物流派遣本身约占总引擎时间的 46.2%，仍然是最大瓶颈。现有索引已经让候选匹配很便宜，但大量实际派遣、路线推进和槽位检查仍会每步发生。

## 60 秒后有多少对象能封存

| 对象 | 总数 | 60 秒时看似稳定 | 再验证 5 分钟仍稳定 | 验证期自动唤醒 |
| --- | ---: | ---: | ---: | ---: |
| 实体 | 2,648 | 1,098 | 943 | 155 |
| 线路 | 5,746 | 2,240 | 1,547 | 693 |

需要注意，稳定实体中有 582 个是仓储类对象。它们多数只是没有变化，本来就几乎不消耗生产计算，因此“943 个实体稳定”不能直接理解为节省 35.6% CPU。

更有意义的覆盖率如下：

- 生产/采集计算覆盖率：22.38%。
- 线路计算覆盖率：26.92%。
- 物流站计算覆盖率：6.25%，416 座中只有 26 座保持稳定，其中仍在活动的只有 5 座。
- 电力对象覆盖率：56.86%，但电力本身只占总耗时约 4.7%。
- 同时要求普通生产建筑自身和所有相邻线路均稳定后，第一版安全候选仅 126 座。

自动唤醒情况：

- 60 秒学习后，5 分钟内有 14.12% 的实体候选发生变化并需要唤醒。
- 线路候选的唤醒率更高，为 30.94%。
- 仍保持封存资格的对象，影子合同最终值与精确模拟值一致；没有出现“未唤醒但算错”的对象。

这说明 60 秒足以筛掉一部分不稳定对象，但不能只检查一次后永久冻结。物流、缓存边界和线路流量会让相当多的对象在数分钟后重新变化。

## 性能收益

基于实测子系统耗时和验证后的覆盖率：

| 方案 | 预计平均单步 | 耗时下降 | 等价处理速度提升 |
| --- | ---: | ---: | ---: |
| 当前精确模拟 | 110.402 ms | - | - |
| 保守的专用封存实现 | 102.019 ms | 7.59% | 8.22% |
| 理想的专用封存实现 | 98.049 ms | 11.19% | 12.60% |

这里的“专用实现”不包括本实验脚本的通用 JSON 树差分。影子脚本为了证明状态变化，会递归比较完整对象，额外开销很大，不能放进游戏循环。正式版本必须使用引擎内部脏标记、拓扑版本和边界事件，守卫开销应控制在每模拟秒 1～2 ms 以内，否则会抵消封存收益。

以上数字是基于真实 profiler 的工程估算，并不是已经接入引擎后的最终跑分。正式上线前仍需用 A/B 引擎和状态哈希做一次实际测量。

## 为什么本存档收益不高

这份终局工厂最贵的不是单台熔炉或制造台，而是 416 座物流站持续进行派遣和路线推进。逐建筑封存最容易识别的是闲置仓库、稳定矿脉和部分普通机器；它们不是当前最大耗时来源。

物流站即使长期平均流量稳定，每一秒也可能出现以下离散变化：

- 船只出发和到达。
- 货物预留、装载和卸载。
- 槽位跨过起送阈值。
- 供需伙伴变化。
- 能量、翘曲器或载具状态变化。

因此“每个字段 60 秒完全重复”会把多数物流站排除。若要取得大收益，必须把多个建筑、线路和物流边界合成一个更大的结算单元，只保留区域对外的净输入和净输出。

## 正式功能应该怎样做

### 1. 先做封存合同，不直接冻结对象

合同至少包含：

- 每秒输入和输出，以及配方副产物。
- 电力需求、燃料和增产剂消耗。
- 矿脉储量消耗和资源模式。
- 输入、输出、线路和物流槽容量边界。
- 科研、戴森和建筑制造等外部进度边界。
- 合同覆盖的实体、线路和拓扑版本。

内部循环中相互抵消的流量不再逐建筑结算，只结算区域边界的净变化。

### 2. 采用事件驱动自动解封

以下任一事件发生时，必须先把合同精确推进到事件时间，再解封：

- 玩家建造、拆除、堆叠、改配方、改线路、改物流设置。
- 科技完成、速度或容量规则变化。
- 供电率、燃料、增产剂或矿脉状态跨过安全边界。
- 输入耗尽、输出将满、物流到达或路线伙伴变化。
- 蓝图、Mod、资源模式或时间倍率改变。

守卫失败时不能继续使用旧速率。实现初期应保留步前状态，丢弃失败的合同步，并对该步重新执行精确模拟。

### 3. 用整条产线或整颗行星作为第二阶段目标

建议顺序：

1. 只封存没有物流站、没有随机分支的闭合生产子图。
2. 再封存对外只有少量物流槽的整颗行星，以净流量合同连接外部。
3. 最后把合同引擎用于离线关键事件快进。

第一阶段容易证明物资守恒；第二阶段才可能跳过本存档中最贵的线路和物流内部计算；第三阶段才有机会让 7 天离线从几十分钟降到分钟甚至秒级。

## 对玩家体验的影响和风险

正确实现后，玩家不应看到产量减少或“建筑真的睡着”。检查器仍可根据合同显示实时插值进度和预计流量，库存只在真实结算点显示真实值。

可能的代价：

- 第一次达到稳定状态前仍需精确运行至少 60 秒。
- 频繁改造的行星会反复解封，收益很小。
- 为保证确定性，边界复杂的区域会主动拒绝封存，不能追求虚假的高覆盖率。
- 合同和唤醒状态会增加少量内存；这些运行时缓存不应写入 GameState，也不应影响存档版本。
- 如果为了提高覆盖率忽略电力、容量或物流事件，会产生资源复制、丢失或离线结果不同，这是不可接受的。

## 建议决策

不建议现在把“逐建筑 60 秒自动封存”直接作为正式默认功能开发。对本存档只有约 8%～13% 的处理速度收益，测试和确定性风险高于收益。

建议保留本分析器作为性能夹具，下一步做一个只支持“闭合生产子图/整颗行星”的合同原型。原型进入正式模拟前必须满足：

- 1 小时、8 小时、24 小时、7 天和 30 天结果与精确模拟状态哈希一致。
- 在线、离线、分段运行、保存重载和时间扭曲结果一致。
- 任意修改能在一个安全模拟步内自动解封。
- 本样本实际单步耗时至少下降 30%，否则不值得承担系统复杂度。
- 与关键事件离线快进结合后，再以 7 天小于 30 秒、30 天小于 2 分钟作为终局目标。
