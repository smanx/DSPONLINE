### 已确认的唯一失败字段

存档中有两座时间扭曲装置：

| 实体 | 数量 | 状态 |
| --- | --- | --- |
| `entity_36721` | `machineCount=3` | 非当前主控装置 |
| `entity_36738` | `machineCount=1` | 当前主控装置 |

服务端 `server/index.mjs` 的 v34+ 云存档校验对每一个 `time_warp_device` 强制要求：

```text
machineCount 必须严格等于 1
```

同一段校验还对 `micro_black_hole_connector` 强制要求 `machineCount === 1`。

客户端 `src/game/storage.ts` 则只要求实体 `machineCount` 是非负安全整数，并会原样保留这个 v46 状态。因此同一个文件出现了：

```text
客户端：存档合法，可以加载、保存和导出
服务器：存档格式非法，拒绝上传
```

### 最小对照实验证明

使用临时目录、临时 SQLite 和本地同构云服务测试，未连接生产服务器：

| 输入 | 结果 |
| --- | --- |
| 原始附件 | HTTP 400，`SAVE_FORMAT_INVALID` |
| 只把 `entity_36721.machineCount` 从 3 临时改为 1，并重算 checksum | HTTP 200，云修订创建成功 |

没有修改其他字段。原始附件保持只读且未被写回。该结果证明时间扭曲装置堆叠是本存档的唯一云上传拒绝原因。

### 上游生成根因

这不是玩家手工篡改存档，而是批量操作路径可以生成服务器随后拒绝的状态。

当前大多数建筑命令已经把时间扭曲装置和微型黑洞连接装置视为“单实体巨构”：

- `placeBuilding()` 强制单次只放置 1 台；
- `addBuildingToGroup()` 禁止给这两种建筑执行普通 `+1`；
- 蓝图放置会把这两类模板的 `machineCount` 固定为 1；
- 单建筑自由输入数量检查会拒绝目标数量不等于 1。

但 `src/game/engine.ts` 的 `batchIncreaseSelection()` 使用通用 `getBuildingStackAdditionCheck()`，没有复用“单实体巨构只能为 1”的领域规则。框选或多选后执行批量 `+1/+10/+100/自定义` 时，时间扭曲装置和微型黑洞连接装置仍会被直接增加。

这解释了本档中的 `time_warp_device ×3`，也意味着微型黑洞连接装置存在同类潜在云存档阻断。

### 必须修复的两层问题

#### 1. 阻止以后继续生成非法单体巨构堆叠

`batchIncreaseSelection()` 必须与单建筑数量调整共用同一份领域检查：

- `time_warp_device` 保持 `machineCount=1`；
- `micro_black_hole_connector` 保持 `machineCount=1`；
- 混合选择中普通建筑和传送带仍按要求增加；
- 两类单体巨构应计入“唯一建筑已跳过”或等价的明确结果；
- 不得为被跳过的巨构扣除施工托盘物品；
- 预览与确认后的实际执行必须使用同一检查，防止预览和提交之间分叉。

同时审计所有可能直接写入 `machineCount` 的命令：单击增加、自由输入、混合批量增加、蓝图创建/放置、施工队列和迁移。不能只给当前 UI 写前端特判。

#### 2. 兼容已经由正式版本生成的历史堆叠

推荐的最小安全热修：

1. 云服务对这两类建筑继续验证 `machineCount` 为正安全整数，但不再因为大于 1 拒绝整份存档。
2. 游戏运行仍只把一个节点视为一座单体巨构，堆叠数量不额外放大黑洞销毁端口或时间扭曲倍率。
3. 保留历史数量，让玩家之后可以通过明确的拆分、回收或降至 1 操作取回额外建筑。
4. 不在上传、加载或保存时静默把 3 改成 1；这种做法会无提示吞掉 2 个玩家建筑。

不推荐在 P0 热修中自动拆成多个画布节点：自动生成位置、连接和主控关系会扩大保存迁移风险。若产品后续希望彻底规范历史堆叠，应单独设计“保留 1 台并把多余数量退回施工托盘”的显式修复入口，并让玩家确认。

### 服务器与客户端校验应消除分叉

本次还应至少做到以下一项：

- 抽取可在浏览器和 Node 共用的云存档结构校验模块；或
- 为服务端的每一条额外强约束增加对应客户端 preflight 和共享合成夹具。

长期推荐第一项。当前服务端维护了一份数百行手写 GameState 白名单，而客户端 `inspectSave()` 使用另一套迁移和结构规则，版本继续增加后仍会重复出现“本地合法、云端非法”。

服务端拒绝时也应返回不包含玩家隐私的稳定原因码，例如：

```text
SAVE_FIELD_INVALID
path: entities[*].machineCount
rule: unique-megastructure-stack
```

客户端可据此显示可行动提示，而不是统一显示“格式无效”。响应不得返回完整实体、库存、玩家 ID 或存档片段。

1. v46 存档包含历史 `time_warp_device.machineCount=3`：客户端可加载、导出和重新加载，数量不丢失。

1. 临时 SQLite 中上传上述两个历史堆叠合成存档，服务端返回 200。

6. 历史堆叠不会放大服务器排行榜对时间扭曲或黑洞能力的计算。

## 当前玩家临时绕过方式

在补丁发布前，不要手工编辑 JSON，因为修改后 checksum 会失效。若玩家必须立即上传，可在游戏内：

1. 找到非当前主控、显示为 `×3` 的时间扭曲装置。
2. 完整回收该节点，确认三台装置均返回施工托盘。

4. 本地保存成功后再次上传云存档。

本附件中的 `×3` 装置不是当前主控装置，因此该绕过不会移除当前主控；但仍建议先导出本地备份。开发修复不得把这个人工绕过当作正式解决方案。

| 保存快照状态 | 时间扭曲关闭，请求倍率 12，待结算预算 0；无限科技 `matrix_compression` 等级 316 |

在本地 1.0.32 只读 Node 基准（不是线上 1.0.33 的完整源码基线）中：

- 创建纯挂机宏观会话约 `12,963 ms`；推进 60 秒约 `312 ms`；停止时重新初始化并最终校验约 `8,393 ms`。
- 单独对约 20 MB payload 执行 `inspectSave()` 约 `8,278 ms`，最终原始 payload 约 `19,902,389` 字节。
- 精确模拟首次 1 秒约 `1,012 ms`，下一秒约 `192 ms`，12 秒合计约 `3,321 ms`。

这些数值尚未计入浏览器 Worker 的 structured-clone、主线程 React 状态更新和大量 DOM/画布重绘，因此低端设备上看到“页面无响应一会儿”是符合现象的。问题不是单一的网络等待，而是停止路径把多项重任务串在了一起：

1. 停止时新建 finalizer，重新初始化并再次做精确校准；
2. Worker 生成完整 GameState，序列化并运行完整完整性检查；
3. 完整状态跨 Worker 回传，主线程持久化后立即更新 11,604 个实体和 27,669 条线路的 UI；
4. 这些工作在同一个用户操作链中发生，形成长主线程任务。

### 推荐最小修复

1. 复用当前纯挂机会话的最近一次已验证检查点和校准结果，停止时不要重新创建 finalizer 或重复跑三段校准。
2. Worker 只序列化一次最终 envelope，主线程接收一个已验证结果或紧凑 delta；不要先传完整候选状态、再传完整最终状态。
3. 结算、写盘、UI 展示拆成阶段：先保存检查点，再异步写最终存档，界面先显示“正在保存/可取消”，不要同步 `setGame()` 触发全量 React/画布重建。
4. 使用幂等的 `settlementId/checkpointHash`，重复点击、迟到 Worker 消息和重试只能提交一次。
5. 保留最近成功检查点直到最终保存确认；取消只取消未提交计算，不回滚已经确认的结算。
6. 1.0.33 已有约 30 秒 deadline、进度阶段和 conservative/recovering 分支，开发时应沿用这些机制；不要因无限科研存在就强制回到长时间精确重放。

### 必须新增的测试与验收

- 使用本附件在桌面和手机上连续点击停止/结算 10 次：主线程 Long Task 不得超过产品门槛（建议 `200 ms`，超过时仍必须显示进度而不是无响应），按钮可取消且不重复结算。
- 记录“校准开始、检查点保存、序列化、持久化、UI 应用”各阶段耗时；终局存档停止总墙钟时间建议不超过 `2 s`，低端移动设备允许降级但不得无限等待。
- 结算前后保存 envelope checksum、库存、在途货物、科研进度和戴森关键字段可重放一致；刷新、Worker 崩溃和网络失败均从检查点恢复。
- 小存档回归：不能为了终局优化让普通纯挂机变慢或改变实际产量。

- 同一存档在“理论峰值”和“实际结算”两栏显示不同但可解释的值；没有“126E”这类单位误读。

#### 代码根因

1. `src/game/engine.ts:5528` 和 `src/game/engine.ts:5819` 会执行 `state.metrics = { ...state.planetMetrics[state.activePlanetId] }`，因此根对象的 `metrics` 永远只代表当前星球。
2. `server/index.mjs:1398-1404` 的 `leaderboardMetricsFromSave()` 读取 `state.metrics.totalItemsPerMinute` 作为 `peakThroughputPerMinute`，没有遍历 `state.planetMetrics`。
3. 客户端 `src/game/account.ts:289-291` 已经按 `Object.values(game.planetMetrics)` 累加，形成“本地账号口径为全局、服务端排行榜口径为当前星球”的跨端分叉。

#### 最小修复建议

- 服务端排行榜的吞吐候选值改为对 `state.planetMetrics` 中每颗行星的同一指标使用饱和加法；`state.metrics` 只继续作为当前行星 UI 快照，不能再作为全局排行榜来源。
- 抽取客户端与服务端共用的“全星区指标聚合”规则，至少明确空值、重复星球键、非有限数、负数和历史旧存档缺失 `planetMetrics` 时的回退行为。
- 统计口径同时保留两个字段：`activePlanetThroughputPerMinute`（当前行星）和 `galacticThroughputPerMinute`（全星区），排行榜只使用后者；后续再叠加稳定窗口“实际结算吞吐”。
- 不把 `matrix_research`、白糖、硅矿等中间节点重复相加到“最终产品吞吐”字段。若产品要展示“全物品处理总量”，应明确它是各物品产出之和；排行榜和生产统计必须显示指标定义与统计窗口。

#### 必须新增的回归测试

1. 构造至少 3 颗行星且切换 `activePlanetId`，服务端排行榜吞吐始终等于三颗行星指标合计，不随当前星球变化。
2. 使用本 19 MiB 存档的只读副本验证：当前星球值约 `14.50` 十亿/min，全局值约 `189.65` 十亿/min；两者不能混用。
3. 客户端账号、生产统计和服务端排行榜对同一存档得到相同的全局吞吐；缺失或非法行星指标不会产生 `NaN`、`Infinity` 或负数。
4. 旧云存档只有根 `state.metrics`、没有完整 `planetMetrics` 时保留兼容回退，并明确标记“旧口径”，不得静默伪造全局值。
5. 对理论速率、实际 `totalProduced` 增量、堵塞、缺料和物流不足分别测试，避免修复跨行星漏算后又把名义产能误当实际产量。

#### 历史排名风险

该修复可能把本用户吞吐从约 `145 亿/min` 调整为约 `1896 亿/min`，并显著改变排行榜排序。这不是玩家存档损坏，也不会改写实体、库存或生产；开发前必须决定采用“按新口径重算历史榜”还是“旧口径/新口径分榜并从补丁版本起生效”，保存指标版本与审计记录，不能直接覆盖历史成绩。

### 已确认的服务端错误含义

服务端 `readJson()` 在收到以下请求时进入 gzip 解压路径：

```text
Content-Encoding: gzip
```

若 `gunzipSync()` 失败，它明确返回：

```text
HTTP 400
code: REQUEST_ENCODING_INVALID
error: 请求压缩内容无效
```

因此该反馈不是以下问题：

- 存档 checksum 错误；
- GameState/envelope 版本不兼容；
- 云档体积超过 32 MiB；
- 玩家登录态、云修订冲突或网络超时；
- 服务端成功接受后又丢失数据。

服务端本地隔离测试已验证：合法 gzip 上传返回 200，故意损坏 gzip 返回同一 `400 / REQUEST_ENCODING_INVALID`。这说明服务端解压和错误分类正常，错误发生在 Android 请求到达服务端之前。

### 根因：CapacitorHttp 劫持破坏 gzip Blob 正文

当前 Android 配置启用了：

```json
"CapacitorHttp": { "enabled": true }
```

这会把跨域 `window.fetch` 改由原生 Capacitor HTTP 插件执行。云上传在请求超过 256 KiB 时会：

1. 使用 `CompressionStream("gzip")` 产生压缩字节；
2. 将字节包装为 `new Blob([compressed.buffer])`；
3. 保留 `content-encoding: gzip`；
4. 调用被 CapacitorHttp 劫持的 `fetch`。

Capacitor Android 的 `native-bridge.js` 取到了 `options.body` 的 `Blob`，但 `convertBody()` 只处理 `ReadableStream`、`Uint8Array`、`FormData` 和 `File`，没有 Blob 分支。Blob 因此落入默认的：

```text
data: Blob
dataType: json
```

原生桥接的 JSON 边界无法保留 Blob 二进制内容。最小只读验证中，合法 gzip 的 Blob 被 JSON 化后成为 `{}`；服务器再按 gzip 解压 `{}` 时得到 `Z_DATA_ERROR`，与玩家看到的错误完全一致。

线上 `1.0.33+2bd81de8d7f1` 的公开 `cloud` bundle 仍采用“gzip Blob + 仅网络超时才 raw retry”的逻辑，因此这个问题不能仅靠让玩家重试解决。现有客户端在收到明确的 `400 / REQUEST_ENCODING_INVALID` 后直接报错，并不会补发一次原始 JSON。

### 为什么不能只修服务器

服务端收到的是带有 gzip 头、但正文已经被原生桥接改坏的数据。原始存档正文没有到达服务器，服务器无法从 `{}` 或损坏字节恢复出玩家存档。

接受损坏 gzip 并把它当 JSON 也不能解决问题，反而会扩大请求格式歧义和安全风险。正式修复必须在 Android 客户端发送前避免 gzip Blob；服务端只需要保持严格解压和明确错误码。

### 推荐最小热修

#### 1. Android 原生应用禁用云上传 gzip

在 `src/game/cloud.ts` 的压缩决策处，检测 `__APP_PLATFORM__ === "android"`（或等价的 Capacitor 原生运行时），直接返回 `null`，让现有上传流程发送字符串 `rawBody`：

```text
Content-Type: application/json
无 Content-Encoding
body: JSON string
```

字符串正文是 CapacitorHttp 已支持的路径，不经过 Blob 二进制桥接。当前客户端原始请求安全上限为 30 MiB，服务器展开后上限为 32 MiB；正常 Android 存档应可直接恢复上传。

不要全局关闭 `CapacitorHttp`：它可能承担 Android 跨域请求、更新检查和网络兼容性。只对云存档压缩正文绕开 gzip 即可。

#### 2. 所有平台对明确 gzip 拒绝补一次 raw 回退

当且仅当首次请求实际使用 gzip，且服务端返回：

```text
status === 400
payload.code === "REQUEST_ENCODING_INVALID"
```

客户端应在原始正文不超过 30 MiB 时补发一次无 `Content-Encoding` 的 raw JSON 请求。该错误发生在服务端读取业务 payload 前，不会创建云修订；`expectedRevision` 仍可防止并发覆盖。

此兜底保护未来的异常 WebView、代理或浏览器实现，但不能替代 Android 的“预先不压缩”，否则每次 Android 上传都会多发一条必定失败的请求。

#### 3. 大于 30 MiB 的后续方案

本 P0 不应为了保留 gzip 而重新实现复杂原生二进制桥接。若后续 Android 原始 JSON 真实超过 30 MiB，应单独设计并测试二进制安全的文件上传/原生请求协议（例如明确 base64/文件 URI + 服务端有限解码），并重新评估扩大后端解压上限的拒绝服务风险。

在该方案完成前，客户端必须明确显示“原始请求超过安全上限，本地档未修改”，并提供导出/网页端上传入口；不得静默截断。

### 必须新增的测试

#### Client

1. Android 编译常量下，`compressCloudRequestBody()` 对 256 KiB、1 MiB、7 MiB 和 20 MiB 原始正文均返回 `null`；发送 body 必须是 string，headers 不含 `content-encoding`。
2. Web/PWA 非 Android 环境继续发送合法 gzip Blob；现有压缩和 5 秒压缩超时回退测试保持通过。
3. 模拟首次 gzip 请求返回 `400 / REQUEST_ENCODING_INVALID`：只补发一次 raw JSON，第二次 headers 不含 gzip，成功后只得到一个新修订。
4. raw 回退遇到 409 时进入现有冲突流程；取消、网络超时和未知状态保持既有幂等确认逻辑。
5. rawBody 超过 30 MiB 时不发送请求，显示准确上限和“本地存档未修改”。

#### Server

1. 保留合法 gzip 200、损坏 gzip `REQUEST_ENCODING_INVALID`、解压超限 413 的既有边界。
2. raw JSON 与 gzip JSON 的相同 payload 生成等价 cloud metadata、checksum 和排行榜更新。
3. 损坏 gzip 和 raw fallback 之间不得留下半条 cloud revision、上传指标或排行榜提交。

#### Android Package

1. 构建真实 debug APK，使用最小隔离云服务和 Android WebView 119+ 上传有效 1 MiB、2 MiB、7 MiB、20 MiB 存档。
2. 抓取测试服务收到的请求头和 body：Android 必须为 raw string、无 `Content-Encoding: gzip`，并由 `inspectSave()` 通过。
3. 从当前正式 APK 覆盖安装候选 APK；本地主档、账号 token、云修订比较和下载恢复均保持。
4. 使用真实正式 API 做仅授权的测试账号 smoke，不上传任何玩家存档、不覆盖主云档、不向生产数据库写入夹具。

### 验收标准

1. Android App 使用合法、未改动的本地存档可以上传并下载回同一 checksum；不再显示“请求压缩内容无效”。
2. Web、Windows、PWA gzip 上传继续成功；旧 1 MiB、2 MiB、7 MiB 浏览器基准不回归。
3. 发生真正损坏 gzip 时，服务端仍返回明确 400；客户端最多安全地 raw 重试一次。
4. 所有失败、取消、冲突和超限路径均不写回或清除本地主档，不创建重复云修订。
5. APK 版本、更新清单、签名连续性、哈希和覆盖安装通过后才允许发布。

### 当前玩家临时绕过方式

在热修 APK 发布前，玩家可以先在 Android 系统浏览器访问 `https://dsponline.cn` 上传，或将应用内导出的存档导入桌面/网页版后上传。应用内本地存档不会因该错误被服务端清除；操作前仍建议导出一份本地备份。

### 当前代码依据（只读核验）

- `src/components/FactoryNodes.tsx:215-220` 的 `connectionHandleClass()` 只根据 `connectionDraft`、端口方向和 `itemId` 返回 `factory-handle--origin`、`factory-handle--compatible`、`factory-handle--incompatible` 或 `factory-handle--muted`。
- `src/styles.css:3973-3979` 将 `factory-handle--compatible` 设为绿色、放大并带光晕；这是本需求“相关接口”的现有视觉来源。
- `src/App.tsx:4360` 已将同一个 `connectionDraft` 传入所有画布节点；因此新增卡片状态可以从现有节点数据派生，不需要另建全局连接候选状态。
- `src/App.tsx:4389-4409` 当前节点 class 只在“寻线 → 任务 → 生产线/网络聚焦”之间做互斥选择，没有连线起点/候选卡片 class。
- `src/App.tsx:4665-4690` 的 `isValidConnection()` 还会额外检查同一行星、真实输出、端口、线路等级、重复线路和施工托盘库存。端口的绿色提示与最终合法性不是完全同一层，不能为了卡片高亮而放宽连线规则。
- `src/game/engine.ts:12450-12483` 的 `getAcceptedInputs()` / `getProducedOutputs()` 已覆盖配方、物流槽、配送枢纽、黑洞和矩阵科研等动态端口来源，应优先复用这些目录结果。

### 推荐实现边界

1. 在 `FactoryNodeData` 增加只读的派生视觉字段，或在 `App.tsx` 生成节点 class 时统一计算：
   - `factory-flow-node--connection-origin`：当前 `draft.nodeId` 的整张卡片；
   - `factory-flow-node--connection-candidate`：至少有一个与当前 draft 方向相反、且端口会显示 `factory-handle--compatible` 的节点。
2. 候选判定必须与端口现有语义一致：
   - 从输出端开始：目标建筑有匹配物品输入、空物品通用输入或已配置的合法特殊输入；
   - 从输入端开始：源建筑有匹配物品输出；通用输入不能反向制造不存在的输出；
   - 同向端口保持 muted，不把起点自身误算为候选；不同物品保持 incompatible；
   - 对未配置的物流站空槽、配送枢纽自动接口和黑洞通用接口分别覆盖，不能只检查普通配方数组。
3. 最终点击/释放仍调用现有 `isValidConnection()`。卡片高亮是“可尝试目标”提示，不得代替同星球、库存、端口容量和线路等级校验；释放到不满足最终条件的绿色卡片时继续显示现有失败原因。
4. 不要每次指针移动都扫描并修改完整节点对象。优先使用 `connectionDraft`、当前行星实体和已有 `acceptedInputItemIds/producedOutputItemIds` 做一次派生集合；只在 draft 改变、实体拓扑改变或切换行星时更新节点 class。若必须重算，确保不会破坏 React Flow 节点位置与选择集合。
5. class 组合改为数组过滤后 `join(" ")` 或等价组合，不再让连线候选状态被寻线/任务/网络状态无意覆盖。建议优先级：起点/候选的边框提示与寻线中心/上下游颜色可叠加；不要为了候选高亮把其他建筑全部 dim，保持大画布可读性。
6. 样式使用静态边框和低强度绿色光晕，固定卡片尺寸，不使用持续动画；终局·极限模式保留静态边框但禁用额外脉冲/粒子。亮色模式提供可读的绿色边框与浅绿色底色，不能依赖绿色文字和绿色背景的低对比组合。
7. 连线完成、取消、按 Escape、点击画布退出、切换星球、打开工作区和组件卸载时都必须令候选 class 清除；延迟的 React Flow 节点刷新不能把旧 draft 的 class 重新写回。

### 验收场景

1. 从熔炉/制造台输出端拖线：同物品输入卡片绿色高亮，其他物品卡片不高亮；起点卡片显示起点边框。
2. 从配方输入端拖线：拥有该物品输出的矿脉、机器、仓储或物流站卡片高亮；没有该输出的建筑不高亮。
3. 从通用输入（配送枢纽、黑洞接口、自动识别空槽）或向通用输入连线：相关目标卡片高亮，特殊端口仍按原规则命中。
4. 跨星球目标、同向端口、锁定建筑、重复线路、无传送带库存等情形不改变原有红色/失败提示；不得仅因卡片绿色而建立非法线路。
5. 多个候选建筑、画布缩放、节点 LOD、寻线模式、任务/网络聚焦、建筑选中和移动端触摸拖线下，候选卡片边框稳定、不抖动、不改变布局。
6. 连线成功、取消、Escape、切星球后查询 DOM 不存在旧的 `factory-flow-node--connection-*` class；刷新/保存/导入后的 `GameState` 和 checksum 完全不变。
