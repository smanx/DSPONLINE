## 一、方案结论

方案2在方案1的“30秒启动校准 + 库存守恒宏观账本”基础上增加两个能力：

1. 宏观账本每30个墙钟秒结算一次库存、产出、矿储和容量，同时可以在桶内准确计算预计断料、恢复和满仓时刻。
2. 稳定模式每挂机10分钟执行一次固定的30模拟秒影子校验，用真实Worker校正未来速率；校验不随机、不回改过去收益、失败也不自动停止。

纯挂机界面的“关键累计产量”不再显示生命周期累计最高的4种普通物品。默认改为终局指标：戴森总发电功率、白矩阵累计上传和本次增量、火箭发射、太阳帆吸收、戴森结构点，以及活动存在时的实际交付。

推荐产品提供两档：

- `稳定宏观模式`：默认。30秒守恒结算，每10分钟固定校验30模拟秒，准确度较高。
- `终局极限模式`：30秒守恒结算，但启动成功后不再运行真实引擎，性能和移动端温度表现最好。

两个模式必须使用同一套非负、守恒、容量、保存和恢复门禁。它们只在校验频率上不同，不能出现一个模式允许坏档、另一个模式才校验的情况。

## 三、当前界面问题

当前 [`TimeWarpIdleOverlay`](../../src/components/TimeWarpIdleOverlay.tsx) 使用：

```text
Object.entries(game.totalProduced)
  → 按生命周期累计数量倒序
  → 取前4项
```

这会产生三个问题：

1. 终局存档通常由矿物和常用中间产物占据前4名，玩家看不到白矩阵、戴森和活动进展。
2. 数字是整个存档的生命周期累计值，不是本次挂机新增，也不能判断当前产线是否断料。
3. 当前面板同时展示大量Worker内部诊断，真正的终局产出反而只占一个很小区域。

方案2应移除“累计数量最高4项”的选择逻辑，改为固定终局指标定义。普通物品不删除数据入口，但只进入可展开的“产线效率详情”，不占据默认首屏。

## 四、三个刷新周期

### 4.1 每秒：界面插值

每秒只更新以下轻量显示：

- 本次挂机时长；
- 根据当前宏观速率推算的本次新增；
- 距离下次30秒结算和10分钟校验的倒计时；
- 已知断料/满仓边界的倒计时；
- 当前关键产线最低效率。

这一层不调用游戏引擎、不复制GameState、不扫描实体和传送带，也不形成权威收益。

### 4.2 每30个墙钟秒：宏观守恒结算

每个宏观桶按以下顺序执行：

1. 计算本桶所有生产域的计划消耗和计划产出。
2. 把当前库存、桶内上游产出和聚合物流输入合并为可用供给。
3. 计算每条关键生产链能持续运行的比例。
4. 如果库存会在桶内耗尽，计算准确的耗尽时刻，分成耗尽前和耗尽后两段。
5. 扣除实际消耗，再写入实际产出；处理输出上限和满仓时刻。
6. 更新有限矿储、科研、戴森、建筑制造、量子库存和累计计数。
7. 保存整数余量，供下一桶使用。

30秒是权威宏观结算周期，但不是30秒后才发现断料。账本可以提前算出边界，UI每秒显示预计变化。

### 4.3 每10分钟：固定影子校验

稳定宏观模式从挂机正式开始后，每满10个墙钟分钟执行一次30模拟秒真实校验：

```text
前10模拟秒：预热缓存、线路和航线
后20模拟秒：记录生产、消耗、物流、科研和戴森真实速率
```

校验必须满足：

- 时间点固定，不使用随机抽检；相同存档和挂机时长在不同设备上触发相同校验序号。
- 只在Worker副本运行，不直接提交校验副本。
- 不回改刚刚过去的10分钟收益，只更新下一个宏观桶开始后的合同。
- 校验超时、Worker崩溃或结果非法时继续沿用最后有效合同，并保留下一次重试机会。
- 校验失败不能关闭纯挂机、暂停游戏或清空待结算时间。
- 终局极限模式跳过这一层，但仍执行30秒守恒账本和停止时完整存档校验。

建议的速率更新门槛：

| 与当前合同偏差 | 处理 |
| --- | --- |
| 小于15% | 保留当前合同，只更新诊断值 |
| 15%～30% | 对新旧速率做平滑合并，从下一桶生效 |
| 大于30% | 使用新合同替换未来速率，并突出显示“产线效率已重新校准” |
| 结构或存档校验失败 | 拒绝新合同，继续旧合同并记录原因 |

这些百分比是首轮建议，需要用五份真实存档做精确对照后再冻结，不应直接写死为无法配置的玩法规则。

## 五、库存不足时怎样结算

### 5.1 只有库存，没有上游补充

示例：铁矿库存10,000，产线消耗100/秒，没有继续采矿。

```text
断料时间 = 10,000 ÷ 100 = 100秒
```

前100秒按100%运行，之后对应生产链降为0%。界面显示：

```text
钢铁产线效率 0%
限制原因：铁矿库存耗尽
```

### 5.2 库存不足，但上游持续生产

示例：铁矿库存10,000，消耗100/秒，上游持续补充60/秒。

```text
净消耗 = 100 - 60 = 40/秒
库存耗尽时间 = 10,000 ÷ 40 = 250秒
耗尽后的可持续效率 = 60 ÷ 100 = 60%
```

前250秒按100%运行，之后自动降至60%。如果上游供应继续提升，下一宏观桶可以恢复效率。

### 5.3 多级产线

不能只检查玩家物资托盘。可用供给至少包括：

- 当前行星域中的托盘和允许参与宏观结算的库存；
- 生产建筑输入/输出对应的聚合缓存；
- 本桶内上游工序可生产的中间物品；
- 量子共享库存允许下载的数量；
- 聚合物流在本桶可转入的数量；
- 有限矿脉本桶可以开采的数量。

原料、基础加工、中间加工和终端产品应按生产图拓扑结算。石油、氢等循环配方需要按强连通生产组整体求可持续流量，不能按单条配方顺序造成凭空物品或循环归零。

## 六、效率的定义和显示

每个受监控终局产线分别计算：

```text
产线效率 = 当前可持续产出速率 ÷ 启动校准产出速率
```

结果限制在0%～100%。超过启动校准速率的增长单独显示为“较校准提升”，不把主效率显示成超过100%，避免玩家误解供给状态。

不建议把不同单位的戴森功率、白矩阵、火箭和太阳帆强行加权成一个“总体效率”。首屏应显示：

```text
关键产线最低效率 60%
主要限制：白矩阵产线缺少量子芯片
```

然后每个终局指标卡分别显示自己的效率。启动校准速率为0的项目显示“未运行”，不参与最低效率计算。

状态颜色建议：

| 效率 | 状态 |
| --- | --- |
| 90%～100% | 正常，绿色 |
| 60%～89.99% | 受限，黄色 |
| 0.01%～59.99% | 严重受限，橙红色 |
| 0% | 停止，红色并显示具体缺料或满仓原因 |
| 未校准 | 中性灰，不冒充0% |

颜色必须同时配文字和图标，不能只靠颜色传达状态。

## 七、纯挂机终局指标界面

### 7.1 顶部运行摘要

保留并调整为以下五项：

1. 实际倍率。
2. 本次挂机时长。
3. 关键产线最低效率。
4. 距离下次真实校验时间；终局极限模式显示“仅宏观结算”。
5. 保存/恢复日志状态。

“模拟积压”和详细Worker耗时不再占据首屏主指标。它们移动到可展开的“计算诊断”区域，只有排障时查看。

### 7.2 默认终局指标

#### 戴森总发电功率

- 数据源：`game.dysonSphere.generationKw + game.dysonSwarm.generationKw`。
- 显示：当前功率、本次挂机变化、较校准变化。
- 单位：复用 [`formatPowerKw`](../../src/game/units.ts)，自动显示 kW、MW、GW、TW、PW、EW及更高单位。
- 不把“功率”显示成累计电量；若以后加入累计发电量，必须另设卡片并使用能量单位。

#### 白矩阵累计上传

- 排行榜/云摘要口径：`game.totalProduced.universe_matrix`。
- 当前 [`summarizeCloudPayload`](../../src/game/cloud.ts#L275) 已把该字段命名为 `uploadedWhiteMatrix`，纯挂机界面应保持同一口径。
- 显示：累计上传、本次挂机新增、当前每分钟产量、当前效率。
- 数量格式：优先使用 [`formatQuantityCompact`](../../src/game/quantityFormat.ts)，悬浮或详情显示精确值；极大数自动进入科学计数法。

#### 戴森火箭

- 数据源：`game.dysonSphere.totalRocketsLaunched`。
- 显示：累计发射、本次新增、每分钟发射量、当前效率。

#### 太阳帆吸收

- 数据源：`game.dysonSphere.totalSailsAbsorbed`。
- 显示：累计吸收、本次新增、每分钟吸收量、当前效率。

### 7.3 次级终局指标

在主要四项下方使用无嵌套卡片的紧凑列表显示：

- 戴森结构点：`game.dysonSphere.structurePoints`；
- 当前壳面帆：`game.dysonSphere.shellSails`；
- 轨道太阳帆：`game.dysonSwarm.sailsInOrbit`；
- 无限科技：本次完成级数或当前研究进度；
- 建筑制造中心：本次完成终局建筑数量；
- 量子网络：本次上传、下载和当前主要瓶颈。

没有对应系统或校准速率为0时，次级项可以隐藏，避免空数据占满移动端。

### 7.4 活动交付必须单独显示

“白矩阵累计上传”和“活动交付白矩阵”不是同一个字段：

- 排行榜累计上传：`game.totalProduced.universe_matrix`；
- 活动实际交付：`game.endgame.constructionActivity.personalDelivered.universe_matrix`。

活动有效时增加独立的“巨构活动交付”行，并显示白矩阵、太阳帆、小型运载火箭和反物质燃料棒的个人交付。本次挂机活动增量必须来自实际交付字段，不能用累计生产量代替。

### 7.5 产线效率详情

默认只显示受限最严重的5项，按效率升序排列：

```text
白矩阵       60%  缺少量子芯片    3.60万/分钟
小型火箭     82%  框架材料不足    9,840/分钟
太阳帆      100%  正常            1.25亿/分钟
戴森吸收     74%  壳层容量受限    8,200/分钟
```

每项提供：当前效率、校准速率、当前可持续速率、瓶颈原因、预计耗尽/恢复时间。正常项目可以折叠，避免把界面重新变成生产统计页。

## 九、运行状态

界面标题和可用操作必须对应真实状态：

| 状态 | 标题 | 行为 |
| --- | --- | --- |
| 创建检查点 | 正在保护当前进度 | 还未开始累计宏观收益 |
| 30秒校准 | 正在校准产线 | 显示3个采样窗口进度 |
| 宏观运行 | 纯挂机运行中 | 显示终局指标、效率和下次校验 |
| 10分钟影子校验 | 正在后台校验 | 不阻塞收益和停止按钮 |
| 停止结算 | 正在结算并验证存档 | 冻结停止时间，允许失败后重试 |
| 恢复 | 正在恢复未结算挂机 | 从检查点与恢复日志重新生成 |
| 校验失败 | 使用上一份有效合同 | 不暂停、不清空时间，显示简短原因 |

不再使用“停止时会丢弃未提交切片”作为正常产品文案。方案2的验收目标就是未提交墙钟时间可恢复，而不是提前告知玩家一定会丢失。

## 十、实现边界

建议的最小所有权模块：

- [`src/App.tsx`](../../src/App.tsx)：纯挂机会话生命周期、开始/停止边界和Worker协调；应尽量提取控制器，避免继续扩大顶层文件。
- [`src/components/TimeWarpIdleOverlay.tsx`](../../src/components/TimeWarpIdleOverlay.tsx)：状态展示、终局指标、效率和停止交互。
- [`src/styles/time-warp-idle.css`](../../src/styles/time-warp-idle.css)：桌面、手机、字号和亮色/深色可读性。
- `src/game/pureIdleMacro.ts`：建议新增，保存纯函数账本、边界求解、效率和终局摘要。
- `src/game/pureIdleMacro.worker.ts`：建议新增，执行启动校准、10分钟影子校验和停止结算。
- `src/game/pureIdleRecovery.ts`：建议新增，管理IndexedDB恢复日志、心跳和所有者令牌。
- [`src/game/offlineApproximation.ts`](../../src/game/offlineApproximation.ts)：复用经过修复的校准摘要能力，不复用对所有GameState字段的无限仿射外推。
- [`src/game/storage.ts`](../../src/game/storage.ts)：只复用正式验证和序列化；不以清空或迁移重写作为失败恢复。

宏观合同和恢复日志属于设备上的临时会话数据，不应直接进入云存档或普通GameState。停止成功后只保存标准GameState结果，并清理临时日志。

## 十一、开发顺序

### P0：数据安全和恢复

- 完成方案1发现的负航线 `cargo` 修复。
- 候选状态提交前执行正式序列化和重新加载。
- 手动停止、自动超时、Worker崩溃都保留待结算墙钟秒。
- 建立IndexedDB恢复日志和多标签页互斥。

### P1：30秒库存守恒宏观账本

- 按行星域、量子域和特殊任务域聚合。
- 支持库存不足、上游持续补充、满仓、有限矿枯竭和循环配方。
- 输出每个终局产线的校准速率、可持续速率、效率和瓶颈。
- 固定桶与一次性长窗口结果保持确定性一致。

### P2：10分钟固定影子校验

- 实现10秒预热 + 20秒测量。
- 固定序号、Worker副本、未来合同更新和失败沿用旧合同。
- 稳定宏观/终局极限模式切换不改变存档格式。
- 记录校验耗时、内存峰值、偏差和替换原因。

### P3：终局指标覆盖层

- 移除累计最高4项普通物品逻辑。
- 接入戴森功率、白矩阵上传、火箭和太阳帆主指标。
- 增加次级终局指标、活动交付和受限产线列表。
- 把Worker详细诊断移入折叠区。
- 完成桌面、手机横竖屏、80%～200%字号和长数字测试。

### P4：性能与发布门禁

- 五份真实存档的10分钟、1小时、24小时、7天和30天矩阵。
- 稳定模式和极限模式分别执行8x、12x、16x、20x长测。
- Android WebView/Chrome验证内存、温度、切后台和恢复。
- 排行榜记录宏观算法版本；速通模式保持禁用或使用独立规则。

## 十二、性能预期与代价

方案1最大档的10分钟逐切片计算约313秒；一次30秒校准/长窗口原型约15秒。稳定模式每10分钟增加一次影子校验，如果复用单Worker副本和紧凑摘要，目标平均单核占用约增加2%～3%，整体仍预计比当前终局逐切片纯挂机降低约94%～97%。

终局极限模式不执行10分钟真实校验，长时间运行预计可降低约95%～99%以上CPU工作，但数值漂移通常更大。

需要接受的代价：

- 稳定模式每10分钟会出现一次短暂后台CPU和内存峰值；
- 极限模式不主动纠正长期速率漂移；
- 纯挂机不显示逐建筑、逐带和逐船动画；
- 校准后完成的生产加速科技可以延后到下次重启纯挂机生效；
- 终局指标是宏观口径，不等同于逐建筑精确统计；
- 移动端若影子校验内存过高，应自动建议极限模式，但不能未经玩家确认改掉收益规则。

当前快速路径在17.34MB存档的Node测试中曾出现约2.91GB RSS峰值，因此影子校验不得每10分钟创建多份完整状态克隆。应保持一个校准副本和紧凑数值摘要，校验结束立即释放。

## 十三、验收标准

### 宏观结算

- 库存不足时显示正确效率、具体物品和预计断料时间。
- 有持续上游时，库存耗尽后降到可持续比例，而不是直接归零或继续100%。
- 上游恢复、容量释放后效率能在下一个宏观桶恢复。
- 30秒分桶、10分钟分桶和一次性结算在同一合同下结果一致。
- 不产生负数、NaN、Infinity、超安全整数或物品不守恒。

### 定期校验

- 每10分钟固定触发，不使用随机数，不依赖CPU速度。
- 影子校验不暂停收益，不直接覆盖GameState。
- 校验失败沿用旧合同并保留待结算时间。
- 不同设备对相同会话触发相同校验序号和合同版本。

### 终局指标

- 戴森功率等于球体和戴森云发电功率之和，单位自动转换。
- 白矩阵累计上传与云摘要/排行榜口径一致。
- 活动实际交付不使用白矩阵累计生产代替。
- 火箭、太阳帆、结构点的累计值和本次增量均来自正确字段。
- 启动校准速率为0的指标显示“未运行”，不错误显示0%故障。
- 普通原矿不会再次占据默认终局指标区。

### UI与可访问性

- 桌面、390×844竖屏、844×390横屏和平板均能看到停止按钮。
- 80%、100%、125%、150%、200%字号下无文字或按钮重叠。
- 超长中文单位和科学计数法不会撑破网格。
- 效率状态同时使用文字、数值和图标，不只依赖颜色。
- 每秒UI插值不会导致整张画布或完整GameState重新渲染。

### 保存与恢复

- 停止、刷新、Worker强杀、浏览器休眠均不清空待结算墙钟时间。
- 候选结果通过完整性校验和 `migrateGame()` 重载后才提交。
- 主存档保存确认前不删除恢复日志。
- 活跃纯挂机会话必须结算后才能上传云存档。

## 十四、最终建议

采用方案2作为正式开发目标：

```text
启动检查点
  → 30秒校准
  → 每30秒库存守恒宏观结算
  → 每10分钟固定30模拟秒影子校验（稳定模式）
  → 终局指标与产线效率显示
  → 停止时完整结算、重载、保存
```

库存不足由账本直接计算，不依赖抽检碰运气；10分钟校验只负责纠正未来速率。界面以戴森总功率、白矩阵累计上传、火箭和太阳帆为核心，普通产量退到效率详情。这样既保留终局挂机真正关心的信息，也避免重新把纯挂机页面做成高频生产统计界面。
