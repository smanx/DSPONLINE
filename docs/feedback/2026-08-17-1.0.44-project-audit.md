## 执行结论

当前工作区并不是 `1.0.45`：`package.json`、Android 版本、应用内发布说明和生产记录均为 `1.0.44`。审计 HEAD 为 `e9e1503025e9563a9dbe4c5362183842ba797a07`，工作区开始及结束时均无用户未提交改动。`1.0.44` 发布代码提交为 `3e580c7`；两者之间只有 CI、测试工具和发布文档变化，没有 `src/` 或 API 实现变化。

项目的存档兼容边界仍为 GameState v46、save envelope v2、cloud schema v7、SQLite layout v2。本次没有发现类型检查、单元测试、服务端测试、运维工具测试、生产 Web 构建或生产依赖审计中的失败；但干净依赖树下的完整 Chromium E2E 为 396 通过、14 条件跳过、3 失败。因此，当前状态不应被标记为 1.0.45 可发布候选。

性能方面，默认画布 LOD 已有效，但超大存档主动运行仍是第一优先级。项目状态文档记录的 36.7 MB 实际附件 Continue -> Pause 为 20,887 ms、Long Task 峰值为 20,291 ms；本次没有该只读附件，不能宣称已复现或已修复。生产预览也确认 500 节点的完整显示/全展开路径会产生 1.2--2.9 秒操作和 125--605 ms 帧 P95，不能作为普通玩家默认路径。

## 已确认问题

### P0-01：完整 Chromium E2E 当前不可通过

复现：在隔离 worktree、根和 `server` 均执行 `npm ci` 后运行 `npm run test:e2e`，结果为 396 通过、14 条件跳过、3 失败，共 413 项。三项失败都在 1.0.44 的 Worker 存档/恢复链附近。

1. `tests/e2e/v138-release.spec.ts:13`，`save Worker returns a transferable verified sparse envelope`
   - 三次单 worker 重跑为 2 通过、1 失败。
   - 断言在 `saveGameSlotVerified()` 后同步调用 `loadGameSlot()`，偶发得到 `null`。
   - `localSaveStore.ts` 将 IndexedDB 的原始正文缓存限制为两份；`storage.ts` 同时提供同步缓存读取 `loadGameSlot()` 和权威异步读取 `loadGameSlotFromPersistence()`。实际 UI 已使用后者。
   - 修复方向：E2E 应使用 `await loadGameSlotFromPersistence()`；并审计所有导出 API，禁止新功能把同步缓存读取当作已持久化事实。`copySpeedrunSlotToNormalSlot()` 也应改为异步持久化读取和异步目标空槽校验，否则将来被 UI 调用时可能把未驻留缓存的槽位误判为空。

2. `tests/e2e/v143-large-save-hotfix.spec.ts:69`，`running simulation that advances during return receives one final cleanup save`
   - 三次单 worker 重跑为 2 通过、1 失败。
   - 失败时主存档 revision 只增加 1，而测试要求增加 2。测试只延迟 `save.worker` 并依赖时钟恰好在返回期间产生 Worker 推进；它没有先证明“新模拟结果已经在第一次保存后抵达”。
   - `App.tsx` 的返回逻辑以 authoritative checkpoint、pending budget、submission ID 和 viewport 签名决定是否需要 cleanup save，这个语义不能只用固定 revision 增量替代。
   - 修复方向：测试中注入并等待一个确定的 simulation Worker 响应，随后断言主/备份的精确状态、pending debt 和恢复后的哈希；保留双击返回、无新增状态时只保存一次、发生新增状态时二次清理保存三种独立场景。

3. `tests/e2e/v144-runtime-recovery-store.spec.ts:1085`，`one simulated hour coalesces passive WAL below 8 MiB with zero transfer-checkpoint writes`
   - 三次单 worker 重跑为 1 通过、2 失败。
   - 450 次 stage/finalize 后，全部结构和容量断言仍正确：1 个 passive segment、450 操作、零 transfer checkpoint、约 1.84 MB 写入；但 0.87--0.91 秒的页面操作中有 1 个 `longtask`，而用例要求严格为 0。
   - 这既是测试稳定性问题，也是主线程持久化预算的真实性能信号。测试应记录 long-task 的起始时间/时长，排除 observer 注册前的 buffered entry；实现侧应避免在 UI 线程上串行准备、摘要和提交过多 WAL 记录。
   - 修复方向：把 durable intent 的 canonical JSON、UTF-8、SHA-256 和合并策略统一放进已有 persistence Worker；按有界批次/时间片提交，保持 sequence、fencing、readback 和掉电恢复语义不变。修复后应以 3 次冷启动 production-preview 重跑，并同时校验最终 recovery proof。

发布影响：在这三项全部稳定通过前，1.0.45 不应进入候选制品、签名或部署阶段。

### P0-02：超大存档主动运行仍缺少当前版本的验收证据

`docs/PROJECT_STATUS.md` 记录的 36.7 MB 玩家附件在 1.0.43 中仍出现 Continue -> Pause 20,887 ms 与 20,291 ms Long Task。1.0.44 引入 Worker、持久化和画布优化，但本次没有取得该附件，无法验证现有代码是否已达标。

建议的 1.0.45 验收合同：使用经授权的只读副本，在 import、首次进入、运行 60 秒、Continue -> Pause、手动保存、返回菜单、重载六段流程中记录主线程 Long Task、输入确认延迟、Worker 往返、WAL 字节、内存和状态哈希。目标应以“暂停/交互可在短时间内确认，保存保持 Worker 权威，重载无损”定义，而不是仅以迁移或导入加速替代运行态结果。

### P1-01：本机依赖树与 Android 生成物已经漂移

当前工作区的 `node_modules` 缺少已锁定的 `@axe-core/playwright`，并残留不在 `package.json` 的 Capacitor filesystem/share 包。`npm ci --dry-run` 明确显示会新增前者并删除后两者。

受影响的忽略生成物 `android/app/src/main/assets/capacitor.plugins.json` 停留在旧时间，仍注册 filesystem/share；因此当前工作区的原生安全测试为 23/24。干净 worktree 不带该陈旧生成物，且锁文件安装后原生套件为 24/24。源配置、Gradle 列表和 `package.json` 本身已排除这两个通用插件。

风险与修复：发布脚本通常会执行 `cap sync`，但任何绕过同步的直接 Gradle 构建可能带入旧插件。CI 已使用 `npm ci`，但没有在 `npm run android:sync` 后复跑原生安全测试。应新增独立 Android 生成物门禁：干净安装 -> `npm run android:sync` -> `npm run test:native`，并在打包前确认生成插件清单只含 allowlist。开发机 preflight 也应提供同样的无副作用检查说明。

### P1-02：开发/打包依赖存在 1 个中危和 4 个高危公告

干净根依赖树的全量 `npm audit` 报告 5 个传递性公告：`brace-expansion`、`fast-uri`、`nanoid`、`undici`、`postcss`。它们分别来自 Electron Builder 工具链、Vite/PostCSS 和 Electron/node-gyp 的开发或可选依赖；`npm audit --omit=dev` 与 server production audit 均为 0，因此当前证据不指向已发布 Web/API 的运行时漏洞。

修复方向：建立单独的工具链升级 PR，先更新 Vite/插件、Electron Builder 及其锁文件，再完整重跑 typecheck、native、构建、E2E 和桌面打包。不要在发布候选上直接执行无审查的 `npm audit fix`。

### P2-01：发布与路线图文档存在明显版本漂移

- `CHANGELOG.md` 的最新正式条目仍是 1.0.39，缺少 1.0.40--1.0.44 的玩家可读摘要。
- `docs/ROADMAP.md` 的“当前推荐下一迭代”仍引用 1.0.15，且前段存在已经完成或被后续方案替换的待办。
- `docs/TESTING_RELEASE.md` 的顶部含 1.0.44 发布信息，但覆盖矩阵仍以 1.0.43/1.0.42 历史数量为主。
- `docs/ARCHITECTURE.md` 同时包含“1.0.44 开发态（未发布）”和现网事实，容易误导后续维护者。

修复方向：将 `PROJECT_STATUS.md` 保持为唯一当前事实；在 1.0.45 开发开始前整理 CHANGELOG、ROADMAP、ARCHITECTURE 和 TESTING_RELEASE 的当前段，把历史证据保留在 release/feedback 文档中，不再让旧计划占据“当前”位置。

## 性能与架构观察

### 已验证的正面结果

- 默认连接 LOD 的 106 节点 production-preview 路径通过：进入 10.9 ms、帧 P95 7.1 ms，逻辑 full 节点 18/106。
- 500 站物流基准中，indexed/legacy 的状态哈希全部一致；indexed 3 秒模拟中位从约 6,511 ms 降至约 783 ms，改善约 88%。这证明索引优化正确且有效。
- 传送带 64、256、1,024、4,096 lanes 保持单一 belt object；2,000 步约 914--1,020 ms，不呈现 lane 数量线性恶化。
- 首屏 budget 通过：总 gzip 192,589 B、JS 100,519 B、CSS 92,070 B；菜单闭包 274,007 B，工厂运行时没有被拉入首屏。

### 仍需处理的瓶颈

- `FactoryRuntime` 压缩前约 720 KB、全局 CSS 约 604 KB，构建仍报告大 chunk 警告。它们不阻断首屏预算，但会提高进入工厂和样式维护成本。
- production-preview 的 500 节点场景中，auto 模式三轮帧 P95 为 7.1--13.9 ms；full 模式操作为 2.62--2.87 秒、帧 P95 为 500--605 ms；connect expand-all 为 1.23--1.27 秒、帧 P95 为 125--174 ms。默认 auto 正确，full/expand-all 只能是明确警告、可逆且不自动开启的诊断路径。
- `src/App.tsx` 约 10,955 行、`src/game/engine.ts` 约 12,888 行、`src/styles.css` 约 21,032 行、`server/index.mjs` 约 5,521 行。测试数量很高，但这些文件继续膨胀会增加 Worker、保存、画布和交互之间的回归概率。
- E2E 默认将未配置 API 请求代理到本地关闭端口，产生大量预期 `ECONNREFUSED` 日志。用例多能自行 mock，但日志噪声掩盖真正故障，也增加诊断成本。

## 1.0.45 建议开发顺序

### P0：稳定性与发布门禁

1. 修正三个 E2E 用例及其真实行为合同，连续 3 次单 worker、1 次 CI 并行分片均为 0 失败。
2. 将 WAL intent 准备和有界合并移入 persistence Worker；保留 deterministic sequence、fencing、CAS、掉电恢复和 exact readback。
3. 用授权的 36.7 MB 只读附件建立固定性能夹具和可复现报告，先修主动模拟/暂停/保存的交互阻塞，再考虑新玩法。
4. 增加 `npm ci` + `npm run android:sync` + `npm run test:native` 的生成物门禁；禁止用脏 `node_modules` 或旧 Android assets 打包。

### P1：性能与可维护性

1. 保持 auto LOD 为默认；对 full/expand-all 增加节点上限、运行时帧预算退避和明确恢复按钮，绝不修改 GameState 或模拟结果。
2. 将 `App.tsx` 按 `simulation runtime`、`durable persistence`、`return/lifecycle`、`canvas presentation` 切出有测试的 hooks；将 `engine.ts` 按电力、物流、科研、戴森和实体命令抽为纯模块。每次拆分必须做状态哈希和 Worker/main 等价回归。
3. 拆分 CSS 为 shell、factory canvas、workspace、responsive 层，避免一次样式改动覆盖全端。
4. 为 E2E 提供明确的 API mock 或临时 API，而不是默认拒绝连接；保留真实 API 套件在 server/integration 层。

### P2：产品与运营质量

1. 优先完善生产瓶颈定位、告警到设备/线路的直达导航、保存/恢复状态可解释性和大工厂性能诊断；这些比继续叠加复杂玩法更能降低真实玩家流失。
2. 修复 COS 异地备份写路径和上海恢复演练状态。该项来自 1.0.44 发布记录，本次未进行线上验证，需作为单独 release/operations 任务处理。
3. 取得 Windows 代码签名，继续维持 Android 签名连续性；补充 Android 真机、低配 Windows、Firefox/WebKit 和 Linux 实例级发布演练。
4. 增加 coverage 报告和风险域阈值。当前项目有大量测试但没有发现 coverage 脚本或门禁，不能量化存档迁移、Worker 协议和返回菜单分支的覆盖缺口。
