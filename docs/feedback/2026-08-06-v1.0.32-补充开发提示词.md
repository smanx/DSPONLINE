## 需求二：统一修复三条递归制造路径

### 玩家可见问题

玩家拥有原油以及其他基础材料，但递归制造只识别现成精炼油：

- 施工托盘绿色锤子无法继续制造依赖油路的建筑。
- 物品递归手搓无法使用原油生成所需精炼油。
- 建筑制造中心长时间显示缺少精炼油或持续加工，不能从原油继续完整材料链。

这不是三个独立 Bug，而是三条路径共用同一错误配方权限造成的系统性问题。

### 已确认根因

1. `src/game/engine.ts:8576-8577` 的 `recursiveManufacturingRecipes()` 当前只保留 `isHandcraftableRecipe(recipe.id)` 为真的配方。
2. `src/game/engine.ts:11346-11362` 的 `NON_HANDCRAFTABLE_RECIPE_IDS` 同时包含：
   - `plasma_refining`
   - `xray_cracking`
   - `reforming_refine`
3. 该名单来自 1.0.28 的炼油循环保护。它正确阻止了玩家直接手搓炼油循环，却错误地同时剥夺了“作为递归上游”的资格。
4. `plasma_refining` 是无自循环的基础油路：消耗 `2 原油`，产出 `2 精炼油 + 1 氢`。它必须能被递归规划使用。
5. 三条路径都调用同一个候选集合：

| 路径 | 规划入口 | 执行/消费入口 | 当前共同问题 |
| --- | --- | --- | --- |
| 施工托盘绿色锤子 | `getConstructionQuickCraftPlan()` / `buildConstructionQuickCraftPlan()` | `craftConstructionWithUpstream()` | 无法把原油转为精炼油；绿色/灰色状态和最大批数受影响 |
| 物品递归手搓 | `getRecursiveHandcraftPlan()` / `buildRecursiveHandcraftPlan()` | `handcraftRecipeWithUpstream()` | 最终配方允许递归，但上游候选仍排除等离子精炼 |
| 建筑制造中心 | `buildConstructionAutomationPlan()` | 制造中心任务、WIP 和批量结算 | 同一候选集合被规划、缓存和重复批处理分析使用 |

### 目录量化审计

审计条件：解锁全部科技，提供所有真正的基础资源，提供原油但不提供精炼油，然后遍历当前可递归目标并独立重放规划步骤。

| 审计对象 | 当前结果 | 仅允许 `plasma_refining` 作为递归上游后的结果 |
| --- | --- | --- |
| 当前可递归手搓物品配方 | `53/70` 可完成，`17/70` 错误卡在精炼油 | `70/70` 可完成 |
| 当前施工建筑目标 | `25/41` 可完成，`16/41` 错误卡在精炼油 | `41/41` 可完成 |
| 独立重放库存与规划库存 | 受阻目标无法验证 | 全部一致，数量守恒 |

受影响的 17 个物品目标：

`sulfuric_acid`、`titanium_alloy`、`logistics_vessel`、`graphene`、`particle_broadband`、`deuteron_fuel_rod`、`casimir_crystal`、`antimatter_fuel_rod`、`frame_material`、`dyson_sphere_component`、`small_carrier_rocket`、`plastic`、`organic_crystal`、`titanium_crystal`、`structure_matrix`、`information_matrix`、`universe_matrix`。

受影响的 16 个建筑目标：

`geothermal_power_station`、`mini_fusion_power_plant`、`artificial_star`、`energy_exchanger`、`plane_smelter`、`assembling_machine_mk3`、`quantum_chemical_plant`、`miniature_particle_collider`、`vertical_launching_silo`、`interstellar_logistics_station`、`orbital_collector`、`construction_center`、`galactic_material_exporter`、`micro_black_hole_connector`、`time_warp_device`、`space_station_construction_launcher`。

### 同时确认的同类 P1 守恒 Bug

`src/game/recursiveCrafting.ts:78-83` 的 `producingRecipes()` 只检查目标物品总输出是否大于 0，没有扣除同一配方对目标物品的输入。

`deuterium_fractionation` 的真实配方是：

```text
输入：10 氢
输出：9 氢 + 1 氘
```

当前规划器可能把它当成“制造 9 氢”的配方。已复现：

```text
初始库存：10 氢
目标需求：11 氢
错误规划：possible = true，执行 1 批氢分馏
真实重放：最终只有 9 氢，需求并未满足
```

小范围库存/需求穷举产生 55 个同类虚假成功结果，全部来自把氢分馏当作氢生产路线。这个漏洞会同时污染绿色锤子、递归手搓、建筑制造中心、最大批数和缺料提示。

### 必须采用的统一规则

#### 1. 分离两种权限

不要再用一个 `isHandcraftableRecipe()` 同时表达两种语义。至少在领域层明确区分：

```text
directHandcraftable：玩家是否能把该配方作为最终手搓配方直接选择
recursiveUpstreamAllowed：该配方是否允许作为三条递归制造路径的上游步骤
```

本版策略必须为：

| 配方 | 直接手搓 | 递归上游 | 原因 |
| --- | --- | --- | --- |
| `plasma_refining` | 保持禁止 | 允许 | 原油到精炼油是无循环的必要基础链，并保留副产氢 |
| `xray_cracking` | 禁止 | 禁止 | 涉及氢和精炼油种子、自循环及批次数复杂性 |
| `reforming_refine` | 禁止 | 禁止 | 必须先有精炼油种子，不能被当成从零制造精炼油 |
| `deuterium_fractionation` | 按现有最终配方规则 | 可用于制造氘 | 绝不能作为制造氢的候选 |
| 发射、科研、射线接收、蓄电器充放电等状态转换 | 保持禁止 | 保持禁止 | 不是递归材料制造 |

玩家所说“手搓递归能用原油”是指制造塑料、硫酸、建筑等最终目标时，规划器可在内部先执行等离子精炼；本需求不要求把“等离子精炼”显示成可直接点击的手搓配方。

#### 2. 递归候选按净产出判断

对每一个目标物品计算：

```text
目标物品净产出 = 该配方中目标物品的输出总量 - 该配方中目标物品的输入总量
```

只有净产出严格大于 0，配方才可作为该物品的递归生产候选。为满足缺口需要执行的批次数必须基于净产出计算，不能基于总输出计算。

该规则必须作用于核心配方和内容包配方，不能只给 `deuterium_fractionation` 写特判。输入和输出数组里若同一物品出现多次，应先分别汇总再求净值。

#### 3. 三条路径只使用一份领域策略

- 绿色锤子、递归手搓、建筑制造中心必须调用同一个“递归上游允许”函数和同一个净产出函数。
- `getMaxConstructionQuickCraftBatches()`、`getMaxRecursiveHandcraftBatches()` 必须复用修复后的规划器，不能维护另一套估算公式。
- 灰色锤子缺料导航和制造中心阻塞原因必须来自同一个规划结果。
- 桌面和新版手机 UI 必须只展示领域函数结果，不能分别计算可制造状态。
- 建筑制造中心的 `constructionAutomationPlanCache`、重复批处理分析和 relevantItems 扫描必须使用新策略；缓存键或失效条件不能让旧“缺精炼油”结果继续驻留。

#### 4. 保持原子性和库存守恒

- 规划失败不得扣除任何原油、中间材料、建筑库存或便携载具。
- 规划成功后，执行结果必须与规划库存逐物品一致，不能出现负库存或凭空物资。
- 等离子精炼产生的氢必须进入正常副产物结算，不能被静默丢失。
- 绿色锤子和递归手搓继续允许递归副产物临时超过物资托盘软上限，但仍不得超过 `Number.MAX_SAFE_INTEGER` 安全边界。
- 建筑制造中心继续沿用现有 WIP 保留、额外副产物返回/销毁计数和安全上限机制，不得因本修复重新引入“卡氢”。
- 同一状态、同一目标和同一批数的规划决策顺序必须确定，Worker 与主线程回退结果一致。

#### 5. 缺料提示必须指向真正原料

有足够科技但原油不足时：

- 绿色锤子应显示灰色，并提示“缺少原油”及准确数量。
- 单击灰色锤子的导航应定位原油来源/相关图鉴，不得跳到精炼油、钢材或无关配方。
- 递归手搓应显示缺少原油，不应显示“无配方”或“缺少精炼油”。
- 建筑制造中心状态应显示原油短缺，补入原油后无需重新放置建筑、重设目标或开关制造中心即可恢复。

#### 6. 内容包安全边界

当前内容包配方会进入同一递归候选，但内容包格式没有独立的手搓/递归策略字段。1.0.32 的最低要求是：

- 所有内容包配方同样经过“目标物品净产出 > 0”过滤。
- 增加目录或单测审计，覆盖输入输出重叠、净产出不为正和递归循环。
- 不要为修复核心原油问题而静默改变现有内容包格式或存档格式。

若开发过程中确认必须向内容包公开策略字段，应作为单独兼容设计提交，不要混入本次 P1 热修。

### 重点回归用例

#### 领域规划器

1. `10 氢 -> 需求 11 氢`：不得使用氢分馏，结果必须失败并报告氢不足。
2. `10 氢 -> 需求 1 氘`：允许执行一批氢分馏，结果为 `9 氢 + 1 氘`。
3. `2 原油 -> 需求 2 精炼油`：允许一批等离子精炼，结果同时包含 `1 氢`。
4. 精炼油为 0 时，禁止从 `reforming_refine` 凭空启动；氢/精炼油种子不足时禁止使用 `xray_cracking`。
5. synthetic 内容包配方对目标物品净产出为 0 或负数时，不得成为该目标的生产候选。
6. 同一配方重复输入/输出同一物品时，净产出按汇总值计算。

#### 施工托盘绿色锤子

1. 用原油和其他基础材料递归制造至少一个受影响的普通建筑和一个终局巨构，规划与执行均成功。
2. 批量制造 1、2、最大可制造数量和“最大值+1”，验证二分上限准确且失败原子。
3. 原油不足时灰锤提示和单击跳转都指向原油；补入原油后同一张卡立即变为可制造。
4. 桌面施工托盘和新版手机建造抽屉显示相同锤子状态、缺料名称和消耗预览。

#### 物品递归手搓

1. 以 `plastic` 为最小回归：托盘只有足量原油、高能石墨及科技、没有精炼油时，可递归制造塑料，并保留等离子精炼副产氢。
2. 再覆盖一个多层油路目标，例如有机晶体或宇宙矩阵，验证多层计划和实际库存一致。
3. 覆盖便携载具 `logistics_vessel`，确认最终仍进入 `portableFleet`，不错误进入托盘。
4. 覆盖副产物已超过托盘软上限、接近 `Number.MAX_SAFE_INTEGER`、科技锁定和基础资源不足。

#### 建筑制造中心

1. 目标选择至少一个受影响建筑，只提供基础资源和原油，不提供精炼油；制造中心应自行完成等离子精炼和后续链。
2. 先在无原油状态生成阻塞/缓存，再补入原油，下一次有效规划应自动恢复，不能继续显示旧阻塞。
3. 精确逐步路径与重复批处理路径在 1、10、100 个目标上库存、WIP、副产物、销毁计数和总产出一致。
4. 验证暂停、无电、低电、目标切换、制造中心堆叠、离线模拟和 Worker 路径。
5. 对三条路径执行目录审计：当前全部可递归物品与施工建筑在“全科技+全部真实基础资源”条件下均可规划，且逐步重放与计划库存一致。

## 需求三：离线/纯挂机后科技无法完成（P0）

### 玩家原话与现象

> 在保持科研的情况下退出挂机重进，出现无法完成科技。取消再继续，取消无用。

截图中的科研站为 5 台堆叠，正在研究“宇宙矩阵”科技所需的五种矩阵均已进入缓存：

```text
电磁矩阵 100/100
能量矩阵 100/100
结构矩阵 100/100
信息矩阵 100/100
引力矩阵 1403/100
```

这些数量与 `src/game/content.ts:1268-1276` 的宇宙矩阵科技成本完全对应，但科技没有进入完成状态。玩家取消后重新选择仍无法继续完成，构成科技树和后续白糖阶段的进度阻断。

### 附件诊断中确认的事实

| 项目 | 诊断结果 |
| --- | --- |
| 应用版本 | `1.0.31+19040a9d1e45` |
| GameState | v46 |
| 工厂规模 | 265 个实体、193 条传送带、53 项已完成科技 |
| 诊断采集时状态 | `paused: true`，标准难度，1x 基础速度 |
| 最近错误 | 50 条，其中 48 条是无关的 `ResizeObserver` 通知，2 条是 593 ms/255 ms 主线程长任务 |
| 科研异常日志 | 没有未捕获的科研异常或 Worker 异常堆栈 |

`paused: true` 是重要旁证，但不能单独证明玩家在 Bug 首次出现时已经暂停。1.0.31 的纯挂机 Worker 超时/失败保护会主动停止时间扭曲并把模拟设为暂停，玩家如果没有看到提示，所有生产和科研都会停止。开发时必须同时验证“科研状态卡死”和“纯挂机退出后处于安全暂停”两条路径。

当前诊断格式没有包含 `selectedTechId`、`pausedTechId`、`queuedTechIds`、`progressByTech`、时间扭曲启用状态或暂停原因，因此仅凭该诊断不能百分之百还原玩家当时的科研对象和进度字段。玩家没有同时提供完整存档，不能宣称已从附件精确重放原存档；但以下状态机死锁和可能的生成路径已由代码确认。

### 已确认的状态机死锁

当前普通科研完成事件只在科研站实际产生可消费周期时触发：

1. `src/game/engine.ts:796-802` 的 `remainingResearchCosts()` 会把已经达到成本的项目过滤掉。
2. `src/game/engine.ts:1247-1253` 的 `availableInputCycles()` 对科研模式累加剩余成本；当全部进度已满时返回 0。
3. `src/game/engine.ts:4234-4237` 在最大周期小于 1 时直接跳过设备。
4. `src/game/engine.ts:4246-4275` 只有进入科研设备消耗分支后才调用 `completeTechnology()` 和 `activateNextQueuedTechnology()`。

因此只要存档出现以下组合，就会永久卡死：

```text
selectedTechId = 某项未完成科技
progressByTech[该科技] 的每一种矩阵投入 >= 对应科技成本
completedTechIds 不包含该科技
```

此时剩余成本为 0，科研站没有可运行周期，完成函数永远不会再执行。`cancelCurrentResearch()` 按现有正确设计保留已投入矩阵；重新选择同一科技后仍是“投入已满但没有完成事件”的相同状态，所以玩家所说的“取消无用”与代码行为完全一致。

### 高可信触发链：近似结算跨越离散科研边界

1. 1.0.30/1.0.31 的快速离线和时间扭曲近似结算通过仿射增量外推数值字段。
2. `src/game/offlineApproximation.ts:828-834` 明确把 `research` 和 `progressByTech` 列为可外推敏感字段。
3. `captureAffineSnapshot()` 会记录数组结构，但仿射合同只对 number/decimal 生成增量。因此 `progressByTech` 中的矩阵数字可以增长，`completedTechIds` 数组、`selectedTechId`、科技奖励和队列切换不会作为同一个原子领域事件增长。
4. `normalizeFastSettlementState()` 会修正库存、缓存和数值边界，但当前没有“科研投入已满则完成科技”的一致性校验。
5. 快速离线最终只对普通库存漂移和白糖/戴森关键指标做尾验，没有把普通科技完成集合、当前科技和研究队列作为硬门禁。
6. 旧的 `runOfflineApproximation()` 会因存在 `matrix_research` 而拒绝近似，但默认快速离线与时间扭曲路径没有复用这个科研阻断条件。

这条路径能够生成“数值进度到达或越过成本，但离散完成事件未执行”的非法状态，与玩家现象高度吻合。相同风险也存在于无限科研：如果只外推 `progress` 而没有同步提升 `level`，剩余白糖成本可能变成 0 或负数，科研站同样失去下一次触发机会。

### P0 修复要求

#### 1. 建立唯一的科研完成边界结算函数

在领域层新增或提取一个确定性、幂等的科研边界函数，语义类似：

```text
settleCompletedResearchBoundaries(state)
```

该函数必须：

- 检查当前普通科技的每项投入是否都达到成本，而不是等待科研站再消耗一件矩阵。
- 达标时把每种投入规范到科技成本，不能把仿射外推的超额投入携带到下一项科技。
- 通过现有唯一的 `completeTechnology()` 路径完成科技，确保建筑奖励、宇宙矩阵特殊奖励、星球开放等副作用完整且只执行一次。
- 完成后调用现有队列切换规则，并把所有科研站的周期进度重置到合法范围。
- 如果下一项队列科技以前保留的投入也已达标，可以继续结算，但循环次数必须以科技目录数量为硬上限，防止坏档无限循环。
- 已经位于 `completedTechIds` 的科技不得再次发奖励；重复调用必须得到完全相同的状态。
- 对无限科研使用其现有 BigInt 成本与升级函数处理整级边界，不得用 Number 强转大数，也不得直接修改等级绕过封顶和历史等级规则。

#### 2. 在所有可能提交状态的边界执行一致性检查

至少覆盖：

- 普通在线 `advanceSimulation()` 的科研阶段前后。
- 快速离线精确校准、宏观应用和最终精确尾验提交前。
- 时间扭曲/纯挂机每个可持久化宏观检查点提交前。
- Worker 返回主线程并成为权威状态前。
- v46 存档加载/迁移规范化后。
- 选择科技、恢复暂停科技以及取消后自动开始队列项的命令边界。

不要在 React 组件中直接把科技标记为完成。UI 只能调用领域命令并展示结果。

#### 3. 1.0.32 正确性门禁：研究期间不得盲目仿射外推

最安全的 P0 热修策略是：只要存在当前普通科研或当前无限科研，就禁止快速离线和时间扭曲路径直接仿射外推科研字段。可选实现只有两种：

1. 遇到活动科研时安全回退精确结算。
2. 实现真正的事件边界切段：最多外推到下一次科技完成/无限科研升级边界，调用领域完成函数、切换队列并重新校准后再继续。

如果 1.0.32 没有足够时间证明事件切段完全正确，应先选择精确回退。性能下降可以接受，科技树坏档不可接受。

禁止以下“看似修好”的方案：

- 只从 `FAST_SENSITIVE_KEYS` 删除 `research`，让玩家离线期间完全没有科研收益。
- 只把 `progressByTech` 截断到成本，但不执行完成、奖励和队列切换。
- 只在科技页面打开时修复，导致后台模拟、云存档和排行榜仍保存非法状态。
- 清空玩家科研进度、科研站输入或研究队列。
- 取消时删除投入来绕过死锁。

#### 4. 自动修复已经卡死的 v46 存档

- 旧存档加载后，如果当前普通科技投入已满但未完成，应立即按领域规则完成一次并继续合法队列。
- 修复不得要求玩家取消科技、重建科研站、清空输入、关闭纯挂机或新建存档。
- 科研站缓存中的未消费矩阵必须完整保留；只有已经记录在 `progressByTech` 的投入参与完成判定。
- 如果诊断中的宇宙矩阵科技满足成本，恢复后应解锁宇宙矩阵配方并执行现有宇宙矩阵科技奖励，不能重复赠送其他科技建筑。
- 无需新增存档字段时保持 GameState v46、envelope v2 和 cloud schema v7；如开发者认为必须做版本化语义迁移，应先单独说明理由和兼容测试，不能静默清档。

#### 5. 纯挂机退出与暂停状态必须明确

- 正常停止纯挂机且 Worker 在安全窗口返回时，应恢复正常模拟，不应无理由留下 `paused: true`。
- Worker 超时、异常或恢复日志失败时可以为了数据安全保持暂停，但必须显示持续可见、不可被普通运行记录覆盖的提示，并提供明确的“继续普通模拟”按钮。
- 点击继续后先执行科研边界自愈，再恢复模拟；不能让玩家只看到科研不动却不知道全局仍暂停。
- 记录进入纯挂机前的暂停状态，停止后遵守产品定义：若玩家开始前已暂停，恢复暂停；若开始前运行中，正常安全停止后恢复运行。

#### 6. 补充匿名诊断字段

后续诊断至少应增加以下非敏感摘要，便于确认问题而不导出完整存档：

```text
research.selectedTechId
research.pausedTechId
research.queuedTechCount
research.selectedProgress / selectedCosts
research.completedTechCount
timeWarp.enabled / pendingSimulationSeconds / lastStopReason
paused / pausedReason
matrixResearchLabCount / poweredResearchLabCount
```

不要在诊断中加入账号令牌、云存档正文、玩家自定义文本或完整库存。

### 最小确定性复现

开发测试必须直接构造以下状态，不依赖玩家原存档：

1. 新建状态并解锁宇宙矩阵前置科技。
2. 设置 `selectedTechId = "universe_matrix"`，但不把它加入 `completedTechIds`。
3. 把 `progressByTech.universe_matrix` 的五色投入全部设为 100。
4. 放置有电的矩阵研究站并选择 `matrix_research`，输入缓存放入五色矩阵。
5. 推进普通模拟。修复前 `availableInputCycles()` 为 0，科技永远不完成；修复后应在不额外消耗矩阵的情况下完成一次。
6. 对同一状态执行取消、重新选择、保存、重载，再推进，仍只能完成一次且奖励不重复。

## 需求四：版本公告历史分页与详情完整性（P1）

### 玩家可见问题

公告窗口顶部提供“跳转页码”和“查看历史版本”，但玩家反馈：

- 在公告详情页直接修改“跳转页码”没有实际跳转，页码数字可能变化，历史列表和公告内容却不变。
- 打开历史后，历史版本只能看到第一条信息，无法查看该版本完整的更新内容。

附件截图显示当前界面停留在 `1.0.28` 的详情，工具栏为“第 2 / 11 页”；该截图用于确认问题发生在公告历史工作区，不是普通版本公告内容缺失的文字反馈。

### 当前代码级证据

相关组件和测试：

- `src/components/ReleaseNotesDialog.tsx`
- `src/components/ReleaseNotesDialog.test.ts`
- `tests/e2e/ui-visual-feedback.spec.ts` 的 `release history supports direct paging...` 用例

已确认的状态链：

1. `historyPage`、`selectedReleaseId` 和 `historyOpen` 是三个独立状态。
2. 页码 `<select>` 的 `onChange` 只调用 `setHistoryPage(...)`。
3. `historyOpen === false` 时不会渲染 `.release-notes-history-list`；此时仅修改页码不会改变 `selectedReleaseId`，所以详情态中的直接跳页是无可见效果的。
4. `showRelease(id)` 会关闭历史列表并查找选中的记录；详情渲染本身会遍历 `selectedRelease.items`，没有只取数组第一个元素的代码。
5. 但 `RELEASE_NOTES_HISTORY` 中多个版本的 `items` 数据确实只有一条摘要项（尤其是 1.0.25～1.0.30），因此用户看到的“只能查看第一条”还包含历史数据源不完整的问题。不能用组件显示正常来掩盖静态历史只录入一条的事实。
6. 现有 Playwright 只验证在已经打开历史列表后选择最后一页，再点击 `1.0.0`；没有验证详情态直接改页码、每页首尾版本、版本详情多条更新全部显示，也没有检查历史条目是否覆盖发布文档中的完整内容。

### 推荐修复方案

1. 把分页动作集中成一个领域无关的 UI 状态函数，例如 `openHistoryPage(page)`：先把页码限制在 `0..pageCount-1`，再打开历史列表；如果当前选中版本不属于新页，可让该页第一条成为列表高亮/预览，不能继续显示上一页内容而让玩家误以为跳转失败。
2. `showRelease(id)` 必须按 `RELEASE_NOTES_HISTORY` 的索引同步计算所属页码，再更新 `selectedReleaseId`，这样从任意页打开版本、返回历史和再次打开时页码一致。无效 ID 不能静默显示当前版本而不提示，应回到当前版本并清理无效选择。
3. 详情态的“跳转页码”要么明确禁用并说明“请先打开历史”，要么（推荐）选择页码后自动进入历史列表并展示目标页；不能保留一个可操作但没有可见效果的控件。
4. 历史列表与详情必须使用同一份 `RELEASE_NOTES_HISTORY` 静态数据。每个版本至少包含该版本公告中所有条目的 `id/title/description`、日期、版本号、摘要；不得因为页面空间或旧实现只保留第一项。数据必须离线随包提供，不通过网络补拉。
5. 详情继续遍历所选记录的完整 `items`，并为历史条目提供稳定图标或通用 `Info` 回退；不得把 `CURRENT_RELEASE_NOTES.items` 当成未知历史版本的静默回退内容。
6. 保留现有返回行为：从详情返回历史时恢复刚才的页码和历史列表滚动位置；从历史返回当前版本时显示当前公告，不改变已读公告键 `RELEASE_NOTES_SEEN_KEY`。该修复只能改变设备级 UI 状态，不得进入 GameState、云存档、排行榜或版本签名摘要。
