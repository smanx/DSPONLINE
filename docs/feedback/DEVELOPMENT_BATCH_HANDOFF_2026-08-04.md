## 4. 需求 1：建筑与物流塔直接输入最终堆叠数量

### Task ID / title

`DSP-FB-20260804-01` / 建筑、设备和物流塔统一使用最终堆叠目标输入框

### Priority

P2，操作效率优化。

### Source and attachments

- 玩家文字反馈，无截图。
- 用户期望设备和物流塔像传送带数量一样，直接填写最终数量，而不是反复点击增加或减少。

### Reproduction or observed evidence

当前普通建筑检查器同时存在“增加建筑”步进器和仅能减少的“保留数量”输入框。“保留数量”的最大值被限制为当前堆叠，因此不能直接从 `100` 输入 `10,000` 完成扩建。参见 [GamePanels.tsx](../../src/components/GamePanels.tsx#L736)。

当前独立物流管理页已经存在双向的“堆叠数量”目标输入，底层也已有远程目标命令，可以同时处理增加与减少。参见 [LogisticsManagementPanel.tsx](../../src/components/LogisticsManagementPanel.tsx#L168) 和 [engine.ts](../../src/game/engine.ts#L10763)。因此本项重点是统一普通检查器和物流管理页，而不是再创建另一套数量模型。

### Required behavior

1. 将普通检查器中的“增加数量”和“保留数量”统一为明确的“堆叠目标”输入框。
2. 输入框显示当前最终数量，接受 `1` 至 `100,000,000` 的正整数。
3. 按 Enter 或输入框失焦时提交；Escape 恢复当前真实数量。
4. 目标大于当前数量时，差值就是需要消耗的建筑数量。例如当前 `100`，输入 `1,000`，应一次扣除 `900` 个对应施工件。
5. 目标小于当前数量时，差值完整返还施工托盘。例如当前 `1,000`，输入 `100`，应返还 `900` 个对应施工件。
6. 库存不足、建筑锁定、输入非法或超过硬上限时必须显示真实原因，不能部分增加，也不能把输入框伪装成成功值。
7. 行星物流站、星际物流站、生产设备、储存设备和普通电力设施使用同一口径。单体唯一巨构继续锁定为 `1`。
8. 采矿设备若接入该输入框，只调整矿机数量，绝不能增加矿脉实体或资源储量。
9. 保留现有 `+1/+10/+100` 和批量功能作为快捷入口，但它们与最终目标输入必须调用同一领域命令。

### User-visible acceptance criteria

- 从 `1` 输入 `10,000` 后，只执行一次确认和一次扣料，最终显示 `x10,000`。
- 从 `10,000` 输入 `1` 后，返还 `9,999` 个施工件，实体 ID、位置和线路不变化。
- 库存只够增加 `500` 个时，输入增加 `1,000` 必须整体失败，不能只增加 `500`。
- 输入空白、小数、负数、指数表达式、超安全整数或超过一亿时，显示错误并保持原数量。
- 历史存档中已经超过一亿的旧堆叠必须原样读取；允许降低，禁止继续增加到更高的超限值。

### Compatibility and data-preservation constraints

- 减少物流塔堆叠后，如果运输机、运输船、翘曲器或槽位库存超过新额定容量，已有数量继续保留为安全超额，只阻止继续补入，不能删除。
- 生产输入、输出、燃料、喷涂点数、配方进度和建筑制造任务不得因数量调整而清零。
- 不应为本项升级 GameState；优先复用现有建筑增加、部分回收和远程目标命令。

### Smallest owning modules

- `src/components/GamePanels.tsx`
- `src/components/LogisticsManagementPanel.tsx`
- `src/App.tsx`
- `src/game/engine.ts`

### Required tests

- 单元测试：增加、减少、库存不足原子失败、锁定建筑、历史超限降低、物流塔安全超额。
- E2E：桌面和触摸端输入、Enter、失焦、Escape，以及切换实体后草稿不串值。

### Known risks / rollback

最大风险是减少堆叠时误删缓存或载具。开发必须复用既有物资守恒命令；若守恒测试失败，应回退 UI 入口而不是清理玩家状态。

## 5. 需求 2：矩阵研究站科研模式支持喷涂

### Task ID / title

`DSP-FB-20260804-02` / 科技矩阵生产与科研模式完整接入喷涂系统

### Priority

P2，功能缺失和规则补全。

### Source and attachments

- 玩家文字反馈，无截图。
- 用户要求科技矩阵相关建筑也可以使用喷涂。

### Confirmed current behavior

电磁、能量、结构、信息、引力和宇宙矩阵六种生产配方都拥有正常输入和输出，现有通用规则理论上允许安装喷涂模块并获得增产或加速效果。参见 [content.ts](../../src/game/content.ts#L636)。

矩阵研究站切换到 `matrix_research` 后使用空输入、空输出的特殊配方。喷涂资格和安装检查要求普通配方同时存在输入和输出，因此科研模式会被判定为不兼容。参见 [content.ts](../../src/game/content.ts#L642) 和 [engine.ts](../../src/game/engine.ts#L1156)。

科研实际消耗由当前科技成本动态决定，并在模拟分支中单独结算。这意味着不能简单给 `matrix_research.inputs` 写死一种矩阵，否则会破坏多矩阵科技和无限科研。

### Required behavior

1. 六种矩阵生产配方保持当前喷涂行为，不得回归。
2. `matrix_research` 被明确纳入喷涂安装资格，允许安装、拆卸、切换等级和连接增产剂输入线路。
3. 科研模式推荐只开放“正常”和“加速”两种模式。
4. 科研加速按实际获得喷涂的科研周期提高速度，并应用对应的喷涂耗电倍率。
5. “额外产出”在科研模式中禁用并说明“科研模式仅支持加速”，避免产生无定义的免费科技进度。
6. 每次科研喷涂消耗必须按该周期实际消耗的矩阵数量结算。当前科技需要多种矩阵时，不能按空配方成本错误地固定消耗一个点数。
7. 增产剂耗尽后研究站应恢复普通科研速度并继续运行，不能因缺少增产剂永久停机。
8. 从矩阵生产切换到科研、再切回生产时，已安装模块、剩余增产剂和点数完整保留。

### User-visible acceptance criteria

- 科研模式检查器显示可安装喷涂模块，不再提示“当前设备或配方不兼容”。
- 选择“加速”后，科研周期、实际倍率、耗电倍率和增产剂余量同步更新。
- 断料、缺电、增产剂耗尽、切换科技和无限科研均显示真实状态。
- 蓝图复制已安装喷涂模块的矩阵研究站后，模块等级和支持的模式按现有蓝图规则恢复。

### Compatibility and data-preservation constraints

- 不要将动态科技成本复制到普通配方目录。
- 不要凭空增加科技完成度，也不要改变科技原始矩阵总成本。
- 旧存档中科研模式下已经保留喷涂字段的实体应正常读取，不得删除缓存。

### Smallest owning modules

- `src/game/engine.ts`
- `src/game/content.ts`，仅在确实需要标记特殊能力时修改，不要写死动态输入
- `src/components/GamePanels.tsx`
- `src/components/FactoryNodes.tsx`

### Required tests

- 六种矩阵生产喷涂回归。
- 普通科技、多矩阵科技、无限科研的科研加速、点数消耗和耗电测试。
- 增产剂耗尽后基础速度继续运行。
- Worker、离线结算和主线程回退哈希一致。

### Known risks / rollback

这是科研结算规则，风险高于普通 UI。若额外产出语义未获产品确认，不得自行实现“免费科研进度”；只交付加速模式。

## 7. 需求 4：终局存档打开生产统计耗时过长

### Task ID / title

`DSP-FB-20260804-04` / 生产统计首屏懒加载、缓存和后台计算

### Priority

P1，终局可用性和主线程性能问题。

### Source and attachments

- 玩家文字反馈，无本项存档、性能报告或录屏。
- 因缺少同一用户的终局存档，本次没有得到真实打开耗时，不能承诺固定性能提升百分比。

### Confirmed implementation evidence

生产统计打开后会同步执行 `calculateFactoryStatistics(game, planetScope)`，扫描实体、缓存、状态和电力消费者；`game` 每次权威状态更新都会使该结果失效。参见 [StatisticsWorkspace.tsx](../../src/components/StatisticsWorkspace.tsx#L253) 和 [statistics.ts](../../src/game/statistics.ts#L76)。

页面还会在当前标签并不需要时提前计算以下内容：

- 银河工业快照；
- 已选择生产规划；
- 标签栏中的完整传送带网络数量。

这些工作在终局实体和线路数量很大时可能共同形成长任务。最终根因占比仍需用用户存档和性能监控确认。

### Required optimization plan

1. 点击“生产统计”后先渲染页面框架、关闭按钮、标签和加载状态，不等待完整统计扫描。
2. 只计算当前活动标签需要的数据。生产标签不提前计算网络拓扑、生产规划和银河页数据。
3. `listBeltNetworks(game)` 不得仅为了标签角标在每次渲染时全量执行；使用已有摘要、缓存数量或进入网络页后再算。
4. `calculateProductionPlan` 只在规划标签打开且确实存在选中方案时运行。
5. 全实体统计使用状态版本和星球范围缓存；筛选、排序、时间范围改变时复用原始统计结果。
6. 终局全量扫描优先放入可取消 Worker。关闭页面或切换统计范围时，过期任务结果不得覆盖新选择。
7. 页面打开期间不要跟随每次高频模拟结果立即重算。建议以 1 秒级稳定快照更新，或由玩家选择刷新频率；不能改变模拟本身。
8. 物品、问题设备和网络列表使用虚拟化或分批渲染，避免一次创建大量 DOM。
9. 统计数值必须标注采样时间；优化不能用长期显示旧数据伪装性能改善。

### Performance acceptance criteria

- 在双方约定的终局基准存档中，点击后 200ms 内出现可关闭的统计页面框架。
- 打开动作不产生超过 100ms 的不可中断主线程长任务；目标应进一步压到 50ms 以下。
- 完整生产表目标在 1 秒内可用；若硬件或存档规模无法满足，必须持续显示可取消的真实进度，页面仍可关闭和切换标签。

## 8. 需求 5：时间扭曲纯挂机按设备计算能力自动降档

### Task ID / title

`DSP-FB-20260804-05` / 时间扭曲计算能力调速器与积压保护

### Priority

P0。玩家反馈高倍率会超过设备能力并卡死，存在进度未保存和浏览器/桌面端崩溃风险。

### Source and attachments

- 玩家文字反馈，无本项存档、性能报告或崩溃日志。
- 该问题与此前“终局时间扭曲纯挂机仍然卡死”重复相关，但本次明确提出按设备能力自适应，而不是继续提高固定倍率上限。

### Confirmed current behavior

当前引擎只根据剩余供电计算可稳定倍率，未把 CPU/Worker 实际吞吐纳入倍率上限。参见 [engine.ts](../../src/game/engine.ts#L194) 和 [engine.ts](../../src/game/engine.ts#L3414)。

纯挂机当前每积累约 10 秒墙钟时间再提交一次任务，并用固定的最多 120 模拟秒切片。参见 [App.tsx](../../src/App.tsx#L1681) 和 [simulationBudget.ts](../../src/game/simulationBudget.ts#L1)。当一个终局存档处理 120 模拟秒所需时间超过预算产生速度时，积压会持续增长，现有逻辑没有计算能力闭环降档。

### Required adaptive model

定义三个上限：

1. `requestedMultiplier`：玩家请求倍率。
2. `powerLimitedMultiplier`：现有供电能够支持的倍率。
3. `computeLimitedMultiplier`：当前设备最近一段时间实际能够持续完成的倍率。

最终实际倍率必须为三者最低值。计算能力调速器应满足：

- 使用最近多个已完成 Worker 切片的“模拟秒 / 真实计算秒”计算平滑吞吐，不能根据单次偶发尖峰频繁抖动。
- 初次启动使用保守倍率；连续稳定多个切片后逐级升档。
- Worker 耗时上升、待处理预算增长、任务超时或内存压力出现时立即降档。
- 动态切片以可取消、可停止为目标，不再固定认为 120 模拟秒适合所有存档。建议让单个切片的计算墙钟目标保持在 0.25 至 1 秒，硬上限不超过约 2 秒，具体阈值通过真实终局存档标定。
- 待处理模拟预算限制在少量切片内。不能一边计算一边无限累计未来任务。
- 即使设备连基础时间扭曲倍率都无法持续处理，也应降回普通模拟速度或安全停止，并明确提示“当前设备计算能力不足”。

### User-visible behavior

纯挂机面板增加：

- 请求倍率；
- 电力上限；
- 计算能力上限；
- 实际倍率；
- Worker 最近耗时；
- 当前模拟积压；
- 降档原因。

玩家仍然可以请求高倍率，但系统只执行设备持续承受得住的倍率。性能恢复后可以自动回升，不要求玩家反复手动试档。

### Stop, save and failure safety

1. 点击停止只等待当前有界切片到达安全点，不能把全部积压改到主线程一次性同步补算。
2. 已提交并完成的模拟结果必须保存；尚未真正计算的加速预算不能伪装成已获得收益。
3. Worker 崩溃、页面隐藏或内存压力过高时，优先安全降档或停止，不得不断重试同一超大任务。
4. 自动降档是设备级调度信息，不进入云存档和排行榜；玩家请求值和已完成的确定性游戏状态继续按现有规则保存。

### User-visible acceptance criteria

- 在低性能设备上请求 12x，不再持续累积直至卡死，而是自动稳定在设备可承受倍率。
- 在高性能设备上不会被固定锁死在低倍率，稳定后可以逐级提高。
- 同一状态实际推进相同模拟秒数时，自动档和固定档最终游戏哈希一致。
- 停止纯挂机后在可接受时间内回到游戏，且没有重复收益、负库存或进度回退。

### Smallest owning modules

- `src/App.tsx`
- `src/game/simulationBudget.ts`
- `src/game/simulation.worker.ts`
- `src/components/TimeWarpIdleOverlay.tsx`
- `src/game/engine.ts`，仅保留玩法倍率和供电口径

### Required tests

- 人工模拟快、等速、慢和超时 Worker，验证升档、降档和积压上限。
- Worker 与主线程回退确定性。
- 停止、刷新、页面隐藏、Worker 崩溃和保存失败路径。
- 至少使用一个普通档、一个终局档和一个超级终局档持续运行测试。

### Known risks / rollback

错误的调速器可能导致倍率频繁抖动、错误丢弃已完成预算或重复结算。上线前必须提供关闭新调速器的开发回退开关；回滚不能改变已保存的游戏状态。

### Recommended verified definition

- 单位：`/min`；
- 描述：`相邻两次有效主云存档之间的白糖实际平均产量峰值`。

3. 启用内容包的存档继续遵循现有官方排行榜排除规则。
4. 离线和时间扭曲使用模拟时间作分母，排名比较的是每模拟分钟产能，不是玩家真实等待分钟。
5. 自动云同步约十分钟一次，因此正常玩家会自然形成稳定采样区间；手动刷新也必须遵循最小时间差，防止短窗口尖峰作弊。
6. 大数使用现有万、亿和科学计数格式，悬浮可查看精确值。

### Backward compatibility

- 服务端持久化布局必须兼容旧记录；如果只是 JSON 指标扩展，不应升级 SQLite layout。

### Original buildings absent or represented by abstractions

### Existing routes that are not numerically identical

即使只比较已有对应物，也不能说当前配方与原版完全一致。以下 7 项是实质数值差异；普通临界光子的批量表示和氢分馏的确定性批量表示虽然写法不同，但平均意义接近，未列入表中。

| 配方 | 当前项目 | 当前原版参考 | 风险 |
| --- | --- | --- | --- |
| X 射线裂解 | `精炼油 2 + 氢 1` | `精炼油 1 + 氢 2` | 改动会改变既有红糖/油路配平，但输入物品种类不变 |
| 物流运输机 | `钢材 5 + 处理器 2 + 电磁涡轮 2 / 4s` | `铁块 5 + 处理器 2 + 推进器 2 / 4s` | 需要先恢复推进器物品链 |
| 物流运输船 | `钛合金 10 + 处理器 10 + 电浆激发器 4 / 8s` | `钛合金 10 + 处理器 10 + 加力推进器 2 / 6s` | 会影响建筑制造中心递归链和载具库存估值 |
| 粒子对撞制氘 | `10 氢 -> 5 氘 / 5s` | `10 氢 -> 5 氘 / 2.5s` | 当前吞吐只有参考值一半 |
| 高效卡西米尔晶体 | 消耗光栅石 4 | 消耗光栅石 8 | 调整会使现有稀有资源需求翻倍 |
| 氘核燃料棒 | 同原料与产量，`6s` | `12s` | 当前生产速度为参考值两倍 |
| 反物质燃料棒 | 反物质/氢各 10，`12s` | 反物质/氢各 12，`24s` | 同时涉及材料成本和生产速度 |

这些差异可能是本项目主动做过的节奏和平衡调整。本项只记录事实；除`重整精炼`外，不得以“修 Bug”为名一次性覆盖现有数值。

### Required behavior: phase A, oil-route fix

1. 新增稳定的 `reforming_refine` RecipeId 和对应科技 ID，名称显示为“重整精炼”。
2. 配方必须使用原油精炼厂，耗时和输入输出以实现时复核的原版数据为准。
3. 科技树应放在红糖/石油阶段的合理位置，并显示准确的前置、矩阵成本和解锁说明。
4. 完成科技后，桌面检查器、手机配方选择、配方图鉴、生产管理和蓝图配方覆盖均能选择该配方。
5. 配方图必须同时把精炼油识别为输入和输出，递归规划必须防止把该循环当作无限免费来源。
6. 已有精炼厂继续保留当前选中的等离子精炼或 X 射线裂解，不自动切换，不清空缓存，不拆线路。
7. 手搓和建筑制造中心不得错误开放精炼厂专用化工配方；它只能由兼容生产建筑执行。
8. 增产剂、缺料状态、生产统计、离线结算和大时间步结算均遵守现有闭环规则。

### Required behavior: phase B, parity decision

开发前由产品负责人明确选择以下一种范围：

1. **推荐：只补生产链中有实际用途的缺失配方。** 先交付重整精炼；推进器链可作为后续完整物流改造；继续保留无地基、无分拣器、无供电塔的 2D 简化设计。
2. **全面追求原版非黑雾目录。** 必须连同缺少物品、建筑、科技、资源来源、使用场景、UI、迁移和测试成套引入，不能只让图鉴数字看起来齐全。
3. **维持当前改编版平衡。** 只在图鉴或项目说明中明确“并非原版 1:1 配方”，并为刻意替代的物流/供电/分拣系统写出对应关系。

本报告推荐方案 1。它能解决玩家看到的真实油路缺口，同时避免恢复已经被项目架构取代的建筑。

### User-visible acceptance criteria

- 研究“重整精炼”后，原油精炼厂配方列表出现该项，选择后按正确比例稳定生产精炼油。
- 配方搜索“重整”“精炼油”“煤”“氢”都能找到该路线。
- 配方图鉴明确显示它是精炼油循环增产路线，不把循环错误展示成无原料产物。
- 原有`等离子精炼`和`X 射线裂解`仍可选择，已有产线载入后不改变配方、不丢缓存。
- 新旧存档、在线、离线、喷涂、大时间步和生产统计结果保持物资守恒。
- 内容审计能对一份固定的原版非黑雾配方清单输出“已实现、主动替代、明确不适用、缺失”四种状态；新增原版配方后漏登记会使测试失败。

### Compatibility and data-preservation constraints

- 新增 RecipeId/TechId 会扩大内容目录；只有确实新增持久状态字段时才升级 GameState。普通目录扩展本身不应强制升级存档版本。
- 旧存档未研究新科技时保持原状；不能自动扣矩阵、自动完成科技或替换已有配方。
- 若未来修改 X 射线裂解或载具配方，必须单独评估现有机器缓存、递归制造任务、生产规划和排行榜节奏，不能与新增重整精炼混在一个不可回滚改动中。
- 配方循环必须有确定性的终止和净产物判断，避免建筑制造中心、手搓递归或规划器无限递归。

### Smallest owning modules

- `src/game/types.ts`
- `src/game/content.ts`
- `src/game/recipeGraph.ts`
- `src/game/progressionAudit.ts`
- 配方/科技/图鉴 UI 的既有通用目录消费者，原则上不新增硬编码分支
- `src/game/content.test.ts`
- `src/game/recipeGraph.test.ts`
- 相关引擎和 E2E 测试

### Required tests

- 内容目录引用完整性和固定原版非黑雾清单审计。
- 重整精炼正常生产、缺煤、缺氢、缺精炼油、输出容量不足、无电/低电、喷涂和堆叠生产。
- 同一物品同时出现在输入和输出时的净结算、统计与守恒。
- 配方图循环检测；递归手搓和建筑制造中心不得进入无限递归。
- 旧存档载入后既有精炼厂的配方、缓存、进度和线路保持不变。
- 桌面、手机竖屏、手机横屏的配方选择、科技跳转和图鉴搜索。
- 60 秒与分段推进、在线与离线结果哈希一致。

### Known risks / rollback

重整精炼是输入和输出均包含精炼油的闭环配方，比普通单向配方更容易暴露递归图、净统计和输出容量的错误。最安全的回滚边界是独立撤销新科技和新配方；不得通过删除玩家缓存或回退整个存档版本处理失败。

## 13. 合并验证矩阵

开发完成后至少执行：

```powershell
npm run typecheck
npm test
npm run test:server
npm run build
```

聚焦 E2E 至少覆盖：

1. 建筑和物流塔直接输入最终数量，含库存守恒和历史超限。
2. 矩阵生产喷涂回归、科研加速、缺增产剂回退普通速度。
3. 物流槽位紧凑布局的桌面、手机竖屏、手机横屏和五档字体截图。
4. 终局统计打开性能、快速关闭和过期 Worker 结果取消。
5. 时间扭曲低性能自动降档、积压上限、停止和保存。
6. 排行榜白糖速率的服务端计算、旧记录兼容和限制账号。
7. 星球下拉顺序与筛选状态保持。
8. 五档字体下节点、端口和线路几何不漂移。
9. 重整精炼的科技解锁、闭环净结算、配方图循环保护和旧油路兼容。

高风险项 2、5、6、8、9 合并后必须再运行完整相关回归。任何涉及 `GameState` 新字段的实现还需增加旧存档迁移夹具；如果按本文推荐方案实现，需求 1、3、4、7、8 不需要升级存档版本，需求 6 优先只扩展服务器排行榜 JSON 指标，需求 9 的目录扩展也不应单独触发 GameState 升级。
