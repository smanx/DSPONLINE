# 多核模拟与量子物流性能报告（2026-08-01）

> 发布状态：仅完成本地实现、只读玩家存档测试和报告；按用户要求未推送 VPS、未更新下载页、未生成发布安装包。

## 结论

本轮适合上线的是量子物流单 Worker 优化，不适合直接启用多 Worker 权威模拟。

- 402 座量子塔的批量升级、接入和交接已经从逐塔重复扫描改成一次规划、一次更新，结果哈希与串行 Oracle 一致。
- 量子边界回写建立一次 `stationById`；输入和输出请求只在每个五秒边界规范化、分组和排序一次。
- 量子塔及接入中的塔不再进入传统舰队派遣、翘曲器补充和拥堵扫描。接入中的既有路线继续安全到达，但不会再创建新路线。
- 1/2/4/8/12/16 Worker 探针证明行星只读分区有并行潜力，但也证明当前量子阶段太短，拆成子 Worker 后消息传输会比计算本身更贵。
- 本轮没有修改 GameState v44、存档 envelope v2、云 schema v7、玩法倍率或库存规则。

## 量子优化结果

| 场景 | 优化前 | 优化后 | 下降 |
| --- | ---: | ---: | ---: |
| 402 塔 / 2,010 槽完整五秒边界，中位数 | 17.50 ms | 12.18 ms | 30.4% |
| 402 塔批量升级本体 | 54.66 ms | 2.84 ms | 94.8% |
| 402 塔批量开始接入 | 8.62 ms | 0.22 ms | 97.4% |
| 402 塔批量完成交接 | 10.46 ms | 0.12 ms | 98.9% |

真实终局样本在三组电网都补充相同的基准电源后，传统物流与全量量子物流各运行五个模拟秒。2026-08-01 最终复测如下：

| 场景 | 总耗时中位数 | 传统物流阶段 | 量子阶段 |
| --- | ---: | ---: | ---: |
| 传统物流 | 668.68 ms | 443.95 ms | 0.43 ms |
| 402 塔稳定量子物流 | 245.61 ms | 5.94 ms | 3.26 ms |

相同五个模拟秒下总耗时下降 63.27%，传统物流阶段下降约 98.66%。量子态处理了 942 个有效边界请求，没有创建传统 `StationRoute`。不同独立进程的五秒复测下降范围为 60.8%～64.8%，用于说明 Windows 调度和 JIT 抖动，不应只挑最快的一次作为结论。

持续 Worker 又做了两次独立进程复测。每次运行 2 秒预热和 30 个稳态单秒步骤，覆盖 6 个完整量子结算边界。下表使用两次长采样的中点，并在括号中保留实测范围：

| 场景 | 平均耗时/模拟秒 | P50 范围 | P95 范围 | 物流阶段均值 | 传送带阶段均值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原始玩家档，传统物流 | 115.39 ms（112.90～117.88） | 107.76～116.59 ms | 145.87～149.10 ms | 71.61～75.38 ms | 23.79～24.48 ms |
| 同档 402 塔稳定量子化 | 43.72 ms（42.71～44.72） | 38.30～40.44 ms | 76.41～80.91 ms | 1.18～1.28 ms | 24.49～25.50 ms |

持续运行口径下降 60.4%～63.8%，中点约 62.1%，约等于同一台机器每秒可处理的模拟量提高到 2.64 倍。量子边界、历史采样和系统调度仍会形成 P95 峰值，因此不能只看 P50。

## 多 Worker 探针

探针把同一终局样本按行星切分，只执行只读实体、槽位、航线和传送带扫描。结果使用可交换校验值按固定规则合并；每档校验值完全一致。这是理想上限，不等于完整模拟已经可以并行。

| 子 Worker | 墙钟中位数 | P95 | 传输与合并 | 相对协调线程串行 |
| ---: | ---: | ---: | ---: | ---: |
| 协调线程串行 | 76.93 ms | 79.00 ms | 0 | 1.00× |
| 1 | 108.22 ms | 112.56 ms | 19.49 ms | 0.71× |
| 2 | 56.60 ms | 59.19 ms | 13.41 ms | 1.36× |
| 4 | 34.13 ms | 37.91 ms | 10.59 ms | 2.25× |
| 8 | 21.48 ms | 25.91 ms | 8.13 ms | 3.58× |
| 12 | 21.25 ms | 26.39 ms | 9.83 ms | 3.62× |
| 16 | 19.48 ms | 28.80 ms | 7.20 ms | 3.95× |

单独增加一个子 Worker 会因为结构化克隆而变慢约 29%。8 Worker 的理想扫描已经有明显收益，但仅传输与合并就需要 8.13 ms，高于五秒量子边界本身的 3.26 ms。因此量子结算不启用子 Worker。

## 完整模拟的多核收益模型

目前还没有把权威 `GameState` 拆给多个 Worker 并确定性合并，所以不存在“完整游戏 8 核实测”数据。下面只把两个真实测量组合起来：真实玩家档的阶段占比，以及同一档案在 2/4/8/12/16 Worker 下的实际分区、传输和合并成本。

传统状态中可先按行星拆分的生产、传送带、电力和戴森平均合计约 33.93 ms，剩余串行部分约 81.47 ms；量子稳定后对应数字约为 33.51 ms 和 10.21 ms。模型同时计入探针测到的负载不均和消息成本，但尚未计入未来完整库存增量的确定性合并，因此仍应视为上限估算：

| 子 Worker | 传统物流整步估算 | 相对 115.39 ms | 稳定量子整步估算 | 相对 43.72 ms |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 113.92 ms | 下降 1.3% | 42.43 ms | 下降 3.0% |
| 4 | 102.43 ms | 下降 11.2% | 31.05 ms | 下降 29.0% |
| 8 | 95.48 ms | 下降 17.3% | 24.16 ms | 下降 44.7% |
| 12 | 96.33 ms | 下降 16.5% | 25.01 ms | 下降 42.8% |
| 16 | 94.09 ms | 下降 18.5% | 22.76 ms | 下降 47.9% |

这张表说明：传统物流仍占大头时，即使使用 8 个子 Worker，整局也只能再快约 17%，因为每秒约 72～75 ms 的物流仍在串行等待。先切换稳定量子物流后，8 Worker 才有约 45% 的理论追加空间；与原始传统状态相比，组合模型约从 115.39 ms 降到 24.16 ms，即总耗时最多下降约 79.1%、吞吐约提高到 4.78 倍。

工程上不能承诺模型上限。真正实现确定性增量合并后，建议把发布验收目标定为：传统物流档 8 Worker 下降 10%～15%，稳定量子档追加下降 30%～40%，两者组合相对原始状态下降 70%～75%。未达到 20% 或状态哈希不一致就保持单 Worker。

从收益与复杂度看，4 Worker 是第一档值得实现的配置，8 Worker 是高端桌面的合理上限；12 和 16 Worker 已出现明显边际递减及更差的 P95，不应默认开启。手机仍应保持 1～2 Worker。

## 用户体验与代价

- 生产、物流、科研、戴森、离线收益和状态哈希规则不变。
- 已在途货物不会删除；接入期间只停止新的传统派遣，让尾货真正排空。
- 批量操作不再产生数百份中间 GameState，降低点击“全部升级/接入”时的主线程停顿和临时垃圾回收。
- 性能面板新增独立“量子物流”阶段归因，但监控仍默认关闭。
- 没有为了跑分降低刷新率、删减动画、减少收益或粗放提高模拟步长。

## 后续多核门槛

下一阶段应先实现紧凑的行星只读输入和固定顺序增量输出，只并行无写冲突的生产、电力和线路连通分量。传统物流、科研完成、建筑制造和全局库存仍留在协调 Worker。2/4/8 Worker 必须逐档满足：

1. 与单 Worker Oracle 的完整状态哈希一致。
2. 输入、输出、线路、载具、翘曲器和在途货物守恒。
3. 真实终局档墙钟至少下降 20%，P95 不恶化。
4. Worker 克隆与合并不超过节省时间的三分之一。
5. 低端手机自动保持 1 个 Worker，不因线程和内存压力变慢。

在这些门槛全部通过前，生产版本继续使用单个权威模拟 Worker。
