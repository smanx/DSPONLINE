# 暂停模拟时画布性能优化计划

> 日期：2026-07-31
> 性质：只读诊断、设计方案和风险评估，不代表已经开发或部署。
> 目标：玩家点击“暂停模拟”后，仍能流畅摆放、拖动、连接、移动和缩放建筑。

## 1. 先说结论

当前“暂停模拟”只暂停了工厂的时间推进，不等于暂停了浏览器画布。

可以把游戏想成两台机器：

```text
模拟机器：Worker、生产、物流、电力、传送带结算
画布机器：鼠标输入、React 组件、React Flow、线路诊断、CSS 动画、浏览器布局
```

点击暂停后，第一台机器基本停下来了，但第二台机器仍然在工作。因此玩家拖动建筑时仍可能卡顿，问题不应优先归因于暂停逻辑本身。

当前最重要的根因是：

1. `src/App.tsx` 的全局 `pointermove` 每次都会调用 `setPointer`。鼠标移动一次，顶层 `FactoryGame` 就可能重新渲染一次（约 1497-1505 行）。
2. 每次顶层重渲染，`useObservedBeltFlowGame` 都会对全部传送带重新采样并创建新的数组。该 Hook 在主游戏和画布各调用一次；排行第一存档有 5,746 条传送带，相当于一次鼠标移动可能重复扫两遍全局线路。
3. 画布线路派生会遍历当前星球的所有传送带并执行 `diagnoseBelt`（约 3204-3285 行）。暂停时线路数据没有变化，但只要上层状态变化仍可能重新计算。
4. React Flow 的 `onMove` 每次移动视口都会调用 `setViewportZoom`（约 4768-4771 行），导致节点、线路和低细节显示判断反复重算。
5. 拖动建筑时，对齐辅助线会逐个遍历当前画布的所有节点（约 3633-3661 行）。建筑越多，每个鼠标事件的成本越高。
6. 暂停状态只传给了生产进度显示，未形成全局的“暂停画布模式”；建筑状态光效、状态点、线路流动等 CSS 动画仍可能继续运行。
7. 画布刷新定时器仍会在暂停时启动（约 934-945 行），性能监控和自动保存也可能在暂停时继续占用主线程。

所以一句话根因是：

> **暂停停止了“工厂计算”，但没有停止“每次输入都重新计算整张画布”。**

## 2. 目标和验收标准

暂停后必须同时满足：

- 不再提交新的模拟预算。
- 已经在 Worker 中运行的任务按明确的安全边界处理，不产生重复生产、库存丢失或时间倒退。
- 鼠标移动、拖动建筑、框选、拉线、缩放和移动画布不触发全局工厂重算。
- 暂停期间建筑、线路、库存和科技数值保持不变；玩家的编辑操作仍然立即生效。
- 取消暂停后，画布显示和模拟状态重新同步，不出现“画面旧、数据新”或“数据旧、画面新”。

建议的性能门槛：

| 场景 | 桌面端目标 | 移动端目标 |
| --- | --- | --- |
| 暂停后移动画布 | P95 帧耗时不超过 20 ms | P95 帧耗时不超过 33 ms |
| 暂停后连续拖动建筑 10 秒 | 长帧（超过 50 ms）不超过 1 次 | 长帧不超过 3 次 |
| 暂停后连续缩放 10 秒 | 不出现明显跳帧 | 不出现持续性卡顿 |
| 暂停状态后台模拟 | 不提交新的模拟任务 | 不提交新的模拟任务 |
| 恢复模拟 | 状态哈希、库存、在途路线与暂停前规则一致 | 同左 |

这些是验收目标，不是当前实测结果。百分比是工程估算，必须通过实际终局存档和真机测试复核。

## 3. 分阶段优化方案

### P0：先建立“暂停专用”性能测量

**做法**

- 性能面板增加 `pausedCanvas` 场景，单独记录：鼠标事件到 React 提交耗时、节点派生耗时、线路派生耗时、React Flow 提交耗时、浏览器长帧数量。
- 将“模拟 Worker 耗时”和“画布主线程耗时”分开显示。
- 分别测试空画布、300 个建筑、1,000 个建筑、排行第一存档，以及暂停/运行两种状态。
- 记录 Chromium、Electron、Android Chrome、iOS Safari 的结果。

**收益**：直接性能提升 `0%–5%`，主要用于避免把画布问题误判成模拟器问题。

**风险**：低。只增加观测，不改变玩法和存档。

### P1：暂停时进入“安静模式”

**做法**

- 暂停时停止画布刷新定时器，不再每 100–200 ms 尝试提交相同的画布快照。
- 暂停时停止只用于测速的持续 `requestAnimationFrame` 采样；改为玩家打开性能面板时才采样。
- 增加明确的 `data-simulation-paused` 或等效状态，让暂停时关闭建筑扫描光效、状态点呼吸、传送带流动、货物动画和不必要的阴影滤镜。
- 纯挂机、页面隐藏、暂停三种状态分别处理，不能混用。

**预期收益**

- 暂停期间后台无效任务减少 `80%–95%`。
- 主线程可用余量增加约 `10%–25%`。
- 画布交互帧耗时预计下降 `10%–20%`。

**风险**：低到中。

- 关闭动画不会影响游戏数据，但需要确认暂停提示、选择框、连接预览仍然可见。
- 如果把所有动画都关闭，可能误伤玩家正在进行的连接预览和按钮反馈，因此应只关闭生产表现动画。

### P2：把鼠标指针和拖动预览从顶层 React 状态中隔离

**做法**

- 不再用全局 `setPointer` 驱动整个 `FactoryGame` 重渲染。
- 鼠标位置放入轻量的指针控制器或独立 Overlay，只更新建筑预览、货物光标、连接预览和提示框。
- 使用 `requestAnimationFrame` 合并同一帧内的多个 `pointermove`，最多每帧更新一次。
- 鼠标没有进入放置、拉线或拖动物品状态时，不更新指针 React 状态。
- 移动端继续保留 pointer capture、双指缩放和软键盘兼容逻辑。

**预期收益**

- 顶层 React 重渲染次数减少 `60%–90%`。
- 暂停时摆放建筑、拖动预览和拉线的主线程负担下降 `25%–45%`。

**风险**：中。

- 指针 Overlay 与 React Flow 的坐标转换必须保持一致，否则可能出现“预览位置和实际放置位置不一致”。
- 需要验证高 DPI、浏览器缩放 80%–200%、触控笔和移动端触摸坐标。
- 连接提示、货物光标和蓝图光标不能出现一帧延迟或残留。

### P3：暂停时复用不可变画布快照

**做法**

- 把画布需要的数据拆成两类：
  - 拓扑数据：建筑位置、端口、线路连接、线路样式。
  - 动态数据：流量、拥堵、生产进度、运输状态。
- 暂停后冻结画布投影快照；鼠标移动不重新调用 `useObservedBeltFlowGame`。
- `BeltFlowSampler` 只在真实模拟结果发布或线路发生编辑时运行，不在每次 UI 重渲染时运行。
- 只更新受影响的建筑和线路：放置、删除或移动一个建筑时，失效该建筑相邻端点和相关线路，不重建整张图。
- 保留 `GameState` 作为唯一权威状态，画布快照只能是派生缓存，不能写入存档。

**预期收益**

- 暂停时传送带扫描、线路诊断和节点派生耗时下降 `50%–80%`。
- 整体暂停画布帧耗时下降 `30%–55%`。

**风险**：中到高。

- 缓存失效不完整会导致新建筑已经放置，但线路或端口仍显示旧数据。
- 必须覆盖多条线路连接同一建筑、拆线、移动建筑、蓝图部署、撤销/重做和切换星球。
- 不能把缓存快照当成模拟状态，否则会破坏存档和确定性。

### P4：优化 React Flow 的移动、缩放和节点拖动

**做法**

- `onMove` 只更新 `viewportRef`；只有缩放跨过低细节档位，或 `onMoveEnd` 时才更新 React 状态。
- 低细节档位只保留 `compact / medium / full` 三档，避免每个缩放小数变化都重算所有节点和线路。
- 节点拖动时，对齐检测使用空间索引或网格桶，不再每个 pointer 事件遍历全部节点。
- 对齐辅助线和拖动位置更新使用帧节流。
- 线路几何、线路标签和节点数据分别缓存；视口移动不应重新执行 `diagnoseBelt`。
- 继续启用视口裁剪，但要确认边的命中区域、端口连接和小地图不被裁掉。

**预期收益**

- 移动画布和缩放时主线程计算下降 `40%–70%`。
- 拖动建筑时对齐检测耗时下降 `60%–90%`。
- 暂停状态的交互 FPS 目标提升约 `1.5–2 倍`。

**风险**：中。

- 只在 `onMoveEnd` 更新缩放状态可能让低细节模式切换晚一帧，需要在跨档位时即时切换。
- 空间索引必须在移动、批量移动、蓝图部署和撤销后正确更新。
- React Flow 的 pointer capture、框选、连接线和触摸手势容易互相影响，需要桌面和手机分别回归。

### P5：节点和线路组件做稳定引用与精确重渲染

**做法**

- 对 `VeinNode`、`MachineNode`、`LogisticsNode`、`PowerNode` 和 `FactoryEdge` 使用基于 `visualSignature`、位置和选中状态的精确比较。
- 不要因为父组件的光标移动，就让所有建筑卡片重新执行 JSX 和图标渲染。
- `visualSignature` 拆分为“拓扑签名”和“状态签名”，暂停时只要拓扑未变就复用组件。
- 避免在每次节点派生时对完整实体执行昂贵的 `JSON.stringify`；改用稳定字段哈希或增量签名。

**预期收益**

- 暂停时无关节点重渲染减少 `70%–95%`。
- React 组件 CPU 时间下降 `30%–60%`。
- 浏览器布局和垃圾回收压力预计下降 `15%–35%`。

**风险**：中到高。

- 比较条件遗漏字段会造成界面不更新，例如库存、端口占用或锁定图标不刷新。
- 动态 Handle 的尺寸变化必须继续触发 `updateNodeInternals`。
- 不能为了复用组件而保留过期的点击回调或旧的 `GameState` 闭包。

### P6：暂停期间的保存和云同步降级为低优先级任务

**做法**

- 自动保存不要在建筑拖动或线路连接的同一帧执行。
- 使用 `requestIdleCallback` 或 Save Worker 在浏览器空闲时间序列化；不支持时使用短时间片分段处理。
- 保存前复制一次一致的状态快照，保存过程不读取正在被编辑的临时画布对象。
- 暂停时允许用户手动保存，但不能因为自动保存阻塞鼠标操作。
- 云同步只在本地保存成功后排队，不在画布交互期间直接执行完整导出和比较。

**预期收益**

- 保存导致的暂停瞬时卡顿下降 `60%–90%`。
- 长帧数量预计下降 `10%–25%`，但只影响保存发生的时间点。

**风险**：中到高。

- Worker 保存失败、浏览器关闭和 IndexedDB 配额错误必须保留现有急救镜像和读回校验。
- 不能为了流畅而跳过存档校验、覆盖新版本或删除手动槽位。
- 云同步冲突不能被自动保存逻辑静默覆盖。

## 4. 综合收益估算

下表是“暂停状态下的画布交互负担”估算，不是模拟速度提升：

| 阶段 | 主要改善对象 | 预期下降 |
| --- | --- | ---: |
| P1 安静模式 | 后台无效定时器和动画 | 10%–25% |
| P2 指针隔离 | 鼠标移动触发的顶层重渲染 | 25%–45% |
| P3 画布快照 | 全量传送带扫描和线路诊断 | 30%–55% |
| P4 React Flow 交互 | 移动画布、缩放、对齐检测 | 40%–70% |
| P5 组件复用 | 节点、线路和布局重渲染 | 30%–60% |
| P6 保存异步化 | 自动保存造成的偶发长帧 | 60%–90% |

这些百分比不能相加。推荐对外使用以下保守目标：

> **P1–P5 完成后，暂停状态下画布主线程负担预计下降 50%–70%，建筑摆放、移动画布和缩放的交互卡顿预计下降 50%–70%。**

> **P6 只改善保存瞬间，不能算入持续画布性能；保存造成的瞬时卡顿目标下降 60%–90%。**

如果只做低风险快速补丁，建议先做 P1 + P2：目标是暂停时交互卡顿下降 `25%–40%`。如果仍然卡，再做 P3 + P4；这两项才是终局大工厂的核心收益。

## 5. 推荐开发顺序

1. P0：先采集暂停画布基线，确认是鼠标移动、视口移动、线路派生还是 CSS 动画占比最高。
2. P1：暂停时停止无效刷新、监控和非必要动画，风险最低。
3. P2：隔离指针与拖动预览，通常能最快改善“摆放建筑卡”。
4. P3：冻结并增量失效画布快照，解决终局线路扫描。
5. P4：优化 React Flow 的视口和拖动路径，解决“移动画布卡”和“缩放卡”。
6. P5：最后做节点/线路精细 memo，避免在缓存不稳定时扩大排查范围。
7. P6：独立处理保存卡顿，不和模拟或画布缓存混在同一个版本中。

## 6. 必须覆盖的回归测试

- 暂停后放置、堆叠、删除、移动、框选和撤销/重做建筑。
- 暂停后连接、拆除和更换传送带，确认端口和物品类型不丢失。
- 暂停后蓝图预览、蓝图部署、矿脉锚点和物流塔载具配置。
- 暂停后切换星球、打开/关闭右侧检查器、折叠侧栏和切换 80%–200% 字号。
- 桌面鼠标、触控板、触摸屏、Android Chrome、iOS Safari/PWA 和 Electron。
- 1x、4x、时间扭曲纯挂机停止、页面隐藏和恢复模拟。
- 暂停前有一个正在运行的 Worker 任务时点击暂停，确认没有重复结算、库存丢失或状态回退。
- 运行、暂停、恢复后比较状态哈希、库存、在途路线、生产统计和视口位置。
- 排行第一存档、300/1,000/3,000 建筑合成夹具，以及 5,000 条以上传送带压力夹具。

## 7. 最终判断

这个问题不是“暂停按钮失效”，而是“暂停只覆盖了模拟层，没有覆盖画布层”。最值得先修的不是继续压缩模拟 Worker，而是减少鼠标移动和画布移动对顶层 React 的影响。

建议把最终版本的暂停体验定义为：

> **暂停后，工厂数值冻结；画布仍然像普通编辑器一样流畅。**

在不改变玩家生产数据、不限制运输船和不删除线路的前提下，合理的整体目标是暂停交互卡顿下降 `50%–70%`；这是可争取的工程范围，不应在没有真实终局和手机测试前承诺固定帧率。
