# 太空电梯与恒星系联合空间站开发 Agent 提示词

> **已废弃（2026-07-31）**：本提示词禁止继续使用。太空电梯、恒星系空间站、八站网络和本文对应的 v43 设计已被量子物流网络方案取代。请改用 [QUANTUM_LOGISTICS_NETWORK_AGENT_PROMPT.md](./QUANTUM_LOGISTICS_NETWORK_AGENT_PROMPT.md)。

下面的提示词可直接交给后续开发 Agent。完整产品规格以同目录的 `SPACE_ELEVATOR_SYSTEM_STATION_DEVELOPMENT_PLAN.md` 为唯一需求来源。

```text
你负责在 DSPidle2 / DSP极简网络中实现“太空电梯与恒星系联合空间站”终局物流系统。

工作目录：D:\GameDev\DSPidle2

开始前必须完整阅读：

1. .codex/skills/develop-dspidle/SKILL.md
2. docs/PROJECT_STATUS.md
3. docs/ARCHITECTURE.md
4. docs/GAMEPLAY_SYSTEMS.md
5. docs/ROADMAP.md
6. docs/TESTING_RELEASE.md
7. docs/SPACE_ELEVATOR_SYSTEM_STATION_DEVELOPMENT_PLAN.md
8. .codex/skills/develop-dspidle/references/project-map.md

然后运行 git status --short。当前工作树可能包含其他 Agent 尚未提交的 1.0.16 改动，全部视为用户工作。不得 reset、clean、checkout、覆盖或回退任何不属于本任务的改动。不要部署服务器，不要替换 Web/API、Windows 或 Android 公开制品，除非用户另行明确授权。

目标不是给现有物流塔增加一个外观页面，而是把玩家主动转换后的终局物流从“塔与塔多对多派遣”改为“最多 8 个恒星系枢纽聚合结算”。太空电梯模式必须彻底退出传统伙伴匹配和 StationRoute 派遣；未升级或仍在 legacy 模式的物流塔继续使用现有逻辑。

必须严格执行开发计划书中的已确定规则，尤其包括：

- 两条各 3 项的终局科技分支和 10 万至 10 亿宇宙矩阵成本。
- 每个恒星系独立建设一座空间站，工地开工即出现在星球切换界面。
- 四阶段真实材料交付，每颗行星最多一座施工发射平台。
- 星际物流站原地升级 Mk.II，升级与模式切换分离，Mk.II 不能降级。
- legacy -> elevator 时停止新派遣，等待该站参与的全部传统航线完成后在 5 秒边界切换。
- 太空电梯模式使用一个大型通用输入口和五个不同物品输出口。
- 通用入口可连接任意数量的独立单物品传送带；输入物品种类不受五槽限制。
- 修改已连线输出口前连续确认两次，只拆目标端口线路，返还传送带并把线路物资退回本系共享仓库。
- 本系共享仓库玩法无限，使用规范十进制整数字符串持久化，科学计数法只用于显示。
- 每 5 个模拟秒按固定顺序聚合结算，不依赖墙上时间或 UI 刷新。
- 上传、下载、多来源、多目标和能源不足统一按申请量比例分配，整数余数使用持久公平游标。
- 跨星系货物即时到账，不保存货物在途；舰队按距离进入聚合冷却。
- 八座空间站共享舰队、翘曲器和能源池，不逐艘模拟。
- 三类固定模块为物流主干、能源核心、星际运输；模块不是独立物品或独立实体。
- 模块从所属星系共享仓库批量扣料并立即完成，每 10 个成本翻倍，拆除按实际 LIFO 成本返还 50%。
- 传统库存、线路、路线、载具、翘曲器和保存数据必须守恒。

实现顺序是硬约束，不允许从 UI 开始：

阶段 0：无界面性能原型

- 在不修改正式 GameState 的前提下实现纯 hub 模型原型。
- 使用匿名 player / terminal2x 夹具和只读真实终局样本。
- 测量 8 hub、5 秒聚合、即时货物、聚合舰队冷却。
- 门槛：物流耗时至少降低 80%，总引擎耗时至少降低 50%。
- 如果总收益低于 30%，停止后续实现并向用户报告证据，不要继续做 UI 或内容。

阶段 1：状态与迁移

- 将 GameState 从 v42 升级到 v43。
- envelope 保持 v2；云 schema 和 SQLite layout 不自动升级。
- 增加 systemSpaceStations、galacticHubNetwork 和 Mk.II 模式字段。
- v42 -> v43 默认不建设、不赠送、不转换任何对象，所有传统物流逐字段保留。
- 服务端接受并严格验证 v43、十进制字符串、模块数和舰队返回桶。

阶段 2：本系枢纽模拟

- 优先新增独立 pure module，例如 systemSpaceStation.ts、systemHubLogistics.ts、systemHubRuntime.ts。
- engine.ts 只保留确定性编排入口，不继续堆积完整领域实现。
- 实现大整数 helper、5 秒边界、比例分配、公平余数、主干和本地能源。
- 同时写 1s/5s/分段/保存重载/离线等价测试。

阶段 3：Mk.II 与线路

- 实现升级、堆叠成本、两种模式、安全过渡和取消过渡。
- 确保 elevator 模式不进入 stationSlotsByKey、findStationSlotPeers、dispatchStationScope 或 advanceStationRoutes。
- 保留 legacy 全扫描路径作为传统物流确定性 oracle。
- 增加稳定输出端口索引，不要复用物资配送枢纽三端口的专用字段。

阶段 4：科技、工地和模块

- 更新全部闭合引用：ID、目录、来源用途、解锁、施工、科技展示、图鉴、迁移、服务端校验和测试。
- 使用计划书中的首轮候选成本和公式，并把数值集中在一个领域目录。
- 批量模块成本使用 BigInt 分段等比求和，不逐模块循环。

阶段 5：空间站工作区

- 桌面和手机分别实现适合其信息架构的页面，共用领域命令和 selectors。
- 空间站入口看起来与当前恒星系行星并列，但实现为独立 workspace，不把 activePlanetId 改成非 PlanetId。
- 打开 workspace 时冻结底层工厂画布快照，模拟继续。
- 功能模块使用固定节点；自由装饰不进入模拟。
- 使用现有图标库，不手绘重复 SVG。

阶段 6：联合协议

- 实现 operational hubs 之间的比例调货、全局舰队、全局翘曲器、银河能源和距离冷却。
- 货物在结算点即时到账；只保存聚合舰队返回桶。
- 只按活跃物品和已建空间站处理，不按全部塔对或逐船循环。

阶段 7：诊断、离线和性能

- 接入 offlineCriticalEvents，但不能改变结算公式。
- 扩展性能监控：hub settlement、BigInt、合同、活跃物品、舰队桶、主干和能源阶段。
- 完成 1 小时、8 小时、24 小时、7 天、30 天在线/离线/分段一致性。
- 完成 30 分钟内存趋势以及 1x、4x、12x 压力测试。

测试要求：

- 先写聚焦单元和迁移测试，再逐阶段运行。
- 最终必须通过 TypeScript、相关 Vitest、服务端测试、生产构建和相关 Playwright。
- 正式候选前运行完整发布矩阵，并准确报告通过、失败、跳过和未运行项。
- UI 必须覆盖桌面、手机竖屏、手机横屏、亮色/深色、80/100/125/150/200% 字体。
- 使用 Playwright 截图检查通用入口、五路输出、空间站建设画布、正式画布和双确认弹窗无重叠。

硬性性能验收：

- 未启用本功能的旧存档性能回归不超过 3%。
- 全转换终局样本物流阶段至少 -80%。
- 全转换终局样本总引擎耗时至少 -50%。
- 平均单模拟秒 <60ms，P95 <80ms。
- 12x 纯挂机无持续债务增长。
- 舰队从 100 增加到 1,000,000 时，枢纽结算耗时变化不超过 5%。
- 状态与存档大小不随物资数量或运输船逐艘对象增长。

保护规则：

- 不得用清档、重建工厂、重置路线或截断库存作为迁移方案。
- 不得把 BigInt 直接放入 JSON；持久化为规范十进制字符串。
- 不得用 Math.random() 或墙上时间参与模拟。
- 不得把运行时索引、候选缓存、脏集合或 React Flow 对象写入 GameState。
- 不得为了性能近似玩家产量、物资、能源或舰队结果。
- 不得默认让旧物流塔升级、切模式或退出传统网络。
- 不得修改或复用现有超大型物资出口活动状态作为空间站库存。
- 不得操作生产服务器或玩家数据。

在每个阶段完成后：

1. 汇报实现范围和未完成项。
2. 汇报精确测试命令及结果。
3. 汇报状态版本、迁移和物资守恒证据。
4. 汇报性能数据，不用主观“更流畅”代替数字。
5. 更新计划书要求的 canonical docs，但只写已经实现并验证的事实。

最终交付必须包含：

- 完整功能代码与领域拆分。
- v43 无损迁移和服务端验证。
- 桌面/手机完整工作区。
- 单元、迁移、服务端、E2E 和性能测试。
- 真实终局存档只读性能报告。
- 更新后的架构、玩法、路线图、测试和发布说明。
- 明确说明没有部署，等待用户单独授权发布。
```
