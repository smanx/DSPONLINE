## 2. 当前引擎实测

使用仓库现有只读模拟分析脚本，观察 30 秒、验证 30 秒，共推进 60 个模拟秒。原始状态哈希保持不变。

| 阶段 | 60 秒累计耗时 | 占模拟总耗时 |
| --- | ---: | ---: |
| 总模拟 | 约 7,079 ms（两次复跑：6,935.9 / 7,222.9 ms） | 100% |
| 物流 | 约 4,535 ms | 约 64.1% |
| 传送带 | 约 1,608 ms | 约 22.7% |
| 电力 | 约 366 ms | 约 5.2% |
| 建筑生产与采集 | 约 265 ms | 约 3.7% |
| 戴森 | 约 28 ms | 约 0.4% |
| 建筑制造/施工 | 约 4 ms | 约 0.06% |

两次复跑的平均每模拟秒耗时为 115.6–120.4 ms，中位数为 109.7–116.2 ms，P95 为 136.1–145.4 ms，峰值为 242.9–250.3 ms。差异主要来自当时机器的 CPU 调度，不是存档内容变化。物流内部派遣约占总模拟时间 44%–45%；航线推进约占 8%–9%。每次 60 秒实验都发生 126,282 次伙伴匹配调用、102,120 次派遣槽检查和 42,636 条路线创建。

现有自动休眠实验只验证出：实体覆盖约 20.7%、线路覆盖约 19.8%、物流站覆盖约 5.5%，保守预计整体节省 6.4%–9.6%。线路/生产契约实验只有 2 个稳定组件通过验证，97%以上观察组件在验证期唤醒，优化路径反而慢约 1.9%。因此，当前不能把“全工厂自动休眠”作为第一方案。

## 3. 根因判断

### 第一优先级：物流派遣和路线决策

416 座星际物流站和 720 条在途路线让每秒派遣、伙伴匹配、优先级、路线经济和拥堵判断成为绝对热点。运输船和运输机数量很大，但真正的问题不是逐台对象的存档大小，而是每个模拟周期仍要反复处理大量站点槽位和航线关系。

### 第二优先级：高并联传送带

5,746 条带几乎全部为 Mk.III、堆叠 4；其中 2,065 条线路使用 4,096 并联数。单个堆叠数字不等于 4,096 个对象，但线路容量、端点诊断、缓存转移和传送带遍历仍然按线路记录执行，因此传送带阶段占 24%。

### 非首要：普通建筑堆叠和建筑制造中心

样本中没有建筑制造中心实体，建筑制造阶段只有 5.6 ms。普通生产阶段只有 3.4%。即使存在 1 亿堆叠，也主要是数字计算，不是生成 1 亿个建筑对象；本样本的主要瓶颈明显在物流和线路。

## 4. 推荐优化方案和百分比

百分比是基于本存档实测阶段占比推算的工程目标，不是保证值；不同优化存在重叠，不能直接相加。

### P0：先补齐性能观测

- 把派遣、伙伴匹配、路线经济、拥堵、传送带端点查找分别计时。
- 报告当前星球、实体、线路、槽位、在途路线和忙碌载具数量。
- 增加主线程长任务和 React Flow 画布耗时，避免只看 Worker。

预期性能收益：0%–5%，主要价值是避免优化方向错误。

### P1：物流聚合派遣

- 按“物品、来源星球、目标星球、供需策略、优先级”聚合请求。
- 先计算星球级总需求和总供应，再分配到站点，不让每个站点重复扫描全部候选。
- 运输船/运输机只保存舰队总数、忙碌数、总运力、冷却和翘曲器预算；不逐船执行相同决策。
- 只在槽位、库存、优先级、科技、星球解锁或航线状态变化时重建候选缓存。
- 同恒星系和跨恒星系使用不同结算路径，跨星系只在边界结算时扣除翘曲器。

本存档物流阶段预计下降 50%–70%，折算整个模拟约下降 32%–45%。这是最值得优先开发的部分。

### P2：传送带索引和批量转移

- 建立按星球、来源、目标和物品的运行时索引。
- 只对有缓存变化或流量变化的线路执行端点诊断。
- 容量按“等级 × 并联数 × 堆叠”批量结算，禁止按并联数创建临时对象。
- 拆分拓扑变化和流量变化；线路位置不变时不重建路径。

本存档传送带阶段预计下降 30%–50%，折算整个模拟约下降 7%–11%。

### P3：谨慎使用休眠

当前样本的普通契约休眠验证失败率过高，只能针对明确稳定、无物流边界的生产闭环启用。对物流站和跨星球线路不能套用简单周期预测。

当前实测可承诺的整体收益只有 6.4%–9.6%；完成 P1/P2 后重新采样，才可能扩大覆盖范围。

### P4：画布专门优化

- 拓扑快照与流量遥测分离。
- 缩放时使用低细节模式，只显示节点轮廓和线路主干。
- 只渲染当前视口节点和线路，远处线路不创建完整 SVG 交互路径。
- 移动画布期间不让每个 `onMove` 事件触发完整 React 状态更新。
- 拖动对齐检测使用空间索引或节流，不每次遍历全部节点。

这是玩家拖动、移动、缩放的独立收益，不计入 Worker 模拟百分比。目标是主线程长帧下降 40%–60%，画布交互 FPS 提升约 1.5–2 倍。

### P5：存档和保存流水线

- 保存快照由 Save Worker 负责序列化、校验和压缩。
- 主线程只提交一致性快照，不在 UI 线程重复 JSON 序列化和读回校验。
- 实体和传送带数组支持压缩或结构化二进制表示，但必须保留旧 JSON 兼容读取。

本存档预计保存停顿下降 60%–90%，主要改善存档时的瞬时卡顿，不直接降低模拟 CPU。

## 5. 综合目标

推荐对外只承诺一个保守目标：

> **P1 物流聚合 + P2 传送带索引完成后，第一名存档的模拟耗时目标下降 35%–50%。**

按本次复跑的当前基线，平均每模拟秒约 118 ms，换算目标约为 59–77 ms。这里的 35%–50% 是整体模拟目标，不是把物流和传送带两个阶段的百分比直接相加。

同时配套 P4 画布优化后，拖动建筑、移动画布和缩放的主线程卡顿目标下降 40%–60%；P5 完成后，自动保存造成的停顿目标下降 60%–90%。这些百分比分别对应不同链路，不能相加成“总性能提升 150%”。

## 6. 验收和风险

- 每阶段都必须与当前引擎比较状态哈希、库存守恒、在途物资、路线数量和生产统计。
- 至少测试 1x、4x、暂停、离线结算、页面后台、云存档和 22 星球全量切换。
- 物流聚合最容易产生供需分配、优先级和翘曲器消耗回归，必须保留旧逐站路径作为测试 oracle。
- 不应通过删除站点、限制玩家运输船数量、截断库存或强制清理路线来换取百分比。
