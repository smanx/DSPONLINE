## 1. 使用说明与工作区边界

后续开发开始前必须重新执行 `develop-dspidle` Skill 的启动检查，并以实际工作区为唯一基线。本规格审计时工作区已有 Android、Capacitor、Electron、网络传输和移动壳层相关未提交改动，`package.json` 也已被其他任务改为 `0.10.0`。这些改动均属于用户或其他开发任务，不得 reset、checkout、clean、覆盖或顺手整理。

本批目标产品版本固定为 `v1.0`，发布制品、`package.json`、桌面与 Android 版本名最终统一使用 SemVer `1.0.0`。产品版本与存档状态版本彼此独立：若实施时其他任务已经修改 `GameState` 版本，则本文所称“v33 -> v34”必须顺延为“实际最终版本 -> 下一版本”，不得抢占、改写或折叠已有迁移。存档 envelope 和云 schema 只有在其自身协议确实变化时才升级，不能跟随 `GameState` 机械加一。

本批只允许在本地开发和隔离测试环境中工作。未经用户明确要求，不提交、不推送、不部署、不修改生产活动配置，也不得把测试账号、测试贡献或测试存档写入香港、上海正式节点。

## 3. 当前代码审计结论

### 3.1 球壳复制失败

`createDysonLayerTemplate()` 已经正确排除节点、框架、壳面 ID，以及所有建设进度。真正的失败点位于 `src/game/engine.ts` 的 `pasteDysonLayerTemplate()`：当目标恒星系的系统总结构点大于已分配结构点，或系统壳面帆大于已分配帆时，函数直接拒绝粘贴。

该保护最初用于避免 `reconcileDysonPlan()` 把目标系统的历史剩余工程量立刻分配给新副本。已经建设完成但仍在发射火箭的系统会持续积累未分配结构点，因此最容易触发。直接删除判断并不正确，因为新层会立即继承目标系统历史进度，违反“副本从零开工”。

### 3.2 活动巨构无法接传送带

显示层已经为 `galactic_material_exporter` 渲染宇宙矩阵、太阳帆、小型运载火箭和反物质燃料棒四个输入端口，`getAcceptedInputs()` 也返回这四项。但是传送带校验和实际传输最终都调用 `targetConsumes()`，该函数没有活动出口分支，因此四种物资全部被判定为不兼容目标。

同一组活动物品目前在 `FactoryNodes.tsx`、`GamePanels.tsx`、`GalacticActivityPanel.tsx`、`galacticActivity.ts` 和 `engine.ts` 中重复声明，存在只修一处、再次分叉的风险。

另外发现两个与 P0 修复直接相关的时钟问题：

- `runGalacticMaterialExporters()` 在活动开始前或结束后仍可能消费缓存，只是不计入个人活动量；这与既有 `0.9.1` 规格“仅活动窗口内消费”不一致。
- `activityClockMs` 当前按已经乘过 `1x/2x/4x` 的模拟秒数前进，4x 会让活动资格窗口在本地提前四倍结束。时间扭曲上线后该问题会进一步放大。

因此活动传送带修复必须同时分离“模拟时间”和“可信墙钟时间”，不能只给 `targetConsumes()` 加一个条件后结束。

### 3.3 1080p 戴森规划遮挡

`.dyson-planner-workspace` 当前固定使用 `inset: 68px 0 108px`。但游戏字号放大后，实际 `.game-shell` 行高依次增长，200% 时顶部为 100px、底部为 168px，规划工作区会覆盖真实顶栏或施工栏。浏览器缩放还会缩小 CSS 视口高度，使问题更明显。

复制和粘贴按钮位于左侧栏的普通内容流中，左右两栏又各自滚动；按钮可能滚出可视区。当前戴森规划没有显式“保存”按钮，只有全局自动保存和关闭按钮。

### 3.4 功率显示

`src/game/units.ts#formatKilowatts()` 始终输出 `kW`，超过 10,000 后借用数量格式器显示“万 kW”。统计、节点、检查器、资料库、星图和排行榜还有大量直接 `.toFixed()`、`.toLocaleString()` 加 `kW` 的实现。它们必须归并到一个以内部 kW 为输入的格式化入口。

### 3.5 物流塔固定供应源和“50 艘只工作约 20 艘”

`findStationSlotPeer()` 只按路线可用、槽位优先级、航程和实体 ID 排序，未把可用库存、已预留库存、需求端剩余容量、两端可用载具、电力和翘曲器纳入可派遣判断。`dispatchStationScope()` 只尝试排序后的第一个供应候选；该候选库存不足或无法派遣时，不会继续尝试其他有货供应塔。这是固定供应源和船只闲置的主要代码原因。

没有写死的 20 艘并发上限。星际站容量为每层 10 艘，模拟层与 UI 都使用 `10 * machineCount`。实际并发还受以下因素限制：

- 首个供应塔扣除 `minStock` 和在途预留后的可用库存；
- 载具所属塔自己的起送比例；
- 需求槽剩余容量和在途占用；
- 载具所属塔的空闲船数；
- 跨恒星航线每船翘曲消耗；
- 两端及中转站供电；
- 路线完成后状态是否正常释放。

堆叠后的翘曲器容量会增长，但现有自动补充目标默认仍为 50；例如每船消耗 2 个翘曲器时，50 个只能支持约 25 艘同时启航。这是“约 20 艘”观感的另一项高概率来源。不得在没有复现数据时擅自提高旧存档的目标值，应该先把限制原因显示出来。

## 4. 全局不变量

1. 相同初始 `GameState`、相同模拟时间预算和相同墙钟时间预算必须得到相同结果，不读取 `Math.random()`、FPS、设备性能或未持久化墙钟。
2. 玩家可见库存、线路货物、物流预留、在途货物和销毁计数均为非负整数；大累计量使用规范十进制字符串或 BigInt 运算，不能跨过 `Number.MAX_SAFE_INTEGER` 后静默失真。
3. 旧存档中的物资、建筑、线路、手持载荷、施工库存、载具、翘曲器、科研、银河出口和戴森建设进度不得减少。
4. 时间扭曲的硬件执行速度不能反向改变游戏规则。Worker 积压可以让显示落后，但不得按 FPS 自动降低游戏倍率、跳过模拟或吞掉待处理时间。
5. 活动倒计时和活动资格只按服务器校准后的墙钟推进，不受暂停、1x/2x/4x、时间扭曲或 UI 刷新档影响。
6. 全服活动数字继续来自 `/api/public-status` 的模拟曲线。本地交付绝不写入 `globalDelivered`，也不伪装成服务器已确认。
7. 微型黑洞只能删除已经由合法传送带完成转移的物品。无效连接、暂停状态、方向错误或保存失败不得删除来源库存。
8. 新巨构属于 `megastructure`，科技完成不赠送施工件；蓝图只能复制空的新实体，不能复制主控资格、确认状态、销毁统计或运行进度。

## 5. 建议的 v34 状态模型

### 5.1 版本策略

若实施时最终版本仍为 v33，则一次性升到 v34并集中迁移本批所有持久字段。不要为七项需求连续制造多个只存在于开发过程的存档版本。若其他 Agent 已经提交 v34，则本批追加为 v35。

存档 envelope 保持 v2。云服务 SQLite schema 保持 v7，但服务端云存档合法性检查必须接受新的最终 `GameState.version` 和新增字段范围。

### 5.2 戴森层分配起点

在 `DysonLayerState` 增加：

```ts
structureAllocationFloor: number;
shellAllocationFloor: number;
```

二者表示该层可以开始使用的系统累计结构点/壳面帆序号，不是已投入量，也不参与模板复制。旧层迁移为 `0`，从而完整保留当前顺序分配语义。

### 5.3 黑洞端口与传送带端口归属

在 `BeltConnection` 增加可选字段：

```ts
targetPortIndex?: 0 | 1 | 2;
```

它只对需要独立通用输入口的建筑生效。旧线路保持 `undefined`，现有活动出口的四个物品专用口仍可继续由 `itemId` 定位。

在 `FactoryEntity` 增加仅供微型黑洞使用的字段：

```ts
blackHolePaused?: boolean;
blackHoleActivationConfirmed?: boolean;
blackHolePorts?: Array<{
  index: 0 | 1 | 2;
  currentItemId?: ItemId;
  totalDestroyed: DecimalIntegerString;
}>;
```

端口数组始终规范为 3 项。累计销毁量属于实体统计，不进入普通 `inputs`、`outputs` 或 `totalProduced`。

### 5.4 时间扭曲状态

建议在 `GameState` 增加独立状态，而不是把无限整数塞进现有 `SimulationSpeed = 1 | 2 | 4`：

```ts
interface TimeWarpState {
  controllerEntityId: string | null;
  enabled: boolean;
  requestedMultiplier: number;
  effectiveMultiplier: number;
  pendingSimulationSeconds: number;
  pendingWallSeconds: number;
}
```

- 现有 `settings.simulationSpeed` 继续只表示免费 `1x/2x/4x`。
- `requestedMultiplier` 是不低于 5 的安全整数，不使用玩法常量作为上限；输入只受有限数值和 `Number.MAX_SAFE_INTEGER` 的技术校验。
- `effectiveMultiplier` 是最近一次确定性电力结算得到的权威档位，装置禁用时回到普通设置。
- 两项 pending 时间用于在 Worker 尚未提交结果时保存可恢复的时间债务；不得因为关闭页面或自动保存而丢失已经累计的时间。
- 若实现采用有序时间预算队列代替两个累计数，也必须限制队列长度、合并相同比例的相邻项，并保持墙钟/模拟预算顺序。

时间扭曲实体本身只需保存是否可作为主控等最小字段；全局只能有一个 `controllerEntityId`。删除主控时，状态原子回退到普通倍率，不自动让多台装置叠加。

### 5.5 物流公平游标

为需求站增加按作用域和槽位保存的最后成功供应源，例如：

```ts
stationLastSupplyPeerBySlot?: Partial<Record<`${StationLogisticsScope}:${number}`, string>>;
```

它只是公平排序提示，不是库存或路线所有权。候选消失、模式改变或槽位换物品时可以忽略或删除提示，不能因此取消合法在途路线。

## 6. v33 -> v34 迁移规则

1. 接受 v1～v33，并在现有连续加载器末尾输出 v34；不得重写旧迁移步骤。
2. 所有旧戴森层的两个 allocation floor 设为 `0`。迁移后逐层完成量、系统结构点、壳面帆、总火箭、总发射帆和发电量必须与迁移前一致。
3. 旧线路的 `targetPortIndex` 保持未定义，不重排线路，不修改 `nextId`。
4. 新建 `timeWarp` 为禁用、无主控、请求 5x、实际为当前普通倍率、无时间债务。
5. 两座新巨构施工库存默认为 0，两项新科技默认为未完成。即使旧存档已完成宇宙矩阵，也只解锁研究前置，不补发建筑。
6. 旧实体不添加黑洞统计。加载微型黑洞实体时才规范为暂停、未确认、三个零计数端口。
7. 物流公平游标缺失时为空；现有 `stationDispatchCursor`、槽配置、载具、翘曲器、预留和在途路线原样保留。
8. v33 的活动 ID、个人交付、pending 批次序号、银河出口等级、累计交付和银河信用逐字段保留，不重新初始化活动。
9. `simulationSpeed` 的旧值 1/2/4 原样保留，不能因为新装置把旧档默认切到更高倍率。
10. 重复迁移必须幂等；导入、主存档、三个手动槽、快照和云存档使用同一迁移结果。

迁移 fixture 至少覆盖：建设完成且有多余火箭的戴森系统、建设中层、四类活动 pending、50 艘在途物流船、堆叠站、超额建筑缓存、手持载荷、递归制造 WIP 和非默认 4x 设置。

## 7. 需求一：修复戴森球球壳复制

### 7.1 分配算法

结构点按层顺序分配，但每层先应用自己的最低累计起点：

```ts
let cursor = 0;
for (const layer of plan.layers) {
  cursor = Math.max(cursor, layer.structureAllocationFloor);
  const required = getLayerRequiredStructure(layer);
  const allocated = clamp(plan.structurePoints - cursor, 0, required);
  distributeWithinLayer(layer, allocated);
  cursor += required;
}
```

普通新建空白层或标准层的 floor 为 `0`，继续允许当前历史余量按原规则进入普通设计。粘贴副本时，两个 floor 分别设为粘贴瞬间目标系统的 `plan.structurePoints` 和 `plan.shellSails`。这样副本不会使用粘贴前的工程量，但粘贴后新发射的火箭和新吸附的帆可以继续建设。

壳面帆使用同样的绝对累计起点。未完成边界框架的壳面继续为 0；当前层激活后允许重新按既有顺序分配，但任何数值不得越过该层的 `shellAllocationFloor`。

### 7.2 复制与粘贴

- 删除当前“目标存在未分配工程量就拒绝”的条件，改用 allocation floor 隔离历史量。
- 模板仍只包含名称建议、半径、倾角、升交点、节点角度、框架拓扑和壳面边界拓扑。
- 粘贴仍追加新层，不覆盖目标层；8 层上限、科技、半径、节点数、角度间距和引用闭合校验保持。
- layer、node、frame、shell 全部使用新 `nextId`，任一失败时 state 和 `nextId` 不变。
- 粘贴前后目标系统总结构点、总壳面帆、火箭数、在轨帆、发电量和材料库存完全相同。
- 第一个粘贴后的新火箭只能推动副本或排在它之前的未完成设计，不能重新解释为历史投入。

### 7.3 回归矩阵

- 空白源层、建设中源层、已完成源层；三者均可复制。
- 源系统仍持续发射且存在多余结构点时可复制。
- 目标为空系统、建设中系统、已完成且有余量的系统。
- 同恒星系粘贴和跨恒星系粘贴。
- 有壳面/无壳面科技、8 层上限、非法模板、重复引用。
- 复制后所有完成量为 0，所有 ID 唯一，源层不变。
- 保存重载和离线推进后 floor 不丢失，未来建设顺序一致。

## 8. 需求二：P0 活动巨构传送带输入

### 8.1 单一物品目录

在领域层导出唯一常量：

```ts
export const ACTIVITY_MATERIAL_IDS = [
  "universe_matrix",
  "solar_sail",
  "small_carrier_rocket",
  "antimatter_fuel_rod",
] as const;
```

同时集中 `ActivityMaterialId -> GalacticExportProjectId` 映射。节点、检查器、活动面板、连接校验、实际传输和结算全部引用该目录，删除组件内重复数组。

### 8.2 连接与传输

- `targetConsumes()` 对 `galactic_material_exporter` 仅接受四项活动物资。
- `getBeltConnectionCheck()` 对错误物品返回“超大型物资出口仅接收宇宙矩阵、太阳帆、小型运载火箭和反物质燃料棒”，不能返回泛化配方错误。
- 活动出口只有输入口，没有输出口；从输入口向外拉线明确提示“物资出口端口只能作为输入”。
- 四个专用口由物品 ID 自动匹配，不覆盖其他口，不要求设备配方。
- 传送带到达后先写实体输入缓存，再在同一确定性模拟提交中结算；暂停或非活动窗口时缓存保留且来源后续停带，不能吞物资。
- 活动窗口内且有电时，整数交付必须原子更新旧银河出口项目、银河信用、个人交付和对应本地 pending 批次。
- 本地交付不会修改服务端状态对象或全服模拟曲线。界面刷新后全服数据继续按服务器时间自然变化。

### 8.3 墙钟与模拟时间分离

实时 Worker 请求必须携带两项预算：

```ts
{
  simulationSeconds: realSeconds * effectiveMultiplier,
  wallSeconds: realSeconds,
}
```

离线请求使用 `simulationSeconds === wallSeconds === realOfflineSeconds`。活动边界按 `wallSeconds` 切分模拟步骤：若一个请求跨过开始或结束时刻，只允许边界内对应比例的模拟产出计入个人活动。`simulateStep()` 不再用模拟秒直接增加 `activityClockMs`。

客户端每 60 秒取得的新服务器时间只能使可信活动时钟单调前进；不接受旧响应回拨，也不能让本地已经错误超前的旧逻辑永久锁死。迁移或首次同步应以服务器锚点和保存时间构造可审计的单调值。

- 四条线路同时输入，个人量、旧出口量、银河信用和四项 pending 均正确。

最终制造成本：

| --- | ---: | ---: |

### 11.2 无玩法上限的十倍功耗曲线

内部功率仍以 kW 计算：

```ts
log10RequiredKw(multiplier) = multiplier + 1;
requiredKw(multiplier) = 100_000 * 10 ** (multiplier - 4);
```

| 实际倍率 | 需求功率 |
| ---: | ---: |
| 4x | 100 MW |
| 5x | 1 GW |
| 6x | 10 GW |
| 7x | 100 GW |
| 8x | 1 TW |
| 9x | 10 TW |
| 10x | 100 TW |
| 11x | 1 PW |
| 12x | 10 PW |
| 13x | 100 PW |

不得定义 `MAX_TIME_WARP_MULTIPLIER = 6` 一类玩法上限。对于无法安全转成 JS Number 的极端请求，使用对数比较判定其必然不可供电，不执行 `10 ** n` 得到 `Infinity` 后再参与电网运算。请求值必须是有限安全整数；这属于数据格式保护，不是平衡上限。

### 11.3 电力与主控语义

- 一座实体不能通过 `+1`、批量放置或蓝图堆到 `machineCount > 1`。
- 可以制造和放置多座，但只有 `controllerEntityId` 对应的一座生效；其他装置显示“非主控”，耗电为 0，倍率不叠加。
- 主控只从自身所在行星和电网取电，效果作用于全存档模拟。切换行星不改变主控。
- 主控作为最低优先级的剩余电力消费者，在普通生产、物流、科研和其他低优先级设备完成预算后使用剩余可调度容量，避免倍率装置导致工厂自我断电并产生档位振荡。
- 蓄电器和能量枢纽属于该电网的可调度容量，允许被主控消耗；界面必须明确提示可能快速放空储能。
- 从请求倍率向下计算最高可完整供电档。若 6x 请求只能支持 5x，则实际为 5x、耗电 1 GW；供电恢复后自动回到 6x。
- 若连 100 MW 都不能完整供应，实际仍回到普通 4x，主控显示供电不足并只获得电网实际分配量。暂停主控后 4x 不再产生 100 MW 负载。
- 请求倍率不因降档被改写，避免电力短暂波动后需要玩家重新设置。

档位解析必须先排除主控自身需求，计算普通负载后的剩余可调度电力，再选择档位并进行最终电力分配。不能用上一帧 `powerFactor` 直接乘档，也不能在同一步内反复 6x/5x 抖动。

### 11.4 时间预算与性能安全

当前 `App.tsx` 在提交 Worker 前直接把真实秒乘以 `settings.simulationSpeed`。本批应抽出统一的时间预算层，让 Worker、主线程回退和离线 Worker 明确区分模拟秒与墙钟秒。

- 普通实时：`simulationSeconds = wallSeconds * 1/2/4`。
- 时间扭曲实时：`simulationSeconds = wallSeconds * effectiveMultiplier`。
- 离线：`simulationSeconds = wallSeconds`，不乘普通或扭曲倍率。
- 活动时钟、倒计时和资格只消费 `wallSeconds`。
- 所有模拟时间债务按顺序进入 Worker；不能因为新请求覆盖旧请求。
- 自动保存、切后台和退出时保存尚未处理的时间预算；Worker 结果提交后原子扣除，重载只能补算一次。
- 主线程回退必须使用分片和可取消调度，不能在极端倍率下同步执行一个无界循环冻结 UI。
- 不允许根据 FPS、Worker 延迟或设备型号改变有效倍率；硬件只影响追赶速度。积压时显示“模拟处理中”和待处理模拟时间。

### 11.5 控件与状态

无上限档位不能使用列出全部值的 segmented control。使用固定尺寸的数值步进器：减 1、当前请求值、加 1，并提供“设为当前最高稳定档”命令。所有图标有 tooltip，输入非法值不写存档。

节点和检查器至少显示：主控/非主控、启用状态、请求倍率、实际倍率、需求功率、实际分配功率、所在电网、距离下一档所需功率、待处理模拟时间和离线不加速说明。

### 11.6 测试与发布门禁

- 4～13x 功率表逐项精确；极端请求不产生 Infinity/NaN。
- 供电边界前 1 kW、恰好达到、超过阈值；自动降档和恢复。

## 13. 需求七：物流塔与运输船调度

### 13.1 候选列表而非单候选

把 `findStationSlotPeer()` 拆为：

1. 从会话索引取得稳定的静态候选列表；
2. 为每个候选计算动态可派遣快照；
3. 返回有序候选，而不是只返回第一个；
4. `dispatchStationScope()` 依次尝试，直到需求容量、供应库存或两端空闲载具耗尽。

动态快照至少包含：

- `available = supply.outputs - supplySlot.minStock - reservedOutgoing`；
- `free = demandCapacity - demand.outputs - inFlightCargo`；
- 需求塔和供应塔各自的空闲载具；
- 载具所属槽自己的 `minimumLoad`；
- 路线策略、作用域、路线可用性和预计航程；
- 载具所属塔的翘曲开关、库存和每船消耗；
- 两端与中转站供电；
- 当前供应塔已经承担的预留和活动航线。

第一个候选不能派遣时必须继续下一个。第一个候选只能满足部分载具时，先创建准确预留，再继续从后续供应塔补足，不能把剩余船闲置到下一轮。

### 13.2 优先级和公平性

候选排序按以下语义：

1. 路线必须合法且可达；
2. 供应槽优先级高于低优先级；
3. 同优先级优先选择当前预留/执行负载更低的供应塔；
4. 使用需求槽持久化的最后供应源做 round-robin，成功后移动游标；
5. 航程和实体 ID 只作为最后的确定性 tie-breaker。

低优先级供应塔不能在高优先级塔仍可派遣时抢占任务；同优先级塔不能因 ID 较小永久独占。供应塔派自己的载具时读取供应槽起送比例，需求塔派自己的载具时读取需求槽比例，继续保留当前 owner 语义。

### 13.3 索引与缓存

- 延续按 scope、位置、物品、模式建立的 `stationSlotsByKey`，不得恢复每塔扫描所有实体。
- `busyVehicles`、`reservedOutgoing`、`inFlightCargo` 和 `activeRoutesByStation` 在创建路线后立即更新。
- 路线经济缓存只在一次 `SimulationAdvanceSession` 内存在，key 包含供需塔、路线策略、翘曲预算和载具数。
- 动态库存、电力、空闲船和翘曲器不能缓存为跨步骤陈旧结果。
- 闲置载具不创建逐船对象，也不产生与数量线性相关的空循环；路线继续按 `vehicleCount` 批量结算。

### 13.4 舰队诊断 UI

新增共享 selector，例如 `getStationFleetDiagnostic()`，桌面和移动检查器共用。运输机和运输船分别显示：

- 已安装总数；
- 泊位容量；
- 执行中数量；
- 当前可用数量；
- 有空闲但不能出发的数量；
- 主阻塞原因和受影响槽位。

阻塞原因至少区分：无匹配供应/需求、供应库存低于起送量、需求库存已满、全部载具忙、供电不足、翘曲关闭、翘曲器不足、路线/中转不可达。翘曲不足应显示类似“50 艘已安装，25 艘受 50 个翘曲器/2 个每船限制”，而不是让玩家推测存在 20 艘上限。

本批不自动改写旧站的 `stationWarperTarget`。如果实测证明默认 50 是主要限制，先通过诊断暴露并允许玩家调整；是否让新堆叠层自动扩充目标应作为独立平衡改动，不夹带在调度修复中。

### 13.5 物流测试

- 三个同物品供应塔：首塔缺货、低于保留、只能满足 20 艘、断电、缺翘曲器、路线不可达时逐一切换。
- 三个同优先级且都有货的供应塔长期 round-robin，无 ID 永久独占。
- 高/中/低优先级严格生效，高优先级耗尽后回退。
- 需求塔 50 艘、供应塔 50 艘同时可派遣，owner、最低装载、预留、翘曲扣除和返航准确。
- 堆叠 1/2/5 层分别验证 10/20/50 艘，模拟与 UI 一致，不存在写死 20。
- 取消路线、回收任一塔、改槽、降堆和离线完成路线均不复制或吞物资/翘曲器。
- 10/50/100/500 塔保留旧扫描对照模式，最终状态哈希一致，并记录候选检查数、经济计算数、中位数和 P95。

## 14. 内容、蓝图与交互闭环

两座新巨构必须闭合以下目录和入口：

- `ItemId/BuildingId/ConstructionId/TechId` 类型；
- `BUILDINGS`、`CONSTRUCTION`、`TECHNOLOGIES`；
- 初始施工库存的零值和迁移归一化；
- 施工托盘、建筑制造中心、递归小锤子、搜索、分类和最近使用；
- 桌面节点、经典手机、新版手机、检查器和生产资料库；
- 内容审计、progression audit、科技前置和“巨构不赠送”测试；
- 自动布局尺寸、端口几何、蓝图捕获/粘贴和回收规则；
- 生产管理和批量改配方不得把无配方巨构当普通生产机。

蓝图复制微型黑洞时只复制建筑类型和位置；新实体暂停、未确认、三口计数为 0。时间扭曲蓝图实体不成为主控、不继承请求倍率。活动出口行为不因新增通用端口模型而改变。

### 17.2 必须新增的领域测试

- 戴森：空白/建设中/完成/历史余量、跨系、未来投入、ID 和发电不变。
- 活动：四种传送带、暂停、错误物品/方向、活动边界、墙钟与高倍率分离。
- 黑洞：三端口、全部物品类别、精确大计数、默认暂停、确认、离线。
- 时间扭曲：无玩法上限的对数功率、自动降档、多台不叠加、全局范围、时间债务。
- 功率格式：全部阈值、舍入晋级、TW/PW、科学计数、负数和非法值。
- 物流：多供应源失败转移、公平轮换、50 船、双端 owner、预留和返航。
- 迁移：v33 复杂存档到最终版本，逐字段保护库存、线路、路线、科研、戴森和活动。

### 17.3 确定性与离线

- 同一状态分别用单次、1 秒分片和 Worker 分片推进，比较完整状态哈希。
- 1 小时、8 小时、9 小时、24 小时、7 天、30 天离线保持与同步路径等价。
- 黑洞销毁、物流路线和活动贡献同时存在时仍等价。
- 4/5/6/8/10x 前台以相同墙钟预算运行；活动时钟相同，模拟产出按有效倍率变化。
- 保存时有 Worker 在途任务和时间债务，重载后既不丢时间也不重复计算。

- 桌面：1920x1080、1536x864、1280x720、960x540。
