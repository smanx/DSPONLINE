# 闭合产线与整颗行星结算合同实验报告（2026-07-31）

## 最终结论

本次已经实际制作并运行了两种只读原型：

1. **严格确定性闭合产线合同**：按“入带、生产、出带”三个真实模拟阶段学习和重放，实际跳过对应生产建筑与传送带循环，最后比较完整 GameState 哈希。
2. **整颗行星净流量影子合同**：物流站和在途航线继续精确运行，只观察行星内部工厂向物流站边界的 60 秒净吞吐是否稳定。

对用户终局存档的结论是：

- **严格、无损、保持状态哈希一致的自动封存，实际性能提升约为 0%。**
- 160 个拓扑候选中，完整观察 60 秒后有 154 个可以建立轨迹；再运行 60 秒，152 个需要自动解封，只有 2 个继续成立。
- 最终只能封存 8 个生产实体和 29 条线路，分别只占可合同化生产实体的 0.65% 和全部线路的 0.50%。
- 300 秒同进程 A/B 中，精确基线为 57,833.467 ms，合同版为 57,856.323 ms；合同版慢 0.04%，属于测量噪声。两者完整状态哈希一致。
- 22 颗有实体的行星都存在物流站或供电设施，样本共有 416 座物流站和 720 条活动航线；不存在可以与全局物流、电力和科研完全隔离的整颗行星。

因此，不能把“稳定 60 秒后自动封存”作为当前版本的透明性能优化上线。对于这份真实终局工厂，它几乎没有无损收益。

- 活动物流航线：720 条。
- 有实体的行星：22 颗。

- 实验结束后原始状态哈希未改变。

## 严格闭合产线原型

### 工作方式

原型不是简单暂停建筑，而是按引擎真实顺序处理：

1. 物流缓存先按原规则结算。
2. 合同接管符合条件的入向传送带阶段。
3. 电力仍按完整实体状态精确计算。
4. 合同接管普通采集和生产阶段；科研、戴森、建筑制造、发电和特殊建筑继续精确运行。
5. 合同接管出向传送带阶段。
6. 物流派遣、载具航行、拥堵和翘曲器继续走精确模拟。

物流站不作为普通图节点，而是按“物品 + 输入/输出方向”拆成边界，避免一条特殊支线让整颗星球的其他产线失去资格。合同只存在于运行时，不进入 GameState 或存档。

### 稳定性结果

| 指标 | 结果 |
| --- | ---: |
| 拓扑候选组件 | 160 |
| 60 秒内没有结构变化 | 154 |
| 下一分钟仍能重放 | 2 |
| 下一分钟自动解封 | 152 |
| 自动解封率 | 98.70% |
| 最终生产实体 | 8 |
| 最终线路 | 29 |

绝大多数失败并不是玩家修改了工厂，而是物流到达、缓存跨阈值、线路信用、供电分配和生产余数使下一分钟的内部轨迹发生变化。终局工厂的长期平均产量可以接近稳定，但它的逐步状态不是静止或短周期重复。

### 实际 A/B

300 个模拟秒的同进程结果：

| 项目 | 精确模拟 | 合同模拟 |
| --- | ---: | ---: |
| 总耗时 | 57,833.467 ms | 57,856.323 ms |
| 平均单步 | 192.778 ms | 192.854 ms |
| P95 | 200.073 ms | 197.764 ms |
| 合同重放开销 | 0 | 14.145 ms |
| 完整状态哈希 | 基准 | 一致 |

耗时变化为 **-0.04%**，即没有可测得的性能提升。短跑中曾测到约 2% 波动，但覆盖率没有变化，300 秒长跑更可信，因此报告按 0% 处理。

## 整颗行星净流量实验

### 为什么另做这个实验

整条产线内部可以不断搬运，真正需要外部世界知道的只是它向物流站送入或取出的物资。第二个原型不要求每台建筑的进度完全重复，而是比较每个 60 秒窗口内，连接物流站的传送带按物品和方向统计的累计吞吐。

为了排除载入后的重新调度，实验又精确预热了 600 秒，再观察后续连续 6 个一分钟窗口。

### 无损结果

- 有 7 颗行星的站点边界流量完全不变，但这些行星没有可覆盖的生产实体或传送带，实际节省仍为 0。
- 没有一颗包含有效工厂负载的行星能在所有物品上保持完全一致。
- 完整物资聚合、内部库存和物流站实际库存也没有行星通过严格一致性检查。

这说明预热十分钟并不能让该终局工厂进入可无损封存的静态状态。

## 如果允许算错一点，最多能快多少

下面是“允许每种边界吞吐存在误差”的影子估算。它没有提交近似状态，不能视为正确模拟结果。

| 允许误差 | 行星数 | 生产覆盖 | 线路覆盖 | 预计总耗时下降 |
| --- | ---: | ---: | ---: | ---: |
| 1% | 7 | 0% | 0% | 0% |
| 5% | 13 | 39.97% | 40.74% | 8.47%～10.59% |
| 10% | 17 | 67.82% | 69.63% | 14.46%～18.08% |
| 25% | 22 | 100% | 100% | 20.84%～26.05% |

这张表不能作为上线承诺：

- 5% 误差会直接改变单项物资的实际产量、消耗、库存满载时刻和物流派遣时刻。
- 误差会随长时间挂机和离线结算累积，不一定正负抵消。
- 科研、戴森、燃料、矿脉消耗和排行榜状态会出现不同哈希。
- 刷新或切换设备后，精确模拟与近似合同可能得到不同工厂状态。

因此即使 5% 档能理论节省约 10%，也不符合本项目的确定性和物资守恒要求。

## 性能上限

当前样本的干净 360 秒基准中：

- 生产约占总模拟时间 3%～4%。
- 传送带约占 22%～23%。
- 物流约占 65%～66%。
- 电力约占 4%～5%。

如果假设所有本地生产和传送带都可以零成本封存，但物流站与航线仍精确运行，理论最大耗时下降只有 **约 25.7%～26.0%**。实际合同还要执行边界结算和唤醒守卫，因此一定低于这个上限。

要超过 30%，必须把物流伙伴匹配、派遣、载具到达和缓存阈值一起改造成关键事件系统。这已经不是简单的“封存建筑”，而是一套新的确定性事件模拟器。

## 为什么不能自动持续提供产出

“持续提供产出”同时意味着：

- 持续扣除所有输入和燃料。
- 持续占用电力并响应供电变化。
- 持续消耗矿脉储量和增产剂。
- 输出满时立即停机，空出后恢复。
- 物流船到达、科技完成、路线改变时在准确时刻改变速率。
- 保存、重载、离线和时间扭曲后得到相同整数库存。

只记录过去一分钟的平均产量无法满足这些条件。要无损实现，合同必须计算“下一个输入耗尽、输出满、船到达、燃料耗尽、科技完成或供电变化”的精确时间，并在事件点解封或重建合同。

## 建议

### 不建议上线

不建议开发当前形式的“60 秒自动封存建筑/行星”。严格版本收益约 0%，近似版本会开倒车，牺牲玩家真实产量、跨端一致性和排行榜可信度。

### 更值得做的方向

1. **继续优化物流派遣热路径**：物流约占 65%，仍是最大收益来源。
2. **离线专用关键事件快进**：只在离线 Worker 内跨越库存、路线和科研事件，无法证明时自动回退精确模拟。
3. **零工作量快速跳过**：对明确断电、缺料、满缓存、无路线的对象使用脏标记和早退出，不预测产量，也不改变状态。
4. **线路与站点分层更新**：稳定拓扑缓存继续保留，只重算发生库存阈值或配置变化的槽位。
5. **视觉封存可以独立实施**：屏幕外行星停止 React/Canvas 动画和状态发布，但 Worker 模拟仍保持精确；这能改善前台体验而不改变玩法。

若未来仍要做事件合同，建议设置硬门槛：真实样本完整状态哈希一致，且同机 300 秒 A/B 至少降低 30% 耗时，否则不进入正式版本。
