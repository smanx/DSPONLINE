# 性能优化阶段报告（2026-07-30）

## 先看结论

性能基础版先作为 `1.0.10-41cbf7ccb07e` 发布，P2 物流、燃料/蓄电和复杂递归制造批量结算随后作为 `1.0.11-f88462df5326` 发布到香港、上海及 Windows/Android 稳定通道。1.0.11 同时加入排行榜数据完整性服务端保护；两阶段都保持 GameState v40、存档 envelope v2、云 schema v7 和 SQLite layout v2 不变。

| 合成档 | 规模（实体 / 线路 / 物流站） | 旧路径 | 新索引路径 | 模拟阶段耗时下降 | 状态哈希 |
| --- | ---: | ---: | ---: | ---: | --- |
| P50 | 300 / 300 / 45 | 103.3 ms | 33.1 ms | 67.9% | 一致 |
| P95 | 380 / 500 / 80 | 328.7 ms | 131.2 ms | 60.1% | 一致 |
| Max | 569 / 1,160 / 128 | 803.1 ms | 256.7 ms | 68.0% | 一致 |

“状态哈希一致”表示生产、库存、线路、物流路线、供电、科研和戴森等持久状态没有因为优化而改变。状态 JSON 大小也保持不变：P50 约 334 KiB，P95 约 474 KiB，Max 约 790 KiB。

## 1.0.11 正式版结果

物流基准在同一台开发机上执行 3 次预热和 10 次正式采样，每次推进 3 个模拟秒。下表中的“旧路径”是保留的 legacy oracle，“P2 路径”包含 1.0.10 索引、稳定候选缓存和派遣结果复用：

| 物流站 | 旧路径中位 / P95 | P2 中位 / P95 | 中位耗时下降 | 状态哈希 |
| ---: | ---: | ---: | ---: | --- |
| 10 | 1.77 / 3.10 ms | 1.10 / 2.13 ms | 37.9% | 一致 |
| 50 | 23.65 / 30.60 ms | 9.80 / 10.92 ms | 58.6% | 一致 |
| 100 | 104.32 / 109.25 ms | 44.59 / 47.48 ms | 57.3% | 一致 |
| 128 | 165.50 / 171.66 ms | 61.12 / 66.52 ms | 63.1% | 一致 |
| 300 | 1,160.84 / 1,174.87 ms | 423.26 / 438.35 ms | 63.5% | 一致 |
| 500 | 3,908.47 / 3,941.67 ms | 1,342.18 / 1,388.64 ms | 65.7% | 一致 |

相对已经发布的 1.0.10 P1 路径，而不是相对最慢的 legacy 路径，50、100、500 站的中位耗时又分别下降约 20.2%、13.6%、14.9%。500 站候选检查从 562,560 次降到 105,480 次，下降 81.3%；路线经济调用保持 78,375 次，派遣阶段从约 1,325.17 ms 降到 1,245.11 ms，说明下一轮仍有路线排序和调度成本可优化。

燃料、能量枢纽和制造中心不再按每件物品或每个成品循环。聚焦测试中，500 万个蓄电单元和 50,000 个直接制造任务约 2 ms；10,000 个含副产物递归任务只建立 1 份计划，制造阶段约 6.6 ms、整步约 11.3 ms。复杂高级配方、多目标和多制造中心的新旧完整状态一致。

匿名终局夹具在同一台开发机的单次预热后采样结果如下；“玩家同形”约等于用户样本的对象数量与并联规模，“2 倍终局”是明确的超额压力档，不包含玩家存档正文：

| 夹具 | 规模（实体 / 线路 / 物流站 / 并联） | 1x | 4x | 11x | 与 legacy 哈希 |
| --- | ---: | ---: | ---: | ---: | --- |
| 玩家同形 | 600 / 1,250 / 100 / 150 万 | 34 ms | 58 ms | 116 ms | 一致 |
| 2 倍终局 | 1,200 / 2,500 / 256 / 300 万 | 278 ms | 401 ms | 745 ms | 一致 |

2 倍终局首次 1x 的约 278 ms 中，首次伙伴/路线经济缓存约占 227 ms；4x 和 11x 均低于 500/900 ms 预算且没有未完成模拟债务。该结果不能替代手机真机 FPS、温度或耗电测试。

## 做了什么

- 模拟会话只建立一次实体 ID、按行星实体、电网电源、线路端点和物流槽候选索引。
- P2 在同一会话内缓存不随库存变化的物流匹配结果；拥堵统计直接读取本步派遣结果，不再重新寻找站点伙伴。
- 燃料和蓄电交换使用闭式批量计算；建筑制造中心把完整递归计划编译为确定性事务。单一稳定目标可跨成品批量结算，多目标和多中心按原轮询快速提交单份事务，已有部分 WIP 保留旧逐步语义。
- 供电、采矿、生产、施工、射线接收、线路转运和线路容量预留复用这些运行时索引；没有把索引写入 `GameState` 或存档。
- 物流路径继续保留 legacy 全扫描 oracle。每档基准都跑旧路径和新路径，再逐状态计算哈希。
- 画布先得到当前行星的实体、线路和实体 ID Map，让端口占用、并联线路分组、任务高亮、节点和边不再为当前页面重复扫描其他星球。
- `performanceFixtures.ts` 的压力状态完全由项目公开目录和固定参数生成，不包含账号、坐标快照、昵称、token 或玩家存档正文。

## 对普通玩家意味着什么

预计受益最大的是后期多星球、多物流站工厂：模拟 Worker 更少排队，物流站多时单次推进更快，画布切换星球时少做无关扫描。新增索引只在模拟会话开始时构建一次，因此小工厂不会产生可见玩法变化。

目前没有证据证明真实手机 FPS 已提高多少。Node 合成夹具不能替代 Chrome、Android WebView、iPhone Safari 或 360 浏览器的端到端测量；真实 FPS、温度、耗电和 JS 堆趋势仍需要独立设备测试。

## 牺牲了什么

- 每次模拟会话会增加一小段索引构建时间和临时内存。当前 Max 夹具索引构建约 0.6 ms，低于省下的物流和供电时间，但低端设备仍需观察 GC 峰值。
- P2 额外保留会话级物流匹配缓存和本步派遣摘要，临时内存会随已配置物流槽数量增长；它们不会进入存档或云同步。
- 运行时保留了 legacy 路径作为回归 oracle，因此代码和测试体积略有增加；这不是玩家存档数据。
- 计划与物流缓存会增加少量会话级临时内存；2 倍终局首次跨星球伙伴匹配仍会出现约 278 ms 的一次性 Worker 长任务，尚未达到 250 ms 理想线。
- 画布只优化了当前行星派生，线路诊断、完整视口裁剪和 React Flow 拓扑缓存尚未完成，极大线路网络仍可能有长帧。
- 本批没有把 Worker 改成权威状态，也没有移动保存序列化；时间扭曲、自动保存和离线结算的复制开销仍存在。

没有牺牲：产量、生产速度、物流规则、科研进度、戴森进度、离线收益、库存守恒、线路在途物资、存档格式或云存档兼容性。没有强制降低并联数、堆叠数、星球数或刷新频率。

## 尚未确认的风险

1. 尚未在真实 Chrome、360、Android 和 iPhone 上连续运行 30 分钟并采集强制 GC 后活跃堆。
2. 尚未测量主线程 FPS、React Flow 长帧、保存耗时和设备温度，因此不能承诺固定百分比的用户端收益。

## 回滚方式

1.0.11 不升级 `GameState`、envelope、云 schema 或数据库 layout，也不需要迁移旧存档。当前线上是 `1.0.11-f88462df5326`，两地代码与上海下载站回滚点均为 1.0.10。代码回滚只切换发布目录，不恢复数据库；香港排行榜内部限制继续保留。legacy 模拟路径继续作为测试 oracle。
