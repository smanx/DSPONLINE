# 公开测试版后续路线图

## 决策原则

首个版本已经上线。下一阶段应从“继续增加功能”切换到“让现有版本能被可靠发布、长期保存、诊断和恢复”。下面按依赖顺序安排，不把尚未实现的内容写入项目现状。

## 阶段 A：冻结并标记首个线上基线

目标：任何人都能从一个 Git 提交重建当前线上版本。

- 整理当前脏工作树，按功能审阅后提交，不删除现有用户或代理留下的有效改动。
- 设定首个公开测试 SemVer，统一 `package.json`、桌面安装包、构建 ID 和 Git 标签。
- 保存前端/后端发布清单、依赖锁文件和部署时间。
- 将本文档与 `develop-dspidle` Skill 作为后续任务的强制入口。
- 建立简短发布说明和已知问题列表。

完成标准：在空目录 `git clone` 后可用锁文件通过测试并生成与发布清单一致的产物。

## 阶段 B：生产数据与安全加固

目标：即使错误发布、磁盘故障或账号攻击发生，也不会丢失玩家存档。

- 将 `/api/metrics` 改为内网、管理员 token 或监控专用入口。
- 异地加密备份、状态记录和每月隔离恢复演练工具已落地；剩余双 VPS 密钥安装、timer 启用和首份真实演练报告。
- 账号与云恢复安全审计、磁盘/TLS/端点探针和可选告警 webhook 已落地；剩余生产告警接收端与日志集中化。
- 邮箱验证、忘记/重置/修改密码、会话撤销、数据导出和账号删除已在 schema v5 工作区落地；剩余邮件供应商配置、异常登录告警和后台处置。
- 补充隐私政策、用户协议、数据导出/删除说明。
- 对反馈和错误上报加入垃圾内容限制与管理查看工具。

完成标准：有书面恢复记录；一次全新主机恢复演练可以还原账号和云存档，并验证修订历史。

## 阶段 C：Web 性能与可观测性

目标：大陆玩家稳定快速进入主菜单，问题发生时能够定位。

- 为 JS、CSS、JSON、SVG 配置 gzip 或 Brotli，验证 `Content-Encoding`。
- 继续拆分首屏 chunk，审计 300 KB 以上资源和重复预加载。
- 建立外部 HTTPS、TLS、API 和静态资源探测。
- 建立前端错误、服务端错误率、P95 延迟、429、云冲突和备份状态看板。
- 为 service worker 设计可追踪版本和失败回退，避免旧资源组合。
- 基于真实访问量评估优选流量包，而不是一次性购买大额流量。

完成标准：记录压缩前后传输量；连续一周可用性和错误率有趋势数据与告警。

## 阶段 D：账号、云存档与排行榜正式化

目标：把当前可用原型升级为可运营系统。

- 本地身份已可显式绑定、换绑或解除云账号，绑定元数据不进入 `GameState`；后续补充首次绑定引导。
- 云冲突界面已支持比较本地/云端时间、运行进度、设备和科技摘要，并明确选择保留方向；后续补跨设备推送提醒。
- 设计赛季结算、封榜、历史榜、昵称治理和管理员撤榜。
- 将关键成绩验证逐步迁移到服务端可重放摘要或权威事件，而非只检查客户端总量。
- 用户规模增长后将单行 JSON SQLite 模型迁移为用户、会话、存档修订、榜单和事件表。

完成标准：多设备冲突和历史恢复有端到端测试；排行榜提交可以追溯到明确云存档和验证版本。

## 阶段 E：稳定性与架构治理

目标：降低改一处坏多处的成本。

- 拆分 `App.tsx` 的模拟会话、画布命令、存档、工作区和输入控制。
- 拆分 `engine.ts` 的电力、物流、科研、戴森和实体命令，保留一个确定性推进入口。
- 将 `styles.css` 拆为有顺序约束的 shell、canvas、workspace 和 responsive 层。
- 按领域分拆 E2E，建立存档 fixture 和少量视觉回归。
- 给内容目录增加生成式 ID/引用检查，减少手工联合类型和目录不一致。

完成标准：核心大文件显著缩小；每个领域有明确所有权和针对性测试，完整回归时长可控。

## 阶段 F：体验与平衡第二轮

目标：让玩家理解瓶颈并愿意长期挂机，而不是只看到系统数量。

- 使用真实玩家存档运行 2/8/24/72 小时平衡审计。
- 调整手搓过渡、科技卡点、电力曲线、物流吞吐和离线回归奖励。
- 完善新手任务到红糖、跨星球和白糖的渐进教学。
- 加强缺料警报到设备、线路和聚焦配方的直接导航。
- 继续优化手机连线、批量操作、抽屉和横竖屏切换手感。

完成标准：新存档从开局到白糖有可重复的通关时间报告；关键卡点来自设计而不是 UI 不可发现。

## 阶段 G：原创化与正式公测

目标：形成可以独立推广的产品身份。

- 审查物品名称、配方、科技树、文案、图标、世界观和产品名称。
- 设计原创资源生态、行星特性和生产策略差异，但暂不引入黑雾战斗。
- 建立原创视觉资产与声音规范，替换仅用于高还原验证的内容。
- 在商业化或大规模推广前获取知识产权与商标方面的专业意见。
- 完成反馈入口、公开问题追踪、版本更新说明和社区运营规则。

完成标准：产品不依赖玩家对另一款游戏的名称记忆也能理解和传播，内容权属与发布材料清晰。

## 当前推荐的下一迭代

优先执行阶段 A、B、C 的最小闭环：

1. 提交和标记当前线上基线。
2. 保护监控端点并做一次可验证的异地恢复。
3. 启用静态压缩和外部可用性监控。
4. 再进入账号正式化或新玩法开发。

这条顺序能直接降低“有玩家之后发布出错或存档丢失”的最高风险。
