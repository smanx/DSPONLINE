# DSP极简网络终局性能优化方案

> 文档性质：只读分析后的实施计划，不代表已经完成的功能。
> 分析基线：2026-07-29，香港正式节点 `1.0.9` / GameState v40。
> 适用范围：客户端模拟、Worker、React Flow 画布、本地存档、云存档服务和排行榜观测。
> 当前状态：P0、P1 与部分 P3 当前行星画布派生已随 1.0.10 发布；下一阶段为 P2 物流与批次计算，其余工作仍按阶段实施。

## 1. 目标

终局玩家将大量星球殖民，并在建筑、传送带、物流站和戴森系统上持续堆叠。目标不是限制玩家规模，而是在保持以下不变量的前提下，让大工厂仍然可以稳定运行：

- 相同 `GameState` 与相同时间输入必须产生相同确定性结果。
- 生产、输入、输出、线路缓存、在途货物、物流载具、科研和戴森进度必须守恒。
- 旧版 v32-v40 存档、云存档历史和手动槽位必须可读取。
- 画面刷新频率、性能模式和低细节渲染不能改变产量、模拟秒数或存档结果。
- 性能采样只能保存匿名聚合数据，不能上传玩家存档正文。
- 任何后端或数据库变更都必须先备份、验证并保留回滚路径。

## 2. 非目标

本计划不包含：

- 删除玩家建筑、线路、库存、载具、在途货物或戴森进度。
- 通过硬性降低堆叠上限解决性能问题。
- 降低生产速度、降低离线收益或改变时间扭曲规则来换取性能。
- 将上海节点反代到香港节点。
- 新增玩法、黑雾战斗或大规模 UI 重做。
- 在没有真实基准证据的情况下宣称固定百分比收益。

### 3.1 对数据的正确理解

“堆叠 100 万台”通常只增加一个数字，不等于生成 100 万个对象。真正影响 CPU 和画面的主要是：

- 实体对象数量；
- 线路对象数量；
- 物流站槽位和在途路线；
- 戴森层、节点、框架和壳面对象；
- 每秒复制和序列化的状态大小；
- 时间扭曲导致的模拟秒数增加。

排行榜不能直接代表性能分布。服务端目前只读取前 100 名、保留历史最大指标、没有完整重放工厂，并且部分功率/吞吐指标来自当前活动星球。排行榜适合观察终局趋势，不适合作为唯一性能样本。

## 4. 当前性能链路

### 4.1 模拟链路

1. 浏览器每秒积累墙钟时间和模拟时间。
2. 主线程把完整 `GameState` 发送给模拟 Worker。
3. Worker 的 `advanceSimulationBudget()` 先复制整份状态。
4. 模拟器按星球、电网、生产、线路、物流、戴森和制造中心推进。
5. Worker 把完整新状态发送回主线程。
6. React 状态更新，随后画布重新派生节点和线路。

相关代码：

- `src/App.tsx`：Worker 提交、状态回传和画布快照。
- `src/game/simulation.worker.ts`：Worker 入口。
- `src/game/engine.ts#copyState()`：模拟前的深复制。
- `src/game/engine.ts#simulateStep()`：模拟阶段编排。

### 4.2 当前主要热点

#### A. 全状态复制与结构化克隆

同一份状态会经历主线程到 Worker 的结构化克隆、Worker 内部 `copyState()`、Worker 返回主线程的结构化克隆。终局存档越大，内存分配和垃圾回收越明显。

#### B. 全局数组查找

传送带阶段反复用实体数组查找线路两端；电力覆盖判断反复扫描同星球电源；画布线路诊断重复查找节点和目标。随着实体和线路增加，重复查找会变成明显的二次增长。

#### C. 物流重复匹配

物流索引已经存在，但每个模拟请求仍会重建部分运行时数据。派遣、路线经济计算和拥堵诊断之间有重复候选扫描。

#### D. 按星球重复扫描

`simulateStep()` 逐个遍历全部星球，而生产、电力和部分统计函数又遍历全体实体。空星球和没有设备的星球仍然付出扫描成本。

#### E. 画布派生

节点和线路对象在快照发布时重新创建。线路自动避让、线路诊断、端口占用和目标建筑查找会在 UI 线程重复执行。

#### F. 大堆叠的批次循环

普通机器主要是批量计算，堆叠数量对耗时增长很小。但燃料、蓄电交换器和建筑制造中心存在按物品或任务迭代的 `while` 路径，极端堆叠和时间扭曲下可能产生长任务。

#### G. 保存序列化

存档生成会复制持久状态、计算校验、序列化并再次解析验证。终局存档在主线程上可能造成可见停顿。

#### H. 服务端整体写放大

当前 `app_state` 约 6.4 MB，其中匿名分析约 3.37 MB、主档历史元数据约 1.16 MB。每次持久化都要整体序列化这份状态；随着账号和事件增长，Node 事件循环会被同步序列化阻塞。

## 5. 已完成的只读基准

### 5.1 现有仓库基准

- `src/game/performance.test.ts`：500 个普通对象、1,000 条线路，10 个 0.1 秒模拟步通过，测试耗时约 255 ms。
- `src/game/logisticsBenchmark.test.ts`：10、50、100、500 物流站确定性测试全部通过；500 站综合测试约 4.3 秒。

### 5.2 终局规模内存基准

只读临时基准构造了 300/569 个生产对象，并将每个对象堆叠设置为 1、3,500、100 万。4 个模拟秒的耗时基本不随堆叠数量增加，证明普通生产堆叠不是第一优先级。

### 5.3 物流规模内存基准

| 物流站 | 4 个模拟秒耗时 | 主要阶段 |
| ---: | ---: | --- |
| 50 | 约 21 ms | 派遣与候选匹配 |
| 128 | 约 105 ms | 派遣、候选、拥堵 |
| 300 | 约 640 ms | 派遣占主导 |

## 6. 预估收益区间

以下是工程估计区间，必须由完成后的同一批基准重新测量。不同优化存在重叠，不能直接把百分比相加。

| 优化 | 阶段内预估收益 | 玩家可见结果 |
| --- | ---: | --- |
| 实体/线路/电网索引 | 模拟阶段快 20%-45% | Worker 积压减少 |
| 跳过空星球、按星球分区 | 全星球模拟快 15%-35% | 多星球切换和挂机更稳定 |
| 物流候选和路线缓存 | 物流阶段快 40%-70% | 物流站多时卡顿明显降低 |
| 燃料/蓄电/制造中心批量结算 | 受影响设备快 80%-99% | 极端堆叠不再产生长任务 |
| 画布拓扑/运行数据分离 | 主线程帧耗时降 30%-60% | 拖动画布和缩放更顺畅 |
| Worker 长生命周期状态 | Worker/GC 开销降 40%-70% | 时间扭曲时积压更少 |
| Save Worker/单次序列化 | 保存停顿降 60%-90% | 自动保存不明显卡顿 |
| 云存档正文 gzip | 正文磁盘降约 90% | 服务器备份和恢复更轻 |
| SQLite 分表 | 整体写放大降 80%-95% | 云 API 延迟更稳定 |

### 6.1 总体目标

完成第一至第三阶段后，建议目标为：

- P50 后期档 CPU 总消耗降低 20%-35%。
- P95 终局档 CPU 总消耗降低 35%-60%。
- 主线程长帧减少 40%-70%。
- 自动保存停顿减少 50%-80%。
- 低端移动设备持续运行稳定时间提升约 1.5-2 倍。

这些目标是预算，不是对每台设备的保证。最大压力档仍需要低细节模式和合理的性能提示。

## 7. 分阶段实施计划

## P0：观测和压力夹具

### 目标

建立不依赖真实玩家存档正文的可复现终局基准，先知道慢在哪里，再修改算法。

### 工作项

1. 增加匿名存档规模摘要：状态字节数、实体数、线路数、活动星球数、物流站数、在途路线数、最大堆叠、戴森对象数、状态版本。
2. 只在玩家主动开启性能诊断或上传错误报告时记录性能样本。
3. 从线上分位数构造三个合成 fixture：P50、P95、Max。禁止把线上原始存档复制到仓库。
4. 每个 fixture 固定测试 1x、4x、时间扭曲、星球切换、统计页、画布拖动和自动保存。
5. 将 Worker 耗时、主线程长任务、FPS、内存、状态大小和保存耗时写入基准报告。

### 完成标准

- 可以在本地复现 P50/P95/Max 三档。
- 每个报告包含实体、线路、物流和戴森规模。
- 不包含账号、昵称、token、原始存档或完整坐标数据。

## P1：低风险运行时索引

### 目标

消除最明显的重复数组查找，不改变 `GameState` 结构和模拟顺序。

### 工作项

1. 在 `SimulationAdvanceSession` 中建立并复用：
   - `entityById`；
   - `entitiesByPlanet`；
   - `entitiesByPlanetGrid`；
   - `powerSourcesByPlanetGrid`；
   - `beltsByPlanet`；
   - `outgoingBeltsBySourceItem`；
   - `incomingBeltsByTargetItem`。
2. 传送带转运和容量预留统一读取索引。
3. 电力覆盖判断只读取电源集合，不再对实体数组做过滤。
4. 物流站槽位索引保留稳定 ID 顺序，避免每步重复排序。
5. 空星球无设备、无线路、无在途路线时跳过生产和电力阶段。

### 风险

- 索引过期会造成错误物流或错误供电。
- 必须在建筑放置、回收、线路变化、配方变化和载具变化后更新索引。
- 索引只属于运行时，不能进入存档或确定性哈希。

### 完成标准

- 优化前后 1/4/11 倍率的状态哈希一致。
- 10/50/100/128/300 物流站结果一致。
- 旧全扫描路径保留为测试 oracle。

## P2：物流与批次计算

### 目标

让物流站数量和堆叠数量不会把单次 Worker 请求拖成长任务。

### 工作项

1. 缓存稳定的站点候选列表，只在槽位、科技、星球、线路策略或中转站状态变化时重建。
2. 路线经济计算按 `(source, target, vehicleCount, policy, warperBudget)` 缓存。
3. 派遣阶段输出结构化结果，拥堵诊断直接消费结果，不重复寻找伙伴。
4. `burnFuel()` 使用“完整燃料单位数 + 最后一个燃料余量”批量扣除。
5. 蓄电交换器使用批量充放电和余量计算，不按每个蓄电器循环。
6. 建筑制造中心合并相同配方的连续批次，保留 WIP、步骤和暂停原因。
7. 对极端任务采用可恢复的确定性分段，不得丢弃或跳过剩余工作。

### 完成标准

- 50/128/300 物流站基准至少达到预估区间。
- 50,000 台建筑制造中心不会产生不可恢复的单帧长任务。
- 燃料、蓄电器、WIP、产物和在途物资守恒。

## P3：画布和 React Flow

### 目标

让画布更新成本主要取决于可见变化，而不是整个星球的完整状态。

### 工作项

1. 拆分拓扑快照和运行时遥测快照。
2. 节点位置、线路几何和自动避让只在节点移动、连线、断线或线路模式变化时计算。
3. 预计算目标端口、黑洞端口和端点实体映射。
4. `diagnoseBelt()` 接受预构建索引或只读诊断快照。
5. 只对变化节点和当前视口内线路更新 React Flow 数据。
6. `BeltFlowSampler` 只维护独立的流量 Map，不复制整份 `GameState`。
7. 根据实体数、线路数、物流站数和 Worker 积压共同决定性能模式，不能只使用当前实体数阈值。

### 完成标准

- P95 终局档主线程长任务低于 50 ms。
- 桌面 FPS 目标 50+，低端移动目标 30+。
- 80%-200% 字体、横竖屏、节点拖动、线路连接和选择行为不回归。

## P4：Worker 状态和保存流水线

### 目标

减少每秒完整状态复制，并把序列化从主线程移走。

### 推荐顺序

1. 第一阶段只让 Worker 长生命周期复用运行时索引和物流缓存。
2. 第二阶段引入带 revision 的命令队列。普通模拟请求只发送时间预算；玩家命令发送事件和版本号。
3. 第三阶段让 Worker 保持权威运行状态，主线程按刷新频率接收当前星球投影和全局摘要。
4. 保存时请求 Worker 生成一致性快照，由 Save Worker 完成序列化、校验和 IndexedDB 写入。
5. 云同步复用最近一次已验证的导出文本，冲突检测继续按完整校验值执行。

### 风险

这是最高风险的客户端改造，涉及命令时序、撤销重做、页面隐藏、自动保存、云冲突和 Android 生命周期。必须先完成 P1-P3，不能一次性替换全部状态流。

### 完成标准

- Worker 忙碌时玩家命令不会丢失、重复或作用于旧状态。
- 页面刷新、后台、返回菜单和覆盖安装都能保存完整状态。
- v32-v40 存档加载、导出、云上传和历史恢复全部通过。

## P5：云服务存储和排行榜观测

### 目标

消除云端历史正文和 `app_state` 的写放大，同时让排行榜成为可解释的性能观测来源。

### 工作项

1. 增加新的压缩正文表，先支持 raw/gzip 双读。
2. 上传时只解析一次 payload，将校验状态、存档摘要和排行榜指标复用给后续步骤。
3. 保留原始 SHA-256 和内部状态校验，解压后必须重新验证。
4. 将账号、会话、排行榜、分析、玩家、错误、反馈、审计和云档元数据拆成独立表。
5. 对历史正文保留现有恢复语义，不得先删除再压缩。
6. 增加后台匿名规模分布：P50/P75/P90/P95/P99，不输出玩家身份。

### 数据保护流程

1. 使用 SQLite Backup API 创建并验证备份。
2. 在备份副本完成迁移、`quick_check`、旧版本读取和恢复测试。
3. 新代码先在未激活目录启动。
4. 核对账号、主档、历史、正文 SHA-256 和排行榜记录数量不减少。
5. 原子切换代码，观察窗口内保留旧正文表。
6. 观察完成后再单独执行空间回收。

## 8. 性能指标和验收矩阵

### 8.1 建议预算

这些是工程门槛，不是玩法规则：

- P50 档 4x Worker 请求 P95 小于 150 ms。
- P95 档 4x Worker 请求 P95 小于 250 ms。
- Max 档 4x Worker 请求 P95 小于 500 ms，并且不持续积压。
- Worker pending simulation debt 不得持续增长超过 2 秒。
- 主线程长任务小于 50 ms。
- P95 自动保存小于 500 ms，普通档目标小于 200 ms。
- 30 分钟持续运行时，强制 GC 后 JS 堆不持续线性增长。
- 服务器健康接口 P95 小于 50 ms，错误和重启次数为 0。

### 8.2 必测场景

| 类别 | 场景 |
| --- | --- |
| 模拟 | 1x、2x、4x、11x 有效时间扭曲 |
| 离线 | 1h、8h、24h、7d、30d |
| 规模 | P50、P95、Max 合成档 |
| 物流 | 10、50、100、128、300 站 |
| 线路 | 1、64、256、1,024、4,096 并联 |
| 交互 | 拖动、连线、框选、批量改配方、回收、撤销重做 |
| 存档 | 主档、备份、快照、三个手动槽、云冲突、历史恢复 |
| 设备 | 桌面 Chrome、低端 Android、移动横屏/竖屏 |
| 字体 | 80%、100%、125%、150%、200% |
| 兼容 | GameState v32-v40、无内容包和启用内容包存档 |

### 8.3 正确性门禁

- 状态哈希确定性一致。
- 输入、输出、库存、线路缓存和在途货物守恒。
- 生产库存仍为非负整数。
- 暂停、断电、缺料、低供电和页面后台不会丢任务。
- Worker 失败会安全回退，不重复结算时间。
- 云上传失败不会创建错误修订或错误排行榜记录。

## 9. 发布和回滚

- P1-P3 可以作为客户端版本逐步发布，优先使用隐藏开关和灰度。
- P4 必须独立版本发布，保留旧状态流回退开关。
- P5 必须单独进行数据库备份、迁移、隔离恢复和双节点验收。
- 代码回滚默认不回滚数据库。
- 不得在生产库执行测试账号写入测试。
- 不得把真实玩家正文复制到仓库、日志、测试 fixture 或聊天。

## 10. 预期最终结果

完成 P1-P3 后，普通终局玩家应看到画布拖动和挂机积压明显减少；完成 P4 后，时间扭曲和自动保存的卡顿应进一步下降；完成 P5 后，云服务可以在账号增长和历史增长下保持稳定。

最终验收必须以优化前后同一批合成 fixture、同一浏览器和同一设备的实测结果为准，不能只使用理论复杂度或单次手工试玩结论。
