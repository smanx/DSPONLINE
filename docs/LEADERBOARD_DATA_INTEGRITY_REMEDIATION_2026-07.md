# 排行榜异常数据处置方案

> 计划用途：下一次版本更新时执行
> 目标节点：香港正式节点
> 审计范围：`season_01` 主云存档排行榜
> 审计日期：2026-07-30
> 当前状态：仅完成只读审计，尚未修改生产数据

## 1. 处置目标

下一次版本发布时，将当前综合榜第一的“伊卡洛斯”从官方排行榜中移除，同时保留其账号、云存档、登录能力和存档下载能力。

本次不删除云存档、不删除账号、不公开账号 ID、邮箱、IP、设备信息或存档正文，也不把其他两个关联异常账号自动一并处理。其他异常账号只保留内部复核标记，除非运营另行确认处置范围。

排行榜移除应是服务器端的持久资格限制，而不是单纯删除一条当前榜单记录。否则玩家重新上传主档、切换排行榜可见性或服务重启回填后，记录可能再次出现。

## 2. 审计结论

### 2.1 数据库和云档没有损坏

- 香港 SQLite `quick_check` 正常。
- 目标主档当前修订为 4，排行榜提交引用修订 4。
- 修订正文、元数据大小、SHA-256 和 envelope 内部校验一致。
- 4 条保留历史正文全部存在，并通过线上现行存档格式校验器。
- 排行榜峰值指标可以由保留历史重建，未发现排行榜串档或重复累加。

### 2.2 官方玩法不可能产生的字段状态

矿脉实体正常使用 `minerCount` 表示矿机数量，`machineCount` 在初始状态为 0；安装矿机和蓝图部署都会增加 `minerCount`，不会增加矿脉的 `machineCount`。

目标档有 39 个矿脉的 `machineCount` 非零，合计约 13.90 亿。该状态从第一条云存档历史开始就存在。当前服务端只检查非负和安全整数，没有检查“矿脉 `machineCount` 必须为 0”。

### 2.3 材料守恒严重不成立

目标档高阶建筑库存包含约 1 亿级别的时间扭曲装置、微型黑洞装置和超大型出口建筑。仅这几类建筑的最低白糖成本约为 7.300 万亿，而存档累计生产白糖约 6.106 亿，缺口约 1.20 万倍。

该估算已经按当前建筑库存和已放置设备计算，并可扣除初始物资、科技奖励和战役奖励的影响；奖励数量相对于万亿级缺口可以忽略。目标档没有建筑制造中心，`constructionAutomation.totalCrafted` 也为 0，因此没有正常自动制造来源。

### 2.4 跨账号的异常指纹

当前共有 3 份主档出现矿脉 `machineCount` 异常：

- 其中另外两份存档的 28 个异常矿脉 ID 和对应数值逐项完全一致。
- 伊卡洛斯存档包含这 28 个异常矿脉，其中 12 个数值完全一致，之后又扩展到 39 个。
- 另外两份完整存档正文并不相同，但高阶建筑库存仍逐项呈现相同的约 1 亿级填充值模式。
- 三个账号的当前会话和审计记录命中同一个匿名网络指纹，并共享设备名称和客户端类型。
- 注册时的网络指纹并不完全相同，因此 IP 证据只能证明后续访问高度关联，不能单独证明现实身份。

这些证据共同支持“存档被外部修改或异常工具写入，并且多个账号可能从同一修改底档分叉”的判断，但不能从服务器数据绝对证明具体现实人员的主观意图。

## 3. 处置边界

### 3.1 自动处理对象

默认只处理目标排行榜账号：当前 `season_01` 综合榜第一、显示名为“伊卡洛斯”、服务器验证策略为 `main-cloud-save-v1` 的唯一提交记录。

目标解析必须同时满足以下条件：

1. 显示名匹配“伊卡洛斯”。
2. 该提交在当前综合榜实际排名第一。
3. 提交的 `verification.cloudRevision` 等于当前主云档修订。
4. 提交校验和等于当前主云档元数据校验和。
5. 目标的当前指标和修订仍与本审计快照一致，或者通过新的只读审计重新确认同一异常规则。
6. 匹配结果必须唯一；同名账号多于一个时不能使用显示名直接删除。

任何条件不满足都应中止迁移并报告，不得猜测账号 ID。

### 3.2 不自动处理对象

另外两个具有相同异常指纹的账号不在本次默认移除范围内。它们应记录为内部 `review` 状态，不能在公开公告中暴露账号、显示名、IP 或设备关联。

## 4. 推荐实现方式

### 4.1 增加服务器端排行榜资格状态

在服务端持久数据中增加可选的内部字段，例如：

```js
leaderboardModeration: {
  [userId]: {
    status: "blocked",
    reasonCode: "SAVE_DATA_INTEGRITY",
    source: "hk-readonly-audit-2026-07-30",
    createdAt: 0,
  },
}
```

要求：

- 该字段只存在服务端，不返回给普通用户接口。
- `status=blocked` 时，排行榜 GET 过滤提交，排行榜 POST、可见性重新开启和启动回填都不得重新创建提交。
- 云存档 GET、PUT、历史恢复、账号登录和账号导出继续可用。
- 删除账号时一并清理该账号的内部处置标记。
- 归一化未知或损坏的处置记录时只保留合法用户 ID、固定状态、固定原因码和有限长度时间戳。
- 该可选字段不升级 GameState、envelope、云 schema 或 SQLite layout，但必须覆盖 SQLite `app_state` 读回测试。

### 4.2 保持现有提交清理逻辑

执行处置时应同时：

1. 写入内部 `blocked` 标记。
2. 删除该账号当前赛季的 submission。
3. 清理该账号其他赛季中仍公开可见的官方 submission（如存在）。
4. 保留云档正文、历史修订和账号。
5. 写入不含 PII 的内部审计动作，例如 `leaderboard.moderation_blocked`。

禁止只改前端隐藏、只删除榜单缓存或只修改显示名。

### 4.3 兼容排行榜入口

以下路径必须统一尊重处置状态：

- `GET /api/leaderboard`
- `POST /api/leaderboard`
- `POST /api/leaderboard/visibility`
- 主槽上传后的自动排名
- 主槽自动同步后的排名
- 历史修订恢复后的排名
- 服务启动时的排行榜回填

被处置账号尝试重新加入时，应返回稳定错误码，例如 `LEADERBOARD_RESTRICTED`，不要暴露内部检测规则或其他账号关联信息。

## 5. 下一版本发布流程

### 阶段 A：代码和测试

1. 在隔离测试数据中实现内部处置状态和唯一目标解析器。
2. 增加重复执行幂等测试：第二次执行不能增加记录、删除云档或改变修订数量。
3. 增加同名账号测试：非目标同名账号不能被误删。
4. 增加重启回填测试：服务重启后被处置账号不会重新出现。
5. 增加可见性测试：被处置账号不能通过 visibility API 重新加入。
6. 增加云档回归：被处置账号仍能读取、上传、恢复主档，排行榜仍拒绝提交。

### 阶段 B：生产备份和 dry-run

1. 读取香港线上当前 Web/API release、数据库 schema 和备份状态。
2. 使用 SQLite Backup API 创建带时间戳的生产备份。
3. 对备份副本运行 `quick_check`，并确认备份可读。
4. 在只读连接上运行目标解析器，输出匿名摘要：候选数、当前修订、提交修订、校验一致性、将移除的 submission 数量。
5. 候选不是唯一一个时立即中止，不进行写入。

### 阶段 C：原子处置

1. 先发布包含资格检查和幂等迁移的后端版本到新目录。
2. 在隔离数据库副本上启动并验证迁移。
3. 在生产数据库事务中写入 `leaderboardModeration`、删除目标 submission、写入内部审计动作。
4. 等待写入队列完成，再查询目标账号云档元数据和正文修订数，确认没有减少。
5. 查询五个排行榜类别，确认目标不在公开结果中，其他榜单记录数量只发生预期变化。
6. 重启或执行一次只读回填检查，确认目标不会重新出现。
7. 观察窗口内不执行数据库恢复；如代码回滚，只切回后端 release，不回滚数据库。

## 6. 验收标准

- 目标在 `galaxy`、`power`、`upload`、`dyson`、`throughput` 五个类别均不可见。
- 目标账号仍能登录、读取云档、上传合法云档和恢复历史。
- 目标当前主档修订数和历史正文数量没有减少。
- 其他两个异常账号没有被本次自动删除或公开点名。
- 同名普通账号不会被误处理。
- 服务重启、主档上传、自动同步、历史恢复和 visibility API 都不会使目标重新入榜。
- SQLite `quick_check` 仍为 `ok`，备份可独立打开。
- 日志和公告不包含用户 ID、邮箱、token、IP、设备名、存档正文、坐标或详细库存。

## 7. 回滚和申诉

处置标记必须可由管理员在审计批准后撤销，但不能通过普通用户 API 撤销。撤销前应重新进行完整存档审计并记录原因。

不要通过恢复旧数据库来回滚代码。需要恢复数据时，先备份当前数据库，再由负责人决定是否从经过验证的副本恢复。

若玩家申诉，只提供通用说明：检测到存档数据一致性异常，排行榜资格暂时受限；不要透露检测阈值、关联账号、IP 指纹或具体字段，以免帮助绕过检测。

## 8. 更新说明文案

公开更新说明只保留一条简短描述：

```text
检测数据修改异常
```

不公开玩家名称、账号、IP、设备、具体异常字段、数量或处罚过程。
