# 建筑制造中心低帧 Bug 分析

> 日期：2026-07-31
> 范围：只读分析，没有修改游戏逻辑、玩家存档或运行配置。
> 现象：玩家刚进入绿糖阶段、工厂规模不大时出现约 2 FPS；删除建筑制造中心后明显恢复。

## 1. 当前证据

用户提供的性能报告为 `1.0.16+d30daeae3a9f.dirty`，报告环境为 Windows、32 个逻辑核心、32 GB 内存、2552×1274。该报告的工厂摘要是 181 个实体、115 条传送带、28 条在途路线；活动工厂最大的星球为 68 个实体、92 条带、28 条路线。

报告的关键值：

| 指标 | 结果 |
| --- | ---: |
| Worker 模拟平均耗时 | 约 4.85 ms |
| Worker 模拟峰值 | 8.3 ms |
| 主线程帧峰值 | 561.3 ms |
| 60 秒最低采样 FPS | 1.97 |
| Worker 往返峰值 | 1022.5 ms |
| 模拟任务积压 | 0 ms |
| 制造与施工阶段 | 0–0.3 ms |
| 建筑制造计划构建次数 | 0 |
| 建筑制造批次数 | 0 |

采样前约 18 秒 FPS 大多为 2–6；之后逐渐出现 20–85 FPS 的样本。报告没有记录“当前是否存在建筑制造中心、目标库存、任务数”，所以不能仅凭报告证明删除动作发生在某一秒，但这种前低后高的变化与“删除中心后恢复”相符。

## 2. 已排除的方向

这不像 Worker 内的递归制造循环持续占满 CPU：

- Worker 本身只有 2.5–8.3 ms，远低于 200–560 ms 的主线程长帧。
- `pendingTaskMs` 始终为 0，说明模拟时间没有持续积压。
- Worker profiler 的 `constructionMs` 很低，`constructionPlanBuilds` 和 `constructionJobsBatched` 在报告样本中均为 0。
- 内存峰值约 295 MiB，远未接近浏览器约 4.1 GiB 的 JS 堆上限，因此不像内存耗尽或持续泄漏。

“Worker 往返 1022.5 ms”也不等于 Worker 计算了 1022 ms。它是从主线程发送请求到主线程处理回包的总时间，主线程被渲染、保存、垃圾回收或其他同步任务阻塞时也会变大。

## 3. 最可能的根因

### 3.1 建筑制造中心把递归配方规划带到了主线程

画布节点重建时，`src/App.tsx` 会对活动星球的每个实体计算 `getEntityOperatingStatus`（约第 3110 行）。建筑制造中心的状态分支位于 `src/game/engine.ts` 的 `getEntityOperatingStatus`：当存在目标库存缺口时，会调用 `getConstructionAutomationStatus`。

当中心尚未形成持久任务时，`getConstructionAutomationStatus` 会调用 `buildConstructionAutomationPlan`。这个规划器会复制当前星球托盘、遍历可手工配方并调用递归材料规划。`src/game/recursiveCrafting.ts` 中的 `ensureItemOptions` 会：

- 每层过滤并排序能生产目标物品的配方；
- 为每个配方复制工作对象、步骤和决策；
- 递归展开输入材料；
- 最多保留 24 个候选分支。

这套规划适合玩家点击“快速制造”时按需运行，但不适合随着画布每次刷新同步运行。中心被删除后，活动节点列表里不再有这个状态查询，因而会出现“删除中心马上变流畅”。这解释了现象，但仍需 A/B 采样才能确认具体耗时。

### 3.2 画布刷新会重复触发这条路径

`canvasGame` 在游戏状态更新或生产刷新定时器触发时更新；随后节点派生、状态计算、视觉签名和 React Flow 更新重新执行。即使 Worker 模拟很快，递归规划仍然发生在主线程，可能造成长帧和 Worker 回包延迟。

### 3.3 保存是独立的长帧来源

报告中最近一次自动保存约 1216 ms，其中主档写入/读回约 930.6 ms，容量检查约 249.9 ms。保存使用 IndexedDB 队列，但序列化、校验和部分存储 API 仍会与页面主线程竞争。它可以解释部分 200–560 ms 长帧，不能单独解释“删掉建筑制造中心后恢复”，因此应和中心规划问题分开修复和验证。

### 3.4 CSS/React Flow 不是首要证据，但不能完全排除

建筑制造中心有专用卡片和状态动画，画布还会对 68 个节点和 92 条线路重建视觉对象。单个中心卡片本身不应造成持续 2 FPS；如果中心堆叠数量很大、状态不断变化或规划结果被写入视觉签名，才可能放大 React Flow 更新成本。

## 4. 需要优先验证的 A/B 实验

使用同一份存档复制出多份，避免直接覆盖玩家原档。每组运行 60 秒并导出匿名性能报告：

1. 保留中心，自动制造开启，目标库存为 0。
2. 保留中心，自动制造开启，设置一个早期建筑目标但不提供原料。
3. 保留中心，自动制造关闭，保留同一目标库存。
4. 删除中心，但保留其他实体和线路。
5. 保留中心，只隐藏画布节点或切换低细节模式，用于区分 UI 与模拟。

重点比较：主线程帧峰值、FPS、Worker 往返、`constructionMs`、`constructionPlanBuilds`、`constructionPlanCacheHits`、节点派生耗时、长任务数量、保存耗时和内存。若第 2 组显著变慢、第 3 组恢复，基本可以确认“中心状态规划器在主线程触发”；若第 4 组仍然慢，则应优先查保存或 React Flow。

## 5. 开发建议（本次不实施）

1. 把建筑制造中心的递归计划缓存放到 `GameState` 之外的运行时缓存，缓存键至少包含中心目标、科技集合、相关托盘物品版本和配方目录版本。
2. UI 状态只读取 Worker 已生成的轻量摘要：当前阶段、阻塞物品、进度、WIP 数量和 ETA；没有任务时直接显示“目标库存已满足/等待材料”，不在渲染期间重新规划整条递归链。
3. 为 `getConstructionAutomationStatus` 增加独立的 `planMs`、调用次数和缓存命中率，不与 Worker 的 `constructionMs` 混在一起。
4. 为主线程增加 `PerformanceObserver` 的 long task 记录，区分递归规划、React Flow 节点派生、存档序列化和 IndexedDB 等待。
5. 给建筑制造中心增加“暂停自动制造”临时开关；这只能作为用户侧缓解手段，不能替代根因修复。
6. 先做上述 A/B 和回归测试，再决定是否需要把建筑制造计算进一步移到 Worker；不得通过删除任务、截断 WIP 或丢弃副产物来换 FPS。

## 6. 结论

这份报告证明的是“主线程严重卡顿，Worker 模拟本身很轻”，不能证明“递归制造算法在 Worker 内卡死”。结合删除建筑制造中心后恢复的复现结果，当前最高概率根因是：建筑制造中心的递归配方规划被画布/检查器状态查询反复同步执行，中心是触发器；自动保存和 React Flow 重渲染是并行的放大因素。

因此，当前应把问题登记为 **P0/P1 性能 Bug：建筑制造中心状态查询在主线程重复递归规划，造成长帧和 Worker 回包延迟**。修复前需要先完成 A/B 采样和独立计时，不能仅凭删除后恢复就直接重写模拟循环。
