# 开发 Agent 执行提示词：终局性能优化

你是 DSP极简网络项目的高级性能工程师。请根据 `docs/PERFORMANCE_OPTIMIZATION_PLAN_2026-07.md` 分阶段实现终局性能优化。

## 一、工作范围

本任务的目标是降低后期工厂的模拟、物流、画布、内存复制、保存和云服务开销，同时保持所有存档和确定性行为。优先完成 P0-P3；只有 P0-P3 的基准和回归通过后，才能开始 P4。P5 是独立的服务端/数据库发布任务。

## 二、开始前必须做的事

1. 阅读以下文档：
   - `docs/PROJECT_STATUS.md`
   - `docs/ARCHITECTURE.md`
   - `docs/GAMEPLAY_SYSTEMS.md`
   - `docs/DEPLOYMENT_OPERATIONS.md`
   - `docs/TESTING_RELEASE.md`
   - `docs/PERFORMANCE_OPTIMIZATION_PLAN_2026-07.md`
2. 执行 `git status --short`，保留所有已有用户改动。
3. 先检查现有测试、`src/game/performance.test.ts`、`src/game/logisticsBenchmark.test.ts` 和性能监控实现。
4. 不访问或复制生产玩家存档正文。终局夹具必须由合成数据生成。
5. 不连接生产数据库执行写操作，不部署，不重启 VPS，不修改生产配置。

## 三、硬性不变量

- `GameState` 是持久化游戏真相；React Flow 对象不能成为存档真相。
- `advanceSimulation()` 对相同状态和相同时间必须确定性一致。
- 不得改变 1x/2x/4x、时间扭曲、离线结算或活动墙钟语义来换性能。
- 不得删除、截断或隐式返还玩家库存、线路缓存、在途货物、载具、科研、戴森和制造中心 WIP。
- 任何索引只能是运行时数据，不能进入存档或状态哈希。
- 输入、输出、线路、物流槽和任务库存必须保持守恒；可见库存必须是非负整数。
- 旧 GameState v32-v40、envelope v2、云 schema v7 和现有内容包兼容不能被破坏。
- Worker 失败、页面后台、`pagehide`、Android 生命周期和自动保存不能重复结算或丢失时间。
- 不得为了性能直接限制建筑堆叠、线路并联或星球数量。

## 四、实施顺序

### 阶段 P0：基准和观测

实现合成的 P50/P95/Max 终局夹具，至少覆盖：

- P50：约 300 实体、300 线路、40-50 物流站、约 450 KB 存档。
- P95：约 380 实体、500 线路、70-80 物流站、约 800 KB 存档。
- Max：约 569 实体、1,160 线路、128 物流站、约 1.5 MB 存档。

每个夹具必须记录：

- Worker 请求耗时和 pending debt；
- `SimulationProfiler` 所有阶段；
- 主线程 FPS、长任务和内存；
- 节点/线路渲染数量；
- 保存耗时和序列化字节数；
- 1x、4x、有效时间扭曲和离线结算结果。

不要把真实线上存档写入 fixture。不要把玩家 ID、昵称、坐标、token 或 payload 写入报告。

### 阶段 P1：运行时索引

在 `SimulationAdvanceSession` 内增加非持久化索引：

- `entityById`；
- `entitiesByPlanet`；
- `entitiesByPlanetGrid`；
- `powerSourcesByPlanetGrid`；
- `beltsByPlanet`；
- `outgoingBeltsBySourceItem`；
- `incomingBeltsByTargetItem`。

替换模拟中的重复 `find/filter`，但保持稳定数组顺序。电力覆盖、线路转运、线路容量预留、物流站端点和拥堵诊断必须使用同一索引边界。

无设备、无线路、无在途路线的星球可以跳过，但不能跳过活动时钟、必要的全局戴森结算或有有效实体的星球。

### 阶段 P2：物流和批量结算

按以下顺序实现：

1. 复用物流槽位候选列表。
2. 缓存稳定路线经济计算。
3. 派遣结果直接供拥堵诊断使用。
4. 将燃料消耗改为完整单位批量扣除和余量保留。
5. 将蓄电交换器充放电改为批量计算。
6. 将建筑制造中心连续相同步骤合并为批次。

所有批量算法必须在以下情况下保持精确：

- 输出缓存满；
- 输入不足；
- 托盘达到上限；
- 线路或物流槽堵塞；
- 断电、低供电、暂停；
- 任务步骤刚好跨越边界；
- 时间扭曲和大离线时间步。

不得简单设置“最多处理 N 个”后丢弃剩余工作。若需要分段，必须保存剩余预算并在下一次继续，且最终状态与旧算法一致。

### 阶段 P3：画布和 React Flow

拆分：

- 拓扑快照：位置、端口、线路几何、线路模式；
- 遥测快照：库存、流量、供电、堵塞、生产进度。

线路几何只在节点移动、连线、断线或线路模式变化时重算。预构建实体 ID、端口占用、黑洞端口和目标建筑映射。避免每个节点过滤全部线路、每条线路查找全部实体。

`BeltFlowSampler` 不得通过复制整份 `GameState` 传递只读流量数据。优先返回独立 Map 或按线路 ID 的轻量遥测。

性能模式触发条件至少综合：

- 当前星球实体数；
- 当前星球线路数；
- 物流站和在途路线；
- Worker 延迟和 pending debt；
- 当前视口缩放。

保持节点、线路点击、拖动、连线、选择、多选、手机端口吸附、80%-200% 字体和横竖屏行为不变。

### 阶段 P4：Worker 和保存

只有 P0-P3 完成后再做：

1. Worker 长生命周期复用运行时索引。
2. 引入命令 revision 和有序命令队列。
3. 逐步让 Worker 持有权威运行状态。
4. 主线程只接收当前星球投影和全局摘要；保存时请求完整一致性快照。
5. Save Worker 负责序列化、校验、IndexedDB 写入和读回确认。

任何命令队列或快照 revision 冲突都必须暂停自动覆盖并显示冲突，不能静默丢弃玩家操作。

### 阶段 P5：云服务和数据库

这是独立发布，不要和核心模拟改动混在同一个提交中。

推荐：

- 云存档正文增加 raw/gzip 双读格式；
- 上传时解析一次并复用校验、摘要和排行榜指标；
- 账号、会话、排行榜、分析、玩家、错误、反馈、审计和云档元数据分表；
- 先 SQLite Backup API 备份和隔离恢复，再切换；
- 保留旧正文表直到观察窗口结束；
- 核对账号、主档、历史、正文 SHA-256 和排行榜数量不减少。

不要在生产环境运行自动化写测试，不要用测试数据覆盖生产路径。

## 五、测试要求

每个阶段至少运行：

```text
npm run typecheck
npx vitest run src/game/performance.test.ts src/game/logisticsBenchmark.test.ts
npm test -- --runInBand
npm run build
```

根据改动增加：

- 确定性哈希测试；
- 1/4/11 倍率测试；
- 1h/8h/24h/7d/30d 离线等价测试；
- 物流 10/50/100/128/300 站测试；
- 线路 1/64/256/1024/4096 并联测试；
- 建筑制造中心 WIP、燃料、蓄电和输出堵塞测试；
- Worker 忙碌期间命令、保存、页面后台和恢复测试；
- v32-v40 存档迁移和云存档兼容测试；
- 桌面、手机横屏/竖屏、80%-200% 字体的 Playwright 回归。

不能声称“性能提升了 X%”除非使用同一设备、同一 fixture、同一模拟时间和同一测试次数对比，并报告中位数、P95、内存和确定性结果。

## 六、交付格式

每个阶段完成后必须报告：

1. 修改了哪些文件以及每个文件的职责。
2. 哪些状态流或索引发生变化。
3. 优化前后 P50/P95/Max 的耗时、FPS、内存和保存耗时。
4. 是否改变了存档版本、envelope、云 schema 或数据库 layout。
5. 运行了哪些测试，完整命令和结果是什么。
6. 已知风险、未完成项和回滚方式。

如果某项优化需要改变持久化格式、Worker 权威边界、云 schema、SQLite layout 或生产部署，请先停在设计评审，不要直接继续修改。

## 七、完成定义

只有满足以下条件才可以认为本任务完成：

- P50/P95/Max 合成终局档有基线和优化后报告。
- 确定性哈希和资源守恒全部通过。
- Worker 不持续积压，主线程长任务达到预算。
- 自动保存、云冲突、历史恢复和页面生命周期不丢数据。
- v32-v40 旧存档和内容包兼容。
- 服务端若有变更，已完成备份、隔离恢复、数量核对和回滚演练。
- 没有修改或暴露真实玩家存档正文、账号信息、密钥、token 或生产凭据。
