# 多核模拟开发方案

> 文档性质：只读分析后的开发计划，不代表功能已经实现。
> 目标：在不改变生产、物流、存档和确定性规则的前提下，把终局模拟拆分到多个 Worker 或桌面端线程，降低单个 Worker 的长任务和界面卡顿。
> 基线：2026-07-31，1.0.16，当前模拟主要由一个持久化 simulation Worker 串行推进。

> 2026-08-01 执行进度：P0 基准与量子物流 P1 单 Worker 减负已完成。402 塔批量升级、接入和交接本体分别下降 94.8%、97.4% 和 98.9%；真实终局样本切为稳定量子物流后，五模拟秒墙钟下降 63.08%。1/2/4/8/12/16 Worker 理想只读分区探针已完成，但 8 Worker 的传输与合并中位数为 9.23 ms，高于量子阶段本身的 3.12 ms，因此生产多 Worker 仍保持关闭。完整数据见 [多核模拟与量子物流性能报告](./MULTICORE_SIMULATION_BENCHMARK_2026-08-01.md)。

## 1. 先说结论

浏览器不会因为电脑有 8 个核心就自动把一段 JavaScript 模拟拆成 8 份。当前架构已经把模拟移到 Worker，因此主线程可以绘制界面，但 Worker 内部的生产、传送带、物流、电力和戴森计算仍按既定顺序串行执行。

多核改造可以带来收益，但不能简单地把 `GameState` 同时交给多个线程。多个线程同时修改同一份状态会造成顺序不确定、库存重复扣除、物流重复派遣和存档结果不一致。正确做法是先按互不写冲突的领域或星球划分任务，再在固定同步点合并结果。

## 2. 性能基线和收益预算

上一轮终局样本的平均模拟帧约 110.4ms，P95 约 123.4ms；其中物流约占 64.8%，物流派遣约占 46.2%，传送带约占 22.8%。这些比例是优化优先级依据，不是每个玩家都必然相同。

预估收益必须用同一批合成存档、同一设备和同一测试时长复测，不能相加，也不能当成承诺：

| 阶段 | 范围 | 预计模拟耗时下降 |
| --- | --- | ---: |
| A | 运行时索引、按星球分区、减少重复扫描 | 10%–25% |
| B | 量子共享池/聚合物流，减少逐站逐船匹配 | 20%–40% |
| C | 4 个 Worker 并行生产、电力、物流分区 | 35%–60% |
| D | 桌面端 4–6 个 Worker，并行物流和星球分区 | 50%–70% |
| E | 8 核设备上的深度分区、批次结算和主线程投影 | 60%–75% |

阶段收益有重叠。例如阶段 C 已经包含阶段 A 的基础设施，不能把 25% 和 60% 直接相加。若物流仍是不可拆的串行瓶颈，增加核心不会继续线性提速，这由 Amdahl 定律决定。

## 3. 推荐架构

### 3.1 主线程

- 只负责输入、React/React Flow 绘制、当前星球投影和命令队列。
- 不直接修改模拟权威状态。
- 命令携带递增序号和状态 revision；Worker 返回已应用的序号。

### 3.2 模拟协调 Worker

- 持有权威 `GameState`、确定性随机种子和运行时索引。
- 按固定模拟秒推进，向子 Worker 分发只读快照或领域输入。
- 在固定屏障合并生产、物流、电力等领域的增量结果。
- 只有协调 Worker 可以提交最终状态和存档快照。

### 3.3 领域 Worker

建议先拆分为以下几类，而不是按每栋建筑开线程：

1. **生产/采集 Worker**：按星球分区计算矿机和生产建筑。
2. **传送带 Worker**：按星球或线路连通分量推进货物和缓存。
3. **物流 Worker**：先使用稳定的候选索引和聚合派遣，再按星球/航线分区。
4. **电力与戴森 Worker**：按星球电网计算，最后返回供电系数和发电摘要。

每个 Worker 只产生增量结果，例如“扣除某物品 100、增加某物品 50、线路缓存转移 20”，不能直接写另一个 Worker 的对象。协调 Worker 按固定 ID 顺序合并增量，出现冲突时使用确定性规则并记录诊断。

### 3.4 桌面端

Electron 桌面端可在验证浏览器 Worker 版本后，评估 Node `worker_threads`。桌面端线程不是免费性能：仍然需要消息复制、合并和错误恢复。桌面专用优化只能作为增强，不能让网页版失去完整功能。

## 4. 分阶段开发

### P0：观测和基准

- 复用 P50/P95/Max 合成终局夹具。
- 记录每个领域耗时、Worker 往返、pending simulation debt、主线程长帧、节点/线路数量和内存。
- 增加确定性哈希、库存守恒和 1x/4x/时间扭曲对照测试。

**门槛**：没有稳定基准和回归 oracle，不开始拆分状态。

### P1：单 Worker 内先减负

- 建立 `entityById`、`entitiesByPlanet`、`beltsByPlanet`、电网和物流槽位索引。
- 空星球跳过生产、电力和物流阶段。
- 合并连续建筑制造批次、燃料结算和路线候选缓存。
- 把画布拓扑和运行时遥测分开，避免每个模拟帧重建所有节点/边。

**预期**：不改变线程模型，先降低 10%–25% 模拟开销，并为并行提供边界。

### P2：可并行的星球分区

- 生产、电力和戴森按星球独立计算。
- 传送带只在所属星球推进；跨星球物流只在屏障点交换聚合请求。
- 每个分区先在本地副本上运行，再返回增量；协调 Worker 固定顺序合并。
- 保留旧串行路径作为测试 oracle 和回滚开关。

**预期**：4 个 Worker 在终局档约 35%–60%，实际取决于物流占比和跨星球依赖。

### P3：聚合物流和量子共享池

- 不逐艘运输船持续模拟，而是保存舰队总数、忙碌数、总运力、翘曲器消耗和航线冷却。
- 同一物品、同一来源/目标策略的请求在 5 秒结算边界聚合。
- 传统塔和量子塔之间使用兼容桥，先保证库存和在途物资守恒。
- 聚合物流结果再分发给各星球分区，避免所有 Worker 访问同一站点数组。

**预期**：物流阶段约 20%–40% 额外收益；它同时决定多 Worker 的上限。

### P4：桌面多 Worker 和保存 Worker

- 浏览器版本先稳定；桌面端再启用 4–6 个 `worker_threads`。
- 保存时由独立 Save Worker 生成一致性快照、序列化、校验和写入 IndexedDB/文件。
- 主线程只接收当前星球投影和全局摘要，不接收每次完整状态用于绘制。
- 加入 Worker 崩溃重建、命令重放、页面后台和自动保存恢复流程。

**预期**：桌面终局约 50%–70%；不能保证所有设备都达到该区间。

### P5：深度优化

- 只在基准证明需要时继续细分线路和物流分量。
- 使用结构化增量、可转移数组或共享只读缓冲区减少克隆。
- 采用 8 核设备的自适应 Worker 数量，低端手机默认 1–2 个，避免线程调度和内存反而变慢。

**预期**：理想 8 核设备约 60%–75%，仍受串行合并和浏览器调度限制。

## 5. 必须保护的规则

- 相同状态和相同模拟时间必须得到相同状态哈希。
- 输入、输出、建筑缓存、传送带缓存、运输船/运输机、翘曲器、在途货物和制造中心 WIP 必须守恒。
- 生产、断电、缺料、暂停、离线收益、时间扭曲和科技进度语义不能因线程数改变。
- 运行时索引、线程编号和性能计时不能写进 `GameState` 或存档。
- Worker 失败只能回退到最近一致快照，不能重复结算同一个命令或模拟时间。
- 旧版本存档、云存档、手动导入和移动端仍使用同一套确定性结果。

## 6. 验收矩阵

至少覆盖：1x/4x/有效时间扭曲、1 小时/8 小时/24 小时离线结算、P50/P95/Max 合成档、10/50/128/300 物流站、64/256/1024 条线路、建筑制造中心递归制造、暂停/断电/缺料、页面后台、自动保存、云冲突、桌面 Chrome、移动 Chrome 和 Electron。

每个版本必须同时比较：Worker 阶段耗时、主线程长帧、FPS、pending debt、内存、存档字节数、状态哈希、库存守恒和生产统计。没有这些对照数据，只能说“完成了并行框架”，不能说“性能提升了多少”。

## 7. 回滚策略

- P1–P3 使用隐藏开关，发现确定性或库存问题时回退到串行路径。
- P4 单独发版，保留旧状态流和旧保存流程。
- 不通过清档、截断库存或删除在途路线来“修复”性能。
- 发布前复制合成夹具，发布后验证旧存档导入、导出、云上传和历史恢复。

## 8. 最终判断

多核值得做，但第一步不是立刻创建更多线程，而是把物流、传送带、生产和电力的边界做成可验证的增量接口。按照 P0→P1→P2→P3→P4 的顺序，既能先获得低风险收益，也能在任何阶段发现确定性或库存守恒回归时安全回退。
