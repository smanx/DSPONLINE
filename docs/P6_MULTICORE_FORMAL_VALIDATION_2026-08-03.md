# P6 多 Worker 正式路径验证报告（2026-08-03）

> 状态：开发实现与本地验证完成；未部署、未更新下载页、未改变 GameState 或存档格式。

## 结论

P6 已经从只读探针发展为真实的协调 Worker + 星球阶段子 Worker 路径，但本次结果明确不支持在生产环境开启。

- 真实终局档发现并修复了一处确定性缺口：分区结果合并后无条件重建运行时索引，会让后续物流和线路屏障使用与串行路径不同的缓存代次，完整状态哈希不一致。
- 修复后，单 Worker、2 Worker 和 4 Worker 在 1、4、12、60、600 秒口径下的完整状态哈希一致；载具、翘曲器、在途货物和量子库存摘要一致。
- 子 Worker 请求从“22 颗行星各复制一份状态”改为“按负载生成 2 或 4 个批次”；快照只保留本批行星实体和全局物流站上下文，不携带传送带。2/4 Worker 路径自身相对旧实现下降约 65.6%/67.2%。
- 即使如此，最终 2/4 Worker 仍比单 Worker 慢约 40%～73%。生产与电力只占该存档整步约 12%，理论最大收益本来就低于 15% 门槛，无法抵消事务基线、结构化克隆、消息和合并成本。
- 生产构建现在硬关闭 P6；开发环境仍可显式运行回归和性能实验。默认单权威 Worker 不变。

## 实现边界

1. 协调 Worker 持有唯一权威 `GameState`，执行探索、手搓、戴森衰减、物流缓存、输入线路和量子准备。
2. 行星按本地生产/电力实体权重做稳定贪心分区，最多生成与子 Worker 数相同的批次。
3. 每个批次只携带本批行星实体、全局物流站只读上下文、戴森接收计划、线路输出容量额度和内容包注册表指纹。
4. 子 Worker 顺序计算批次内行星，返回实体、电网、行星指标、累计产量增量和供电计划。
5. 协调 Worker 在写入前验证所有行星和实体恰好返回一次，再按行星 ID 固定顺序合并；传送带、物流、量子和戴森全局阶段继续串行。
6. 任一 Worker、注册表或分区错误都会恢复请求前完整基线，并用串行路径只结算一次相同的 simulationSeconds/wallSeconds。

## 性能结果

下表是协调 Worker 内部耗时；正数表示相对单 Worker **变慢**。1/4/12/60 秒使用预热后的多样本，600 秒用于长时守恒和稳定性，只运行一个样本，不称为 P50/P95。

| 每次请求模拟秒 | 单 Worker 平均 | 2 Worker 平均 | 相对变化 | 4 Worker 平均 | 相对变化 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 秒 | 58.21 ms | 100.62 ms | +72.9% | 96.39 ms | +65.6% |
| 4 秒 | 208.48 ms | 317.18 ms | +52.1% | 311.98 ms | +49.6% |
| 12 秒 | 598.60 ms | 882.37 ms | +47.4% | 863.70 ms | +44.3% |
| 60 秒 | 2,574.93 ms | 3,824.03 ms | +48.5% | 3,801.57 ms | +47.6% |
| 600 秒（单样本） | 23,275.10 ms | 35,837.20 ms | +54.0% | 35,367.70 ms | +52.0% |

1 秒稳态 P50/P95：单 Worker `50.5/120.9 ms`，2 Worker `93.9/159.2 ms`，4 Worker `86.0/163.8 ms`。多 Worker 既没有降低中位耗时，也恶化了尾部耗时。

旧正式路径每秒向 22 个行星任务各发送完整状态，2/4 Worker 平均约为 `292.78/294.13 ms`。批次和紧凑快照后为 `100.62/96.39 ms`，分别下降约 65.6% 和 67.2%，但仍未快过单 Worker。

60 秒单 Worker阶段平均值说明了上限：

| 阶段 | 耗时 | 占完整模拟 |
| --- | ---: | ---: |
| 传送带 | 1,432.83 ms | 55.6% |
| 物流 | 398.27 ms | 15.5% |
| 量子物流 | 108.00 ms | 4.2% |
| 生产 | 126.10 ms | 4.9% |
| 电力 | 175.70 ms | 6.8% |

当前 P6 只并行生产和电力，合计约 11.7%。即使这部分瞬间完成且没有任何通信成本，整步下降也不足 15%；继续增加 Worker 数不会解决 Amdahl 上限。

| 口径 | 三路共同状态哈希 | 结果 |
| --- | --- | --- |

每组同时比较物流运输机、运输船、翘曲器、在途货物/载具和量子库存摘要，均未发现丢失、复制或负数。60 秒单元回归还比较了单段与 60 次 1 秒分段；排除只反映采样频率的 `productionHistory` 后，权威状态哈希一致。

故障注入用一个无法归属到合法行星的诊断实体制造分区完整性失败。协调 Worker 在任何合并写入前拒绝结果、恢复基线并执行串行回退；最终哈希与直接串行相同，`elapsedSeconds` 只增加 2 秒，证明时间预算没有丢失或重复。

## 发布判断与后续方向

P6 的正式执行、验证和回退边界已经完成，但“生产默认开启”明确不通过。保持关闭不是未完成，而是性能门禁发挥作用。

若后续继续多核，必须先改变可并行占比：优先把传送带编译为按行星的运行时数字网络，再评估可转移数组或持久分区 Worker；物流只有在伙伴匹配、在途账本和公平游标能形成确定性增量协议后才适合拆分。任何后续路径仍需在同一夹具上达到完整模拟至少下降 15%、P95 不恶化、状态哈希和物资守恒一致，才可重新讨论生产启用。
