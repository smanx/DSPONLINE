## 结论

云上传阻塞已在源码中定位并修复：`SqliteStore.commitCandidate()` 曾在任意 revision/user 删除后同步调用全量 `garbageCollectCloudPayloadBlobs()`，其 alias 收集会对整个 `cloud_save_payloads` 运行 `substr + length(CAST(... AS BLOB))`，随后又解析所有引用 blob。第 21 条上传裁剪旧 revision 因而可能同步扫描大库并阻塞主线程。新在线路径只收集当前事务删除行实际涉及的 alias，以启动时建立的实际 alias/refcount 索引判断候选是否仍被引用，并只按候选 checksum 主键删除。离线全量 GC 原样保留。

Release 复核指出的保守性边界已经纳入设计：启动索引不再由 `app_state` metadata checksum 或 blob 表门控，而是审计每个实际 payload 行的 `typeof(payload)` 和最多 161 字符投影。metadata 缺失、错误或指向 B 时，只要实际 alias 指向 A，A 仍计入引用。malformed alias 或 BLOB/integer 等非 TEXT 动态类型不会被误判为 direct；审计标记不完整，在线回收会保留所有候选。该策略宁可暂留 orphan，也不误删可能被引用的 blob。

玩家报告的“所有微型黑洞统一暂停”未在已发布运行时基线复现。独立 `32daa4f` Chromium 证据表明运行态 `false/true` 和玩家暂停 `true/true` 能经过同步保存、save Worker、IndexedDB、导出导入、云正文准备及加载保持；缺字段旧档继续安全归一为 `true/false`。补丁仅要求当前 v46 黑洞在保存时已有显式布尔字段，并在共享稀疏省略之后再次写回两个 own properties。若某存档已是 `true/true`，没有可靠持久证据区分主动暂停与假设中的回归暂停，因此禁止批量自动启用。

## 数据与兼容边界

- GameState v46、save envelope v2、cloud schema v7、SQLite layout v2 不变。
- `cloud_save_payloads` 直接 `SELECT` 合同和 direct legacy payload 保持不变；不迁移、不重写生产正文。
- checksum、revision、20 条历史、恢复、排行榜和物资守恒语义不变。
- 1.0.37 previous-stable/兼容边界不变；代码回滚不恢复数据库。
- 启动固定前缀审计是逐逻辑行工作；在线单 revision 删除只访问目标复合主键、候选 checksum 和对应 refcount，不遍历其他引用，不读取或验证无关 payload/blob。

## Release 交接与回滚

开发任务没有 SSH、生产数据库、线上 Nginx/systemd/软链、下载页或稳定原生制品操作。香港现有上传维护锁现在不能仅凭开发完成解除。Release 必须复算不可变 Web/API manifest，在未激活 API 和临时 SQLite 复验 21 次裁剪、共享 blob、失败回滚与 health/ready，完成正式切换后的 backlog/WAL/延迟/错误观察，再显式决定解锁。建议解除后仍保留可逆 telemetry 边缘熔断。

若新代码异常，只回切香港 Web/API 代码；不恢复数据库，不删除 revision，不手工清 orphan。启动审计不完整时的 orphan 保留是安全退化，后续只能在独立备份、离线全量维护审计和新的数据维护授权下处理。黑洞既有 `true/true` 不自动更改，玩家如受影响只能逐个确认；这是无法无歧义修复的一次性遗留影响。
