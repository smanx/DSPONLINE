- 戴森壳层复制使用独立分配起点，副本不继承目标恒星系的历史结构点或壳面帆。

## 云存储上线修复

第一次香港切换使用候选提交 `87f482ae18c6`。该候选继承了上线前已经存在的单行 JSON 写放大：生产库的 `app_state` 为 136,809,779 字符，任何登录、心跳、指标或云存档写入都会在 Node 主线程重新序列化并同步更新整行。旧进程峰值约 1.6 GB，健康接口反复超过 8 秒并被两分钟 timer 重启。上海在问题修复前没有切换。

最终提交将账号、会话、指标和云存档元数据保留在紧凑 `app_state`，把每个槽位的每个历史正文拆到 `cloud_save_payloads` 独立行。迁移和后续写入使用同一 SQLite 事务；历史裁剪、账号注销、修订恢复、账号导出和排行榜校验都通过独立正文接口完成。云 API schema 仍为 v7，客户端和 GameState 不变。

香港生产副本迁移门禁记录：

- 一次性迁移约 8.1 秒，服务尚未监听时完成。
- `app_state` 从 136.8 MB 降至约 2.55 MB。
- 551 个元数据修订与 551 个正文行逐键一致；SHA-256 和字节数均无差异，`quick_check=ok`。
- 隔离服务常驻约 100 MB；10 次持久化期间健康接口最大 1.4 ms。

正式切换后的香港观察记录：24 次、240 秒健康采样全部为 200，最大 10.407 ms，`NRestarts=0`，RSS 约 133～162 MB。上线后备份时生产流量已自然增长到 78 个账号和 559 个有效修订，元数据与正文行仍一一对应。上海 14 次、140 秒采样全部为 200，最大 1.506 ms，`NRestarts=0`，RSS 约 65～66 MB。

存储布局 v2 写入后，旧 API 不能正确读取独立正文表。两地 `previous-release` 因此都配置为“上一版 Web + 当前 v2 API”，代码回滚不会把 API 切回旧存储实现，也不会恢复数据库。
